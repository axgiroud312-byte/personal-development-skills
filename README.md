# 中文开发技能

用中文说明要做什么，Agent 根据任务选择技能。共九个技能：六个开发技能、一个界面设计技能 `design-ui`、一个工作讲解技能 `explain-work` 和一个项目配置技能 `setup-project-skills`，可以分别使用、按需要组合。

设计参考 [Matt Pocock 的 Skills](https://github.com/mattpocock/skills)，内容由用户独立维护。

## 安装

需要 Node.js 22.20 或更新的受支持版本（包含 npm / npx）和 Git，并能访问 npm 与 GitHub。

使用 [Skills CLI](https://github.com/vercel-labs/skills) 从本仓库默认分支安装，无需单独发布 npm 包。安装的是 Agent 的工作方法和参考文件；React、shadcn 等项目依赖在实际开发时按需安装。

### 给 Codex 安装整套技能

希望各个项目都能使用时，在终端运行：

```sh
npx skills@latest add axgiroud312-byte/personal-development-skills --skill '*' --agent codex -g
```

`--skill '*'` 选择仓库内全部 9 个技能，`--agent codex` 指定 Codex，`-g` 表示安装到用户级技能目录，供多个项目使用。按安装器提示完成安装；安装后在目标项目中开启新会话。

需要建立项目约定时，可以说：“使用 setup-project-skills，为这个项目配置开发约定。”它核实文档、任务和运行入口，在项目的 Agent 入口文件中写入简短项目索引，并配置固定状态入口与维护约定；技能安装由上面的 CLI 完成。已有项目约定足够时，直接提出开发需求。

### 选择项目范围、部分技能或其他 Agent

仅在一个项目使用时，先进入该项目目录，再运行同一命令并去掉 `-g`。希望交互选择技能与 Agent 时运行：

```sh
npx skills@latest add axgiroud312-byte/personal-development-skills
```

交互安装默认针对当前项目；需要全局安装时追加 `-g`。其他 Agent 的标识见 [安装器支持列表](https://github.com/vercel-labs/skills/blob/main/docs/agents.md)。

先查看可安装的技能，不执行安装：

```sh
npx skills@latest add axgiroud312-byte/personal-development-skills --list
```

也可以明确指定技能和目标 Agent。例如，将 Issue、单项开发和整套开发三个技能安装到当前项目，供 Codex 使用：

```sh
npx skills@latest add axgiroud312-byte/personal-development-skills --skill to-tickets implement implement-spec --agent codex
```

### 更新已有安装

从旧版升级到整套新版时，在原来的安装范围重新运行全部技能安装命令。下面以 Codex 全局安装为例，它会取得当前仓库内容，并包含新增的 `design-ui`；已有同名技能会被更新，自己改过安装副本的内容应先保存：

```sh
npx skills@latest add axgiroud312-byte/personal-development-skills --skill '*' --agent codex -g
```

新版已将 `grill-with-docs` 的讨论与记录能力合并到 `grilling`。重新安装不会自动移除已退役的旧技能；曾安装过旧版时，再移除旧入口：

```sh
npx skills@latest remove grill-with-docs --agent codex -g
```

如果旧版安装在项目中，在那个项目目录执行上述两条命令并去掉 `-g`；如果安装给其他 Agent，替换 `--agent` 的值。如果多个 Agent 共用旧技能，还需检查其他安装，安装器可能保留仍被使用的共享副本。移除前核对安装器列出的目标，完成后开启新会话。新安装无需执行移除命令。

## 技能一览

| 你可以这样说 | 对应技能 |
| --- | --- |
| 帮我把这个想法问清楚／边聊边记录 | `grilling`：澄清关键决策，按需记录结论 |
| 统一一下业务术语和关系 | `domain-modeling`：检查并补齐业务定义、关系和规则 |
| 设计一下界面／按这个参考做关键页面 | `design-ui`：确定呈现与交互规范，交付共享 Token、组件选型与可操作样板 |
| 把需求写成 Spec | `to-spec`：澄清关键决策、检查领域模型，再设计整体方案 |
| 根据这段计划直接拆任务 | `to-tickets`：细化局部设计、具体交付和验收 |
| 把这个问题修好／完成这项任务 | `implement`：完成一项开发 |
| 按方案把整套功能连续做完 | `implement-spec`：连续完成整套开发 |
| 讲讲刚才做了什么／做完后解释一下 | `explain-work`：解释工作结果、原理与验证范围 |
| 为这个项目配置开发约定／更新项目索引 | `setup-project-skills`：维护 Agent 入口文件里的项目索引，配置固定状态入口与开发约定 |

## 按需要组合

已有明确任务时直接实施，不为小修补齐文档；需要澄清时使用唯一的讨论入口 `grilling`。只讨论就在聊天中收束，要求边聊边记录时再更新项目文档。目标、主要场景、范围、关键取舍和完成标准足以支持下一步时结束提问。

直接要求写 Spec 时也先检查信息是否足够：事实由 Agent 调查，低风险可逆细节自行决定，无法调查解决且会改变目标或整体方案的选择交给用户。默认一次聚焦一个关键决策，说明推荐与影响。关键决定未明确时标为草稿和待定，不把假设当作已定方案。

新业务功能的主要衔接是：**澄清使用场景 → 检查领域模型，复用或补齐业务定义 → Spec 整体设计（有 UI 时与 design-ui 往返配合）→ Issue 细化任务 → 开发与验收**。用户直接要求写 Spec、拆任务或开发时，由 Agent 主动衔接所需检查，无需用户逐个调用技能。

领域模型检查放在 Spec 划分技术模块和确定协作方式之前：核对主要场景中的业务对象、关系、归属、生命周期和规则。已有定义足够且一致时直接复用；缺失或冲突时主动使用 `domain-modeling` 补齐当前缺口。目标和范围可以先写草稿，依赖未解决业务含义的模块设计暂不定稿。核心场景能讲通即可继续，不要求建模所有未来业务或另建重复文档。

需求和核心领域定义清楚后，涉及 UI 的工作按需衔接 [`design-ui`](skills/design-ui/SKILL.md)。有视觉参考时优先遵循参考，核对布局和几何；无参考时由 Agent 结合产品需求推荐一个方向，说明理由后直接制作样板。默认交付设计规范、实际共享 Token、本次组件选型清单和可操作的关键页面样板；明确只讨论或只要文稿时按该范围交付。已有设计系统直接复用，只补本次缺口。

`design-ui` 与 Spec 可往返调整；拆具体 UI Issue 前，应有足够的设计方向、关键流程、Token、组件与交互状态依据。shadcn 是默认基础，适配的成熟社区开源组件优先补缺，也可沿用项目已有或自研组件；明确选定 registry，开发延续本次清单并按需安装。已有依据足以支持的小改动直接实施，不要求每次重做设计、建设展示站或安装全部组件。

通用 SaaS、工作台与 Agent 界面采用 [前端默认搭配](skills/design-ui/references/frontend-defaults.md)：React、TypeScript、Tailwind CSS v4 与 shadcn 为基础，按需选择表单、表格、图表、日期、拖拽、状态、消息流和节点画布方案。所有组件共用一套颜色、字体、间距、圆角与状态规则，同一种能力优先使用同一个方案。项目配置和 Spec 记录实际选用项，Issue 与开发沿用；已有项目先适配，不因默认表自动迁移或安装全部依赖。

| 记录 | 负责的决定 |
| --- | --- |
| 领域记录 | 业务对象是什么、相互关系、归属、生命周期和业务规则 |
| Spec | 目标、范围、技术模块职责与协作方式、技术上的数据管理、共同技术约束和整体完成标准，引用领域与界面设计依据 |
| 界面设计规范 | 设计方向、页面与交互规则、组件选型及样板入口；沿用项目位置，缺省 `DESIGN.md` |
| 共享 Token 源码 | 实际 Token 值，沿用项目 token 或 CSS 源文件，由样板与业务组件共同使用 |
| Issue | 具体交付、局部接口或字段、状态与异常处理、任务依赖和具体验收步骤 |
| 实施 | 在已有约束内决定具体代码写法，依据新事实更新相关记录 |

业务定义与规则在领域记录中统一，Spec 和 Issue 引用；多个模块依赖的技术接口或约定在 Spec 或它引用的一份权威设计文档中统一，Issue 引用。呈现与交互决定由界面设计规范维护，实际 Token 值只保留在共享源码中，文档引用其位置。单项任务的局部设计由 Issue 承接。每个决定只维护一份当前有效正文，发生变化就更新对应依据及受影响任务。

例如，领域模型先说明“任务、一次运行、生成结果”的关系，以及重试是否产生新运行、是否保留旧结果；Spec 再决定哪些模块负责执行和保存，Issue 细化重试接口、提示与验收。业务对象与技术模块不要求一一对应。

领域模型与 Spec 可以往返调整。拆 Issue 和开发时发现新业务概念或规则变化，先更新领域定义，再核对受影响的 Spec、任务设计、验收与实现，避免只改代码或让不同 Agent 各自解释。明确的小修仍可直接实施；检查关注业务含义是否清楚，不检查前一个技能是否执行过。

项目配置已明确时直接使用开发技能。需要建立或调整项目索引、状态入口、文档位置、领域与界面设计衔接、任务跟踪或验证约定时，使用 `setup-project-skills`；沿用项目现有约定，不要求每次任务重新配置。

## 项目入口索引与当前状态

`setup-project-skills` 在目标项目的 Agent 入口文件中维护固定的 `## 项目索引` 段落。入口沿用项目现有分工；只有 `CLAUDE.md` 时写入该文件，只有 `AGENTS.md` 时写入该文件，两者都没有时新建 `AGENTS.md`。两者都有时维护一份索引，按原有分工引用。再次执行按标题原位更新，保留其他内容，不重复追加。

**索引放常驻事实，Skill 负责流程，状态页保存当前进展。** 索引用一张短表指向业务术语与领域记录、Spec、设计规范、共享 Token 源文件、组件清单或样板、任务跟踪与项目状态入口，以及已从 `package.json` 或项目脚本核实的开发、测试、预览命令。命令按需注明工作目录与脚本来源；未运行的命令不声称通过。仅有未来计划但尚不存在的文件不列入索引，未查到的命令不凭默认经验补齐。

索引每行只放位置或命令与一句用途，不复制设计正文、领域定义、Token 数值、动态进度或流程，建议整个段落不超过 40 行。表旁约定：涉及这些内容时先读对应文件或入口再动手，不凭记忆或默认假设；位置或命令变化时同步更新索引。详细项目规则仍放在原有约定文档，索引引用其位置。

项目状态沿用已有明确入口；没有约定时默认使用一个固定的 GitHub“项目当前状态”Issue，没有 GitHub 才使用根目录 `STATUS.md`。README 和项目索引指向同一入口，不另外维护两份进度。建立远端入口遵守本次授权；远端不可用或未获授权时如实标明待建立，不编造链接或自动换成另一份状态来源。

状态页保持最近核对时间、阶段与范围，以及四项短摘要：**当前目标、已完成与目前可用、下一步及阻碍、需要用户决定的事项**。详细依据链接到原有文档、Issue、分支或 PR。项目约定保留先完成本次整体设计、再进入开发的顺序；设计阶段可以明确记录尚未开始开发，样板不等于业务功能已可用。

当前主 Agent 负责汇总，子 Agent 提供各自任务事实；开始或接手工作时先核对状态，在关键设计结论、阶段、阻碍、交付变化及暂停或结束本轮前更新。更新前读取最新内容，保留其他正文，区分分支结果、主线可用与用户验收。状态维护依赖工作中的 Agent，不是后台实时监控；未核实、未成功写入或中断后的旧状态都应明确说明，下次接手再核对。上述职责写入目标项目约定，不增加新的 Skill。

## 工作完成后的讲解

需要理解刚才的工作时使用 [`explain-work`](skills/explain-work/SKILL.md)。它可以接在开发、设计、配置、部署、文档或研究工作后，也可以在你追问时单独使用。讲解从结果与用途开始，再按需要说明主要变化及原因、关键运作流程、实际验证与限制。

例如：“把这个问题修好，做完后解释一下。”先按 `implement` 完成任务，再按 `explain-work` 解释结果；“按方案把整套功能做完，最后讲清楚。”则先按 `implement-spec` 完成整体交付，再解释整体结果。

只问“刚才改了什么”或“为什么这么改”时，依据已有改动和执行证据讲解，必要时补充只读检查。解释请求本身不授权新的修改或发布。“解释一下”只有明确指向刚才的工作时才使用这个技能；普通知识问答、翻译和尚未执行的新方案不属于它的范围。

本技能借鉴 [Google 开发者文档写作指南](https://developers.google.com/style) 的表达原则，并加入工作完成状态与验证证据的要求；日常使用不需要重复检索指南。

## Issue、开发与交付

Issue 写到未读过聊天的执行者能接手即可，写清目标、范围、必要局部设计、验收和关联，不预先规定所有代码写法。父子关系表示所属目标，阻塞关系表示必须等待的任务；正文保持当前要求，评论记录关键变化，完成实施后回链 PR 和实际验收证据。

验收使用具体输入、操作和可观察结果，例如“重启后仍能读到保存记录”，而非“完成历史模块”。按实际风险选择必要检查，检查通过后只在新变化或未解决问题需要时扩大验证，不为流程重复测试或生成构建产物。

UI 实施复用设计依据、共享 Token、组件清单和样板代码，通过项目实际浏览器或桌面入口核对关键流程与交互；有视觉参考时也核对布局几何。设计变化同步规范、对应源码及受影响任务，样板完成和构建通过都不代替业务功能验收。

`implement` 负责一项任务：读取 Issue → 实施 → 按项目设置验证 → 提交推送 → 创建或更新 PR → 保存交付结果 → 清理。

`implement-spec` 负责多个任务：整理依赖 → 持续推进可执行任务 → 核对和整合 → 更新整体 PR → 保存试用结果 → 清理本次临时工作树与产物。

用户要求“做完后解释”时，在完成上述实际工作后按需衔接 `explain-work`；只要求解释已有工作时直接讲解。讲解依据实际结果，不代替实施、验收或用户确认。

清理以改动已推送且被实际 PR 覆盖、所需交付物已保存为前提。保留主工作区、未交付修改和 PR 远端分支，并报告真实残留。测试和审查分别按项目设置；技能不额外引入运行框架或后台轮询服务。

## 维护

在 `skills/<技能名>/SKILL.md` 修改行为，在对应的 `agents/openai.yaml` 修改中文显示信息。各技能无需共享规则文件即可使用。

本仓库的 `AGENTS.md` 约束技能源文件的维护；使用者项目的规则应写入该项目的 Agent 入口或其引用文档。个人全局偏好由使用者在自己的 Agent 配置中维护，安装本仓库不会复制维护者的个人全局配置。

发布内容包括 `skills/` 下的 `SKILL.md`、显示信息和被引用的参考文件。发布前核对引用可读取、安装器能发现全部技能；本地备份、缓存和目录链接不随源码提交。维护者可以让多个 Agent 的技能入口链接到同一份源文件，新增或迁移时核对链接并保留其他技能。已打开的会话可能仍持有旧上下文，实际触发效果需在新会话中确认。
