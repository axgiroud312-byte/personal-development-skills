# 中文开发技能

用中文说明要做什么，Agent 根据任务选择技能。共九个技能：六个开发技能、一个界面设计技能 `design-ui`、一个工作讲解技能 `explain-work` 和一个项目配置技能 `setup-project-skills`，可以分别使用、按需要组合。

设计参考 [Matt Pocock 的 Skills](https://github.com/mattpocock/skills)，内容由用户独立维护。

## 安装

需要 Node.js 22.20 或更新的受支持版本（包含 npm / npx）和 Git，并能访问 npm 与 GitHub。

使用 [Skills CLI](https://github.com/vercel-labs/skills) 从本仓库默认分支安装，无需单独发布 npm 包。安装的是 Agent 的工作方法；React、shadcn 等项目依赖在实际开发时按需安装。

### 给 Codex 安装整套技能

希望各个项目都能使用时，在终端运行：

```sh
npx skills@latest add axgiroud312-byte/personal-development-skills --skill '*' --agent codex -g
```

`--skill '*'` 选择仓库内全部 9 个技能，`--agent codex` 指定 Codex，`-g` 表示安装到用户级技能目录，供多个项目使用。按安装器提示完成安装；安装后在目标项目中开启新会话。

需要建立项目约定时，可以说：“使用 setup-project-skills，为这个项目配置开发约定。”它核实文档、任务和运行入口，在项目的 Agent 入口文件中写入简短项目索引，并配置固定状态入口与维护约定；技能安装由上面的 CLI 完成。已有项目约定足够时，直接提出开发需求。

### 选择项目范围、部分技能或其他 Agent

仅在一个项目使用时，先进入该项目目录，再运行同一命令并去掉 `-g`。希望交互选择技能与 Agent 时运行：

```sh
npx skills@latest add axgiroud312-byte/personal-development-skills
```

交互安装默认针对当前项目；需要全局安装时追加 `-g`。其他 Agent 的标识见 [安装器支持列表](https://github.com/vercel-labs/skills/blob/main/docs/agents.md)。

先查看可安装的技能，不执行安装：

```sh
npx skills@latest add axgiroud312-byte/personal-development-skills --list
```

也可以明确指定技能和目标 Agent。例如，将 Issue、单项开发和整套开发三个技能安装到当前项目，供 Codex 使用：

```sh
npx skills@latest add axgiroud312-byte/personal-development-skills --skill to-tickets implement implement-spec --agent codex
```

### 更新已有安装

从旧版升级到整套新版时，在原来的安装范围重新运行全部技能安装命令。下面以 Codex 全局安装为例，它会取得当前仓库内容，并包含新增的 `design-ui`；已有同名技能会被更新，自己改过安装副本的内容应先保存：

```sh
npx skills@latest add axgiroud312-byte/personal-development-skills --skill '*' --agent codex -g
```

新版已将 `grill-with-docs` 的讨论与记录能力合并到 `grilling`。重新安装不会自动移除已退役的旧技能；曾安装过旧版时，再移除旧入口：

```sh
npx skills@latest remove grill-with-docs --agent codex -g
```

如果旧版安装在项目中，在那个项目目录执行上述两条命令并去掉 `-g`；如果安装给其他 Agent，替换 `--agent` 的值。如果多个 Agent 共用旧技能，还需检查其他安装，安装器可能保留仍被使用的共享副本。移除前核对安装器列出的目标，完成后开启新会话。新安装无需执行移除命令。

## 技能一览

| 你可以这样说 | 对应技能 |
| --- | --- |
| 帮我把这个想法问清楚／边聊边记录 | `grilling`：澄清关键决策，按需记录结论 |
| 统一一下业务术语和关系 | `domain-modeling`：检查并补齐业务定义、关系和规则 |
| 设计一下界面／制作设计板 | `design-ui`：从需求和参考确定设计方向，在 `docs/design/` 交付 Token 说明与设计板，展示页面效果和必要交互 |
| 把需求写成 Spec | `to-spec`：复用已定需求、补齐关键缺口，形成整体方案 |
| 根据这段计划直接拆任务 | `to-tickets`：拆分设计、准备与实施任务，细化交付、依赖和验收 |
| 把这个问题修好／完成这项任务 | `implement`：完成单项实施与验证，按授权或主 Agent 分工交付 |
| 按方案把整套功能连续做完 | `implement-spec`：连续推进多个任务，统一依赖、整合和整体交付 |
| 讲讲刚才做了什么／做完后解释一下 | `explain-work`：解释工作结果、原理与验证范围 |
| 为这个项目配置开发约定／更新项目索引 | `setup-project-skills`：维护 Agent 入口文件里的项目索引，配置固定状态入口与开发约定 |

## 按需要组合

主要衔接是：**需求讨论 → 业务定义检查 → 整体方案与界面设计 → 任务拆分 → 实施与验收**。各技能根据已有材料按需组合；明确的小修直接实施，不要求完整运行一遍。

`grilling` 负责开放讨论与关键选择；`to-spec` 直接复用已定需求，只补阻止整体方案定稿的缺口。技术模块设计前核对业务定义，已有领域模型足够时直接引用，不足时按需使用 `domain-modeling` 或等价梳理。事实由 Agent 调查，可逆细节自行判断，只有无法调查解决且影响目标或整体方案的用户选择才提问。

涉及 UI 时，`design-ui` 与 Spec 往返配合。主要交付 **`docs/design/design-token.md` 和 `docs/design/design-board.html`**：前者写清颜色、字体、尺寸等设计规则，后者展示配色、排版、组件、完整页面和必要交互。已有设计与项目定制优先沿用，后续开发复用实际样式和组件。具体要求见 [design-ui 主文件](skills/design-ui/SKILL.md)。个人的技术栈、组件与视觉偏好统一维护在全局 `AGENTS.md`，当前任务的明确要求优先。

设计判断见主文件的[怎样判断设计好不好](skills/design-ui/SKILL.md#怎样判断设计好不好)：让设计符合项目特点，让重点先被看到，用真实内容和一致的外观把页面做好。[哪些是不好的设计](skills/design-ui/SKILL.md#哪些是不好的设计)列出具体反例，并说明哪些必要信息应当保留。制作时先写 Token 说明，再做设计板；shadcn 的初始化、搜索、配置和安装等具体操作交给它自己的 Skill。

**设计任务可以在成果产生前拆分。** `to-tickets` 可先建立设计、调查和环境准备任务，再为依赖它们的页面开发标明阻塞条件。拆页面开发任务时需要足够的设计依据；只要求写 Spec 或拆任务，不自动扩大成整套设计或业务开发。

## 决定放在哪里

| 记录 | 负责的决定 |
| --- | --- |
| 领域记录 | 业务对象、关系、归属、生命周期与规则 |
| Spec | 整体技术方案、模块协作、共同接口与整体完成标准 |
| 设计说明与设计板 | 设计方向、Token 约定、页面与交互效果、组件复用和查看方法 |
| 共享源码 | 实际 Token 值和共用组件实现；已有源沿用，新设计项目按需建立 |
| Issue | 单项交付、局部接口与状态、依赖、具体验收及任务进展 |

每项决定只维护一份有效正文，其他位置引用。发生变化时更新对应来源与受影响任务；业务对象与技术模块不要求一一对应。已有材料够用时不补建重复文档。

## 项目入口与状态

`setup-project-skills` 核实当前项目的文件、命令与必要约定，在 `AGENTS.md` 或 `CLAUDE.md` 中维护一份简短的 `## 项目索引`，只列实际存在的入口和查到的命令。索引指向领域、Spec、设计、Token、组件、任务与状态，不复制正文或进度；路径或命令变化时更新。

项目状态沿用已有入口；没有约定时，有 GitHub 默认使用固定“项目当前状态”Issue，没有 GitHub 用根目录 `STATUS.md`，二者只选一个。README 与项目索引指向同一入口；建立远端入口遵守当前授权，不可用时如实标明待建立。

状态保存核对时间、阶段与范围，以及当前目标、已完成与目前可用、下一步及阻碍、需用户决定的事项。当前主 Agent 汇总，执行者提供任务事实；接手时核对，在关键变化及暂停或结束本轮前更新。区分设计完成、分支可用、主线可用与用户验收；状态依赖正在工作的 Agent，不承诺后台实时刷新。维护约定写入目标项目，配置技能本身不反复承担日常更新。

## 实施与交付

`implement` 负责单项实施与必要验证；独立使用时按当前请求和项目约定选择本地修改、提交推送或 PR 交付。作为整体开发的子任务时，按主 Agent 约定交回代码、提交与验证结果，不自行承担整体 PR 或清理。

`implement-spec` 负责多个任务的依赖、分工和整合，持续推进已可执行任务，不逐项询问是否继续。主 Agent 统一安排 PR、整体状态及临时工作树清理；PR 交付通常维护一个整体 PR，项目另有逐项 PR 约定时沿用。只要求推送时不追加 PR，只要求 PR 时不自动合并或关闭目标。

验收关注具体操作与可观察结果，UI 使用真实浏览器或目标桌面入口，测试与审查按项目设置及风险选择。构建通过、模拟检查、分支试用和用户验收分别说明，不为流程重复测试或生成产物。

清理前保存必要成果与恢复材料；移除临时工作树须确认需保留改动已整合并推送，PR 交付还须核对实际 PR 覆盖。只在本地交付或仍有未推送代码时保留承载代码的工作树，保留主工作区、他人修改和 PR 远端分支，并报告实际残留。

## 工作完成后的讲解

用户要求“做完后解释”或追问刚才的结果时，使用 [explain-work](skills/explain-work/SKILL.md) 说明结果、变化原因、关键运作流程和实际验证范围。讲解可用于开发、设计、配置、文档和研究等工作；只要求解释时依据已有证据说明，必要时补只读检查，不启动新的修改或发布。

## 维护

九个技能的行为规则分别放在 `skills/<技能名>/SKILL.md`，`agents/openai.yaml` 只保存显示信息与调用策略；不拆参考文档，也不增加共享规则文件。README 介绍用途与衔接，完整方法以各自主文件为准。

本仓库 `AGENTS.md` 约束技能源文件维护；使用者项目的事实与约定写入对应项目入口。发布主文件与显示信息，不上传备份、缓存或目录链接；安装入口可链接到同一份源码，迁移时核对链接。已打开的会话可能仍持有旧上下文，实际行为需在新会话与真实任务中确认。
