# 设计界面与交互

先想清楚设计，再把规则和效果做出来。用通俗中文说明，所有工作方法都放在本文件中。

主要交付放在项目的 `docs/design/` 下：

| 文件 | 用途 |
| --- | --- |
| `design-token.md` | 记录颜色、字体、尺寸等设计规则，包括具体值和用途。 |
| `design-board.html` | 展示配色、排版、组件、完整页面和必要交互。 |

页面效果和必要交互都在设计板里展示，不单独做原型。其他素材或源码确实需要时再添加，不规定额外的文件排列和目录结构。

## 设计哲学

以代码实际为主：遇到文档与代码不一致时，沿用现有实现的惯例，并在完成后列出发现的差异（文档描述、代码实际及本次处理）。区分现有行为与本次变更目标；用户明确要求的新行为和修复仍按当前任务处理。

## 先确认这次要做什么

先看实际项目、需求、已有界面和业务说明。明确产品要满足什么需求、谁在用、主要做什么、有哪些真实内容，以及使用的设备和操作方式。

功能或数据的含义不清时，按需使用 `domain-modeling` 或做同等梳理。只追问无法查清、又会影响设计的关键问题，不自行更改业务规则。

已有设计、技术栈、组件和规范优先沿用，再根据当前任务调整。只要求讨论、评审、写说明、拆任务或局部修改时，就完成这部分。已授权完整设计或开发时，连续推进，不为每个阶段再加一次确认。

## 看参考，确定设计方向

有参考时先打开原图、页面或文件。看它要表达什么、哪里最吸引人、为什么这样安排，以及需要什么内容和素材才能成立。选择与当前任务相近，或适合现有内容和素材的参考，借用适合本项目的做法。

只换成相同的配色、字体和装饰，容易做出相似的模板。参考中的小字、难找的导航或妨碍操作的效果，也不能一起照搬。

把借鉴点说具体：各部分占多大、如何对齐、间距多少、字有多大多粗、颜色分别用在哪里、哪些区域靠背景或边框区分。有明确尺寸要求时，按这些尺寸制作。参考打不开时说明缺少什么。

没有参考时，结合当前任务和已确认的偏好推荐一个方向。方向不清楚或用户不满意时，可以用相同内容做两个差异明显的小样，说明推荐理由；推荐不等于用户已经选定。

## 怎样判断设计好不好

### 设计要符合这个项目

从产品功能、名字、场所、材料、独特限制或用户的工作方式中寻找设计依据。明确用户需要理解、相信或完成什么，再安排内容，避免每个项目都套“大标题、三张功能卡、评价、价格表”。

内容有主次、因果或先后顺序时，布局要表现这些关系，不能为了套组件，把它们都塞进同样重要的方框。

确定这次主要靠什么吸引人：真实图片、大字与小字的对比、有序排列的作品、熟悉物件的样子，或可信的产品演示。用一句话说清项目特点怎样影响布局或操作。如果换个名字就能原样给竞争者使用，继续寻找更具体的依据。后台或工具界面可以通过真实任务、数据和操作体现特点，不必强加艺术表达。

### 重要内容要先被看到

用大小、位置、疏密和明暗安排阅读顺序，让主任务或主要内容先被看到。辅助信息也要清楚可读。避免所有元素一样抢眼、字号都很接近，或每块内容都争着当主角。

留白应帮助分组、突出重点或调整阅读节奏。删掉装饰后留下的洞、过大的段落间隔、窄小文字旁无作用的空地，不能只用“极简”解释。根据内容补充信息、放大重点或收紧布局。紧凑时要分得清，宽松时也要有完整内容。

### 整个界面要像同一套设计

字体、颜色、间距、对齐、图片处理和组件外观应相互配合。设计特点要延续到正文、业务区域和结尾，避免只有首屏有特色，后面又退回通用模板。

布局可以随内容变化，但表格、列表和同类操作中方便比较、容易学会的重复要保留，不为求新而破坏一致性。

颜色要有明确用途，例如区分背景、突出操作或表达状态。字体既要适合内容，也要读得清楚。渐变、阴影、细线、等宽字、圆角和某种颜色是否合适，要看内容、品牌和用途；无理由地反复堆叠才容易产生套路感。已确认的个人偏好仍是默认方向。

### 页面要有值得看的真实内容

图片应展示对象、说明环境或帮助说明产品特点，值得呈现的细节可以放大。展示产品时，界面要看得清，内容要具体。避免无关图库、过小的截图、灰条拼成的假仪表盘或泛泛的图标代替核心信息；图库图片也不能冒充客户的产品、人员或场所。

页面的丰富感可以来自充分的内容、明显的大小对比、有表现力的图片、大面积色彩、讲究的排版，或大量内容被清楚地组织起来。简洁需要内容和细节，复杂需要秩序；去掉装饰后，页面仍应充实，不能像没做完的空架子。

### 视觉效果要帮助理解和操作

介绍产品或作品时，要让人记住特点，并用图片、事实或演示说明价值；后台或工具界面优先帮助用户看懂数据、比较信息和完成操作。视觉效果不能让人看不清主体、找不到信息或难以操作。

手机上要重新安排内容顺序、图片裁切、布局和操作空间，避免只把桌面缩小。交互和动效用于说明变化、表达位置关系和反馈操作，不能遮住或拖延主要内容。

理念参考：[Taste Skill 的设计方向库](https://github.com/Leonxlnx/taste-skill/blob/6010f91a9935f1c167dfc500fb1a475681892e6b/skills/taste-skill/library/directions.json)与[优秀及薄弱设计分析](https://github.com/Leonxlnx/taste-skill/blob/6010f91a9935f1c167dfc500fb1a475681892e6b/skills/taste-skill/references/research.md)。

## 哪些是不好的设计

不要为了填满空间、显得精致或营造科技感，自行添加没有作用的内容和效果。不能只用“高级感”“科技感”解释为什么需要它。下面这些做法应当避免：

| 问题 | 具体表现 |
| --- | --- |
| 无意义的渐变 | 背景、标题、按钮到处加渐变、发光或彩色光斑，与品牌、内容和阅读顺序没有关系，只是在制造效果。 |
| 多余的小标签 | 标题上方反复加英文小标题、胶囊徽章、“NEW”“PREMIUM”等，既不帮助分类、导航或理解，也不说明真实差异。 |
| 多余的介绍和小字 | 给每个页面、卡片、控件都补介绍、副标题、口号或说明，再靠缩小字号、变灰或拉大字距塞进去，删掉也不影响使用。 |
| 随意的小装饰 | 到处放圆点、星形、十字线、角标、漂浮图形和无关图标，没有帮助表达项目特点或理解内容，反而分散注意力。 |
| 装饰性或编造的数字 | 给没有先后顺序的内容加“01、02、03”，或用无关版本号、坐标、百分比填位置；为了显得专业而编造人数、销量、评分等数据。 |
| 没有依据的状态表达 | 没有对应功能或真实状态来源，却加上“系统正常”“实时同步”“AI 在线”等文字、绿色圆点或呼吸动画，让人误以为系统正在执行某项工作。 |

前文提到的机械套模板、所有元素同样抢眼、只做好首屏、留下没有作用的空地、用假界面或无关图片代替内容，以及视觉效果妨碍阅读和操作，也是不好的设计。

界面文字用于识别内容、完成操作和理解状态。删掉后不影响这些目的的文字，默认删去。例如标题已有“项目”，通常不必再写“在这里查看和管理你的所有项目”。不要用小字或低对比度掩盖多余文字。

有实际作用的信息要保留，包括字段标签、输入要求、真实分类、操作步骤、实际金额与进度、重要状态、错误原因、恢复方法和影响决定的操作后果。它们要写清楚、读得清楚。设计板中的样例数据和模拟状态应明确标注，不能冒充真实业务结果。

设计理由和给开发者看的说明放在设计文档或设计板的说明区域，不混进产品页面本身。设计板中的 Token 名称、数值和组件来源可以保留。

## 先写 design-token.md

在 `docs/design/design-token.md` 中写清本次采用的设计变量。Design Tokens，简称 Token，就是统一使用的颜色、字体、尺寸等约定。

按实际需要记录名称、具体值和用途，主要包括：

- **颜色：** 背景、文字、按钮、状态、焦点等分别用什么颜色。
- **文字：** 字体与备用字体、字号、字重、行高和字间距。
- **尺寸与效果：** 间距、控件高度、圆角、边框、阴影，以及必要的动效约定。

已有项目的主题和样式变量优先沿用，并写清对应名称和源码位置。文档与现有样式不一致时，以实际源码为依据对齐说明和设计板；本次明确要求调整的设计，再同步相关说明、设计板和实际样式。

与这些选择有关的设计理由、组件来源和待定事项，可以在文档中简短说明。已有合适的说明就直接引用，不另写一套相同内容。

## 再做 design-board.html

在 `docs/design/design-board.html` 中展示实际效果。按本次设计需要安排内容，分区和顺序由页面决定：

| 内容 | 展示什么 |
| --- | --- |
| 设计方向 | 参考好在哪里、采用了什么，以及本项目的内容小样；分清当前方案和候选方案。 |
| 配色 | 真实色块、数值与用途，以及文字、背景、按钮和状态提示的搭配。 |
| 字体与排版 | 中文、英文、数字、长短文本，以及实际字号、粗细、行高、分栏和间距。 |
| 组件与状态 | 本次采用的控件、不同样式及必要状态，说明来源和做过的定制。 |
| 页面效果 | 组件放在一起后的完整页面，以及本次需要的窄屏布局。 |

使用真实内容，或明确标注的代表性样例。先打磨能代表主任务的一屏，再补其他需要展示的页面。文字规范、库名清单或截图不能代替实际页面和组件。

确认字体和字重确实加载，用中文、英文和数字看实际效果。候选字体、配色和方向不要混进已经采用的方案。

### 必要交互也放在设计板里

需要查看效果的下拉框、弹窗、切换、筛选等，直接在设计板里操作。按需要展示选中、加载、空数据、输入错误等状态，让人看懂发生了什么、下一步能做什么，不要求把所有状态都做一遍。

操作应及时反馈，弹窗和菜单能关闭、能用键盘操作，关闭后焦点回到合适位置。动效支持“减少动态效果”设置。

可以使用明确标注的模拟数据和响应，不要求连接完整业务后端；不能把展示中的模拟保存说成真实业务已经完成。

## 组件操作交给对应 Skill

组件先复用项目已有的，再从约定来源选择。确实缺少时才补充或自己实现，并说明原因。设计板与后续产品尽量共用实际样式和组件源码，保留已有定制；分清“已使用”和“只是候选”。

需要使用 shadcn 组件时，读取并使用 `shadcn` Skill。初始化、搜索、组件来源配置、安装和更新由它指导，沿用已有项目配置，只处理本次设计需要的组件。该 Skill 不可用时再查[官方文档](https://ui.shadcn.com/docs)。

## 方便查看和继续开发

设计板应能实际打开，优先沿用项目已有的服务和预览方式。需要启动时，说明准确的命令和访问地址。素材、样式或少量源码按实际需要添加，复用项目资源，不另建固定的一套目录。

交付时给出两份主要文件的位置、查看方法、已采用的组件和定制，以及模拟内容或仍待确定的部分。必要的开发说明可放在 `design-token.md` 末尾。

后续开发以 Token 说明和设计板中的实际页面、交互为依据，复用已有组件和样式，不从截图重新猜数值。设计变化时，同步这两份文件、实际样式和受到影响的方案或任务。
