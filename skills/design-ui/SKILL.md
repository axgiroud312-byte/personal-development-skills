# 设计界面与交互

统一负责设计方向、页面交互和 Token 整理。先把实际效果做出来，再提取采用的规则；用通俗中文说明，沿用项目已有设计、技术栈、组件和定制。

**以代码实际为主。** 核实现状时以代码和实际行为为依据；文档不一致就沿用现有实现的惯例，完成后列出发现的差异与处理。用户明确提出或已确认的新需求决定本次目标，不能因为尚未实现而忽略。

## 先确认这次要做什么

先看实际项目、需求、已有界面和业务说明。明确产品解决什么问题、谁在用、主要操作、真实内容、设备和使用方式。

功能或数据含义不清时，按需使用 `domain-modeling` 或做同等梳理。只追问无法查清又影响设计的关键选择，不自行更改业务规则。

只要求讨论、评审、写说明、拆任务或局部修改时完成该范围。完整设计按当前授权连续推进；分阶段开发先做好当前交付需要的设计，远期页面不阻塞，不逐阶段增加确认。

## 看参考，确定设计方向

有参考时先打开原图、页面或文件，理解它要表达什么、哪里吸引人、内容与操作如何安排，需要什么素材才能成立。选择适合当前任务与内容的参考；打不开时如实说明。

把借鉴点说具体：比例、对齐、间距、字号与字重、颜色用途、背景和边框分区、图片裁切。有明确尺寸要求时按要求制作。

避免只换成相同的配色、字体和装饰来套模板。参考中的小字、难找的导航或妨碍操作的效果，也不能一起照搬。

没有参考时，结合任务和已确认偏好形成方向。方向不清或用户不满意时，可用相同内容做少量差异明显的小样，区分候选与当前采用方案，不把推荐当成用户已选择。

## 设计判断

开始设计或评审时读取 [设计质量参考](references/design-quality.md)，其中集中说明好设计、坏设计与实际检查方法。将标准用于当前产品和内容，交付前据此复核，不把固定风格当成答案。设计板的借用、归还、审批等动作应与已确认规则和真实接口状态一致；未决定的权限或政策不得靠模拟按钮暗中定案。

## 先做 design-board.html

在 `docs/design/design-board.html` 制作可查看的效果，已有合适位置则沿用。先打磨代表主任务的一屏，再按本次范围补齐页面与状态；使用真实内容或标明的样例。现有主题变量和组件可直接用于设计，不要求先写一份 Token 文档。

| 内容 | 展示什么 |
| --- | --- |
| 设计方向 | 参考的借鉴点、本项目的内容小样，区分候选与采用方案。 |
| 配色与排版 | 实际颜色、文字和背景搭配，中文、英文、数字及长短内容，字号、字重、行高与间距。 |
| 组件与状态 | 采用的控件、来源和定制，以及本次必要的选中、加载、空数据和错误等状态。 |
| 页面与交互 | 组合后的完整页面、所需窄屏布局，以及可操作的菜单、弹窗、切换和筛选等。 |

确认字体和字重确实加载；文字规范、库名清单或截图不能代替实际页面。交互及时反馈，菜单和弹窗可关闭、支持必要键盘操作与焦点返回，动效支持“减少动态效果”。

设计板中展示页面与必要交互，不另做一份重复原型，也不要求穷尽所有状态或接入完整后端；模拟数据与保存结果如实说明。

## 再从采用的设计提取 Token

设计板的页面和交互已可查看、完成必要检查后，再输出 `docs/design/design-token.md`。直接读取采用的样式与组件源码，不从截图猜值，不把候选方案写成已定规范；已有合适文档原位更新。

- **颜色：** 背景、文字、操作、状态与焦点等的名称、实际值和用途。
- **文字：** 字体与备用字体、字号、字重、行高和字间距。
- **尺寸与效果：** 间距、控件高度、圆角、边框、阴影及必要动效。

沿用已有变量名称和唯一源码，标明源码位置；保留必要的设计理由、组件来源与待定项。复用已有说明，不建立第二套值。提取或统一 Token 改变效果时，回到设计板核对；两份成果与实际样式保持一致。

## 组件复用、查看与交接

先用项目已有组件，再从约定来源补缺口；确需自建时说明原因，保留定制并区分已使用与候选。设计板与产品尽量共用实际样式和组件源码，后续开发直接复用。

使用 shadcn 时读取其 Skill，按它完成必要的初始化、搜索、来源配置、安装与更新；不可用时查[官方文档](https://ui.shadcn.com/docs)。沿用已有配置，只处理本次需要的组件。

沿用已有服务和预览方式，实际打开设计板检查主要页面、窄屏效果与交互，按本次范围验证。确需素材、样式或少量源码时再添加，不为目录完整补文件。

交付设计板、Token 说明的位置与准确查看命令或地址、采用的组件和定制，以及模拟、未验证或待定内容。设计变化同步两份成果、实际样式及受影响的 Spec 和任务，不另加阶段批准。
