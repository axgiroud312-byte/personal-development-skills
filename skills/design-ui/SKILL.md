# 让需求变成看得见、能操作的设计

对用户想完成的事情和期待的体验负责。结合用户表达、上下文和实际材料主动理解设计意图，让调查和设计相互推进。重要假设建立在需求上，影响体验的取舍带着具体效果与用户讨论，已有明确结论直接沿用。

## 用合适的设计表达帮助判断

根据当前最需要弄清的问题，决定展示哪些页面、布局、内容、交互和状态，以及需要细化到什么程度。需要交互原型时，默认制作可独立打开的 HTML，让用户通过实际操作理解设计；已有成果从当前进度继续。

设计工作可以独立开展，也可以作为已授权 Spec 等任务中的一部分。原型、Design Token 和其他设计表达按需求选择，组织形式与产出顺序由模型判断。

让布局、分组、对齐和视觉层级传达内容关系与操作方式，把文字留给必要的信息和提示：

Avoid unnecessary secondary labels and descriptions. Let the layout do the explaining.

结合 [design-quality](../design-quality/SKILL.md) 判断整体效果。使用接近真实长度的内容表现关键流程；设计依据、组件来源、联网依赖和模拟范围等说明放在容易查阅且不干扰产品界面的地方。HTML 原型中的组件与样式说明可以收在折叠区域。

## 随反馈完善并交接

根据实际显示、必要操作和用户反馈调整设计。每次交付前做与当前成果相称的轻量检查，说明打开方式、能体验的内容和仍待确定的部分。用户说停时保留当前可用成果和进度，后续从这里继续。

需要 Token 时，按当前设计与项目用途定义或提取，表达方式由模型决定，并说明它与实际样式或原型的对应关系。设计变化时同步相关产物，如实区分设计提案与用户已确认的选择。

沿用已有文件位置；新建 HTML 原型和 Token 文档时，默认可用 `docs/design/design-board.html` 与 `docs/design/design-token.md`。正式开发据此完成真实业务。
