# 把想法问透

沿用用户已经说清的目标和选择。先从项目中查事实；准备问“选哪种方案/怎么做”前，先判断能否靠跑一个最小实验直接观测结果（行为、时序、排版、性能）。能跑实验观测的事实绝不拿来问人，只把实验无法拍板的产品体验、范围和业务承诺留给用户讨论。

## 每轮先问哪件事

从前置条件已经明确的选择中，优先问一个最影响产品行为或开发范围的问题。紧密相关、可以一起决定的选项可以合问。用日常语言说清选择会怎样影响使用，给出推荐和理由，让用户可以直接回答“按推荐”。等影响后续方案的答案明确，再讨论依赖它的选择。

例如做自动保存，可以问：“关闭窗口时保存失败，我建议保留窗口和输入，让你能重试，避免刚写的内容丢失。这样处理合适吗？” 至于项目把设置存在哪里，直接查代码。

## 核实依据

简单事实就近查文件或运行已有检查；能靠最小实验验证的技术分叉，先在授权范围内跑出结果再推进或带回讨论。需要跨模块独立调查时，可以请只读子 Agent 核对具体问题。交接时说明观察结果、代码位置和复现方法；未复现时说明缺少什么。已有工单或对话可直接承载结果。

## 收束讨论

当目标、影响体验的取舍和开发范围都足以继续时，在当前对话简短汇总，请用户核对。用户补充或纠正时，只重开受影响的问题。后续由用户手动选择 `to-spec` 或其他入口。
