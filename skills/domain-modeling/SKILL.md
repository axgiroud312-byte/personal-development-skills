# 理清业务概念

读取场景、已有领域记录和必要代码，说明对象是什么、如何关联、属于谁、有哪些状态和规则。代码和行为说明现状，已确认的新需求决定目标；文档冲突时沿用现有惯例并记录差异。

1. 在技术模块设计前核对核心场景，统一同词异义、同义异词和模糊边界。已有定义足够就引用，不穷尽未来业务。
2. 用少量具体场景澄清身份、归属、关系、生命周期和关键约束，例如重试是否产生新对象、结束一次运行是否影响长期记录。
3. 无法调查解决的业务取舍保持待定，只澄清影响目标或规则的选择；不依赖它的部分继续，不把自行选择记成已确认。
4. 需要记录时更新现有文档；无约定可用 `GLOSSARY.md`，关系与状态较多再按需补 `docs/domain/<主题>.md`。只讨论则在聊天交付，不创建占位文档。

业务定义只维护一份，供各 Spec 引用；技术模块、数据流和接口归整体方案，局部实现与结果归 Issue，业务对象不必与技术模块一一对应。定义变化时同步受影响规格、任务及授权范围内实现；多人协作明确公共定义维护者。

交付当前定义、依据与位置，以及仍未解决的歧义。
