# 理清业务概念

读取当前对话、已有术语、相关代码，以及实际存在的 Spec 或任务。没有正式规格也能开展；只要求讨论或解释时在对话中交付，已要求记录时再写入领域文档。

主要位置在初步需求清楚之后、Spec 设计模块之前。检查本次主要场景涉及的对象、关系、归属、生命周期和业务规则是否清楚一致；已有定义足够时直接复用，只补新增或变化的部分，不要求重做模型或新建文档。

Spec、Issue 或实施过程中发现业务概念缺口时主动补齐。事实先调查；无法调查解决且会改变业务含义的用户选择，说明推荐和影响后澄清，不把假设写成已定规则。只需让当前核心场景讲得通、足以支持设计，不要求一次建模所有未来情况。

1. 从真实场景明确对象是什么、负责什么、属于谁，以及对象之间的关系、身份和生命周期。
2. 发现同词异义、同义异词或模糊边界时，提出统一定义。区分代码的现状和用户希望的行为。
3. 用少量具体场景检查关键规则，例如失败重试是否创建新对象、关闭一次运行是否影响长期保存的对象。
4. 需要记录时写入项目已有领域文档。无约定时，术语使用 `GLOSSARY.md`；关系和状态较多时补 `docs/domain/<主题>.md`，只在有确定内容时创建。
5. 术语或领域记录保存业务定义、关系与规则；Spec 引用它们并设计技术模块及共同技术约束，Issue 细化局部实现和验收。业务对象与技术模块不要求一一对应。每个定义只维护一份有效正文，其他位置引用；重要取舍沿用项目的决策记录方式。

定义变化时先更新领域记录，再核对受影响的 Spec、Issue 设计与验收条件；当前任务已包含代码修改时同步实现。保留不受影响的已有定义，避免只改代码或在各任务中形成不同解释。改变用户目标或范围的取舍按当前授权处理。多人或多 Agent 并行时明确公共模型的维护者。交付可复用的当前定义、依据、实际记录位置和仍未解决的歧义。
