# 理清业务概念

负责说明业务对象是什么、如何关联、属于谁以及遵守哪些规则。读取当前对话、已有领域记录和必要代码，区分现状与期望；没有正式 Spec 也能开展。

**以代码实际为主。** 核实现状时以代码和实际行为为依据；文档不一致就沿用现有实现的惯例，完成后列出发现的差异与处理。用户明确提出或已确认的新需求决定本次目标，不能因为尚未实现而忽略。

初步需求清楚后，在技术模块设计前检查核心场景；Spec、Issue 或实施中发现业务歧义时也可补齐。已有定义足够就引用，不重做模型或穷尽未来业务。无法调查解决的业务取舍保持待定并按需澄清，不把自行选择的规则写成已确认要求；不依赖该选择的部分继续推进。

1. 从真实场景明确对象的身份、职责、归属、关系、生命周期和关键规则，统一同词异义、同义异词及模糊边界。
2. 用少量具体场景核对规则，例如失败重试是否产生新对象、结束一次运行是否影响长期记录。
3. 需要记录时更新项目已有领域文档；无约定时术语用 `GLOSSARY.md`，关系与状态较多时按需补 `docs/domain/<主题>.md`。只讨论时在对话中交付，不创建占位文档。
4. 领域记录保存业务定义与规则，供相关 Spec 共用；技术模块、数据流和共同接口由对应 Spec 或已有整体方案承接，局部实现与验收按需写入 Issue。业务对象与技术模块不要求一一对应，每项定义只维护一份有效正文。

定义变化时先更新领域依据，再核对受影响的 Spec、任务、验收及授权范围内的实现。多人或多 Agent 协作时明确公共模型维护者。交付当前定义、依据与记录位置，以及仍未解决的歧义；改变目标或范围的取舍沿用用户当前授权。
