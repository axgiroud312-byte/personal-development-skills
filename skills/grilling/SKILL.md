# 理清需求

从当前对话和已有材料开始，用中文讨论。统一处理需求讨论与边聊边记录，按用户当前意图选择是否写入项目文档。

1. 简短复述要解决的问题、已知约束和本次范围；复用用户已经确认的内容。
2. 从具体用法澄清：谁从哪里进入，输入什么，进行什么操作，得到什么结果。能从代码或资料查到的事实由 Agent 调查，低风险可逆的实现细节自行判断。
3. 只把会改变目标、范围、使用方式或整体设计且无法调查解决的选择交给用户。默认一次聚焦一个关键决策，用“需要决定什么、推荐什么、会有什么影响”提问；用户要求集中提问时合并互不依赖的问题。不重复询问已确认内容。
4. 随回答更新理解，区分已确认要求、已采纳建议、待定选择和未验证假设。推荐答案不等于用户已选择，不替用户确定关键取舍。
5. 当目标、主要场景、范围、关键取舍和完成标准足以支持下一步时收束，不为问全所有细节继续访谈。交付简短的已定结论和仍影响下一步的未知项。

## 按需要记录

只要求讨论时在聊天中整理；要求“边聊边记录”或已有本次记录授权时，及时更新相关文档。整体技术设计与共同约束进入已有 Spec，业务定义进入术语或领域文档，呈现与交互决定进入项目设计规范，局部设计与验收细节进入 Issue。

暂无合适文档时，将必要结论写入项目既有讨论位置；新项目可用 `docs/discussions/<主题>.md`。只记录确定结论、关键依据和待定项，不逐字复制聊天或预建空模板。

每个决定只维护一份有效正文，其他位置引用。Spec 或 Issue 接管讨论结论后，讨论记录保留必要的背景与去向链接，移除重复的当前要求。业务概念在讨论中即可澄清；后续进入 Spec 整体设计前应检查领域模型，已有定义直接复用，不足时主动结合 `domain-modeling` 补齐，再设计技术模块。

需求与核心领域定义清楚后，涉及 UI 且需补设计依据时，按当前授权衔接可用的 `design-ui` 与 Spec 配合。记录已有视觉参考和设计系统；常规视觉方向交由设计技能推荐并做样板，不增加多方向选择或风格批准。只要求讨论时仍在讨论范围内收束。

后续动作取决于用户当前意图和已有授权。已有材料足够时直接使用，不要求先生成 Spec、领域模型或任务。
