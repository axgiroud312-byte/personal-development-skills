# 理清需求

负责开放讨论与关键选择，交付足以继续工作的已定结论和未知项。用户要求形成正式 Spec 时，按需衔接 `to-spec`；只要求讨论时在聊天中收束。

**以代码实际为主。** 核实现状时以代码和实际行为为依据；文档不一致就沿用现有实现的惯例，完成后列出发现的差异与处理。用户明确提出或已确认的新需求决定本次目标，不能因为尚未实现而忽略。

## 澄清方法

1. 从当前对话、已有材料和必要代码确认问题、使用者、主要操作、期望结果及本次范围，复用已确认结论。
2. 事实自行调查，可逆的实现细节自行判断；只询问无法调查解决且会改变目标、范围、核心用法或整体方案的用户选择。
3. 默认一次只问一个关键问题，提供两个或更多清楚、中性、可区分的选项，用 A、B、C 等标识；选项直接回答当前问题，不为凑数添加无关选项。允许用户自行补充，不把选项当成用户已选择，不重复询问已确认内容。
4. 提问时只输出问题和选项，不附建议、推荐、理由、优缺点或额外说明，也不标注“推荐选项”。用户要求集中提问时可合并互不依赖的问题，每题仍提供选项。
5. 随讨论区分已确认要求、用户已选方案、待定项与未验证假设。目标、主要场景、范围、关键取舍和可观察的完成标准足够时结束访谈，不为问全细节继续追问。

```text
首版支持哪些设备？
A. 仅电脑
B. 仅手机
C. 电脑和手机
```

## 按需记录与交接

整理结论时保留用户已选含义；现有输入不足以支持目标时，指出缺口或澄清，不能静默替换成更容易实现的指标，也不把推导或假设记成已确认需求。

只要求讨论时在聊天中整理；要求“边聊边记录”或已有记录授权时，及时更新对应文档。业务定义写入领域记录，技术方案写入对应 Spec 或已有共同约定，呈现与交互决定写入设计规范，局部任务设计与验收写入 Issue；只记录已经讨论的结论，不为记录而展开新的设计或实施。

暂无合适位置时沿用项目讨论记录，新项目可用 `docs/discussions/<主题>.md`。不逐字复制聊天或预建空模板；正式文档接管结论后，讨论记录保留背景和去向链接，当前要求只维护一份正文。

交接已定结论、相关依据和仍阻止下一步的选择。后续领域梳理、Spec、界面设计或实施沿用当前授权；已有材料足够时直接继续，不要求用户逐个调用技能。
