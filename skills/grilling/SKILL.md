# 理清需求

负责开放讨论与关键选择，交付足以继续工作的已定结论和未知项。用户要求形成正式 Spec 时，按需衔接 `to-spec`；只要求讨论时在聊天中收束。

## 澄清方法

1. 从当前对话、已有材料和必要代码确认问题、使用者、主要操作、期望结果及本次范围，复用已确认结论。
2. 事实自行调查，可逆的实现细节自行判断；只询问无法调查解决且会改变目标、范围、核心用法或整体方案的用户选择。
3. 默认一次聚焦一个关键决策，说明推荐及影响；用户要求集中提问时合并互不依赖的问题。不重复询问已确认内容，不把推荐当成用户已选择。
4. 随讨论区分已确认要求、已采纳建议、待定项与未验证假设。目标、主要场景、范围、关键取舍和可观察的完成标准足够时结束访谈，不为问全细节继续追问。

## 按需记录与交接

只要求讨论时在聊天中整理；要求“边聊边记录”或已有记录授权时，及时更新对应文档。业务定义写入领域记录，整体技术方案写入 Spec，呈现与交互决定写入设计规范，局部任务设计与验收写入 Issue；只记录已经讨论的结论，不为记录而展开新的设计或实施。

暂无合适位置时沿用项目讨论记录，新项目可用 `docs/discussions/<主题>.md`。不逐字复制聊天或预建空模板；正式文档接管结论后，讨论记录保留背景和去向链接，当前要求只维护一份正文。

交接已定结论、相关依据和仍阻止下一步的选择。后续领域梳理、Spec、界面设计或实施沿用当前授权；已有材料足够时直接继续，不要求用户逐个调用技能。
