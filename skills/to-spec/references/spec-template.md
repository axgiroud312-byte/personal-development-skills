# Spec 编写模板

记录本规格的要求、整体方案和必要开发约束，不放术语表、领域文档、通用编程教程、项目状态或实施日志。三问说明本次目标，其余按需裁剪；规则、契约和结果只写一处，其他位置引用。明确要求与当前工程选择在容易混淆处说明，假设不当事实，不新增固定表格。完成标准约定结果，执行节奏沿用 `to-spec`。

# <规格名称>

## 本次要做什么

- **本次想实现什么：** <谁在什么场景遇到什么问题，本次要交付哪项能力或改变>
- **想要什么：** <期望的行为、体验和可观察结果；用户明确指定、不能自行改变的约束>
- **不想要什么：** <明确排除的功能、做法与体验；哪些留到以后>
- **依据：** <原始需求、PRD、已确认讨论或现有行为的位置>

## 关键场景与业务规则

说明本规格需要的具体行为与约束，不补术语表或领域模型。重要假设写明依据和影响；可以调查解决的问题自行查证，涉及目标或重要取舍的未决选择留给用户，不另设确认任务。

## 整体技术方案

- **模块与流程：** <各部分负责什么、如何协作，关键输入输出与数据流>
- **数据与接口：** <请求、校验、保存、响应与错误怎样串联；保存位置、归属、生命周期及公共契约来源，区分模拟与真实接入>
- **界面与交互：** <已有设计展示版、确认后的 Token 与组件源码；缺失只记需求和待补位置，制作由用户主动调用 design-ui，未确认的设计不要求 Token 就绪>
- **选择与影响：** <当前工程选择及依据、必要的明确约束、待核实假设；说明对现有行为、调用者和数据的实质影响>

区分现状与目标，保留具体方案，不预先规定全部代码细节。实施中新事实可以改变非强制方案，实质调整原位更新并说明依据；影响目标、明确约束、关键体验或授权的重要取舍由用户决定，不以调整方案降低要求。

## 依赖与安排（有实际依赖时保留）

说明先形成哪条完整流程、需要取得哪些代码或成果，以及真实来源和解除条件。常规实现步骤放在所属任务，多份 Spec 按真实依赖互相引用；远期只留范围与未知项。
