# 整理需求规格

本次调用只授权规格工作，不自动启动项目配置、设计版或任务拆分；已有材料直接引用，后续按用户已授权范围推进。

读取需求、项目约定、已确认结论、相关代码和文档，只补阻止定稿的缺口；开放讨论按需衔接 `grilling`。代码与实际行为决定现状，新需求决定目标；文档冲突时沿用现有惯例，记录差异与处理。

## 确定范围

小改动保持规格简短，一项连贯能力通常一份 Spec。大项目先缩小近期范围，仍复杂或存在独立能力边界时，再以 PRD/计划组织多份 Spec。按目标、行为、真实耦合与可观察结果划分，不按页面或前后端机械切割，不要求独立部署。

复用 PRD 的目标和优先级，在已有总览标明各 Spec 的边界、位置与依赖。近期细化，远期保留范围与未知项；共同约定只写一次，其他规格引用，不为结构完整新建空文档。

## 补齐方案并成文

1. 核对目标、场景、范围与关键取舍。事实自行调查；在已定约束内，可逆的选型与实现办法自行决定并简述依据，补齐缺失模块不等于替换既有技术栈。只有确实改变业务规则、用户权利或授权范围的未决选择才需澄清，并只暂停依赖部分。
2. 技术模块设计前核对业务对象、关系、归属、生命周期与规则。已有领域定义直接引用，缺失时衔接 `domain-modeling` 或完成等价梳理。
3. 涉及 UI 时引用已有设计展示版、确认后的 Token 和组件源。缺失时只记录设计要求与待补位置，沿用项目实际路径，不另造格式或启动 `design-ui`。用户主动调用后，设计版先供确认，确认该版后才输出一份 Token；规格工作不代替设计确认。
4. 读取 [Spec 模板](references/spec-template.md)，只保留消除实施歧义的内容。说明模块协作、数据流与完成行为；同一规则、契约或结果只完整写一次，其余引用，不按模板标题重复展开。

沿用现有位置并原位更新；新项目可用 `docs/specs/<主题>.md`，仅要聊天草稿时在对话交付。分清现状、已定方案与未决选择，不把占位项当事实。

## 衔接实施

完成标准描述结果；以集中开发为主，必要测试与构建在授权目标或明确交付阶段收尾安排，详见可用的 `implement`，不逐份 Spec 附加测试阶段。明确的强制检查如实保留。

Spec 保存整体方案与跨模块约定，Issue 引用适用章节，只补本任务范围、局部差异与交接；缺少公共定义时才补必要接口、字段、状态和异常。视觉规则归设计依据，实际值归共享源码。变化更新对应正文与任务，交付方案位置、关键结论和真实未知项。
