# 写清整体开发规格

交付一份能指导任务拆分和开发的 Spec：读者能看懂要实现什么、整体怎样完成、怎样判断结果。

## 理解当前需求

读取本次相关的需求、已有约定和代码，弄清目标、用户明确要求与当前实现。重要假设说明依据，方便用户纠正。

文档和代码有差异时先查证，沿用合适的现有实现，修正已证实的错误。普通工程选择自行调查和决定；影响目标、明确要求、关键体验或授权的重要取舍，由用户决定，其余部分继续。

## 整理方案

使用 [Spec 模板](references/spec-template.md)，按任务大小选择栏目。写清目标与范围、主要场景、整体技术方案、共同要求、实际依赖和完成标准。

一项连贯能力通常写成一份规格；有独立能力边界时再拆多份，相关规格互相引用。近期内容写到可实施，远期保留范围和待明确的事项。

把用户明确要求和当前工程选择区分清楚。方案写明依据，执行时可根据新事实调整工程细节；重要变化写回原处，影响用户重要选择时先交由用户决定。

涉及 UI 时引用已有原型、对应 Token 和组件来源。需要独立设计时，由用户调用 `design-ui`；先看原型，满意后提取 Token。

## 交付规格

已有规格原位更新，新项目默认使用 `docs/specs/<主题>.md`。聊天草稿请求在对话中交付，文件按当前需要创建。

完成标准写用户能看到或系统会产生的结果。实施按 `implement` 集中开发，必要检查在目标收尾统一安排，关键疑问可先小范围核实。

交付规格位置、重要取舍与仍待明确的事项。后续 Issue 引用共同要求，再补本任务的具体做法。
