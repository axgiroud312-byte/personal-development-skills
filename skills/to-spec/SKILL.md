# 把当前讨论整理成 Spec

让接手的人读完就能回答：这次要改什么，怎样看出改对了？以当前对话中已经形成的决定和项目实际行为为依据。

## 流程

1. 读取用户给出的方案、原型或现有 Spec。对尚未了解的相关代码做必要探索，用实际实现核实现状；已有调查结论直接复用。
2. 把每个主要改动写成目标行为。若两种解释会产生不同结果，先从已有决定和项目材料查证；仍需用户取舍时点明待定项，其余明确的行为可以先写。
3. 原需求已说清改动和验收，就引用现有正文，只补必要取舍。已有权威规格足以交接时，直接返回其位置。有新决定时原位更新；需要从聊天交接或用户要求单独成文时，保存一份接手者能独立读懂的简短 Spec。
4. 新 Spec 优先作为一条完整的规格发布到已配置的任务平台，并沿用项目的规格标签。采用仓库文档的项目沿用原位置，尚无约定时使用 `docs/specs/<feature>.md`。返回实际链接或路径。

## Spec 结构

### 问题

从用户的角度说明遇到了什么问题，以及为什么需要解决。

### 要改什么

按用户目标组织主要改动。对每项说明在什么情况下，用户或调用方做了什么，会观察到什么结果。需要交代价值时，可写成用户故事。现有行为与目标行为的差异容易混淆时，把差异说清楚。

### 怎样知道改对了

为每个主要改动给出一个能直接判断对错的观察。可以就近跟在对应行为后面；同一个场景能验证多项行为时写一次即可。选例时问自己：哪种做法看起来完成了，却会给出错误结果？

例如，已约定“导出全部符合筛选条件的账单”时，准备餐饮 A、餐饮 B 和交通 C，每页显示一笔。筛选餐饮后，第一页是 A，第二页是 B。在第一页导出，文件里应恰好有 A 和 B。接口、迁移等任务可以观察返回值或重新读出的数据。已有原型或规格表达得足够准确时，引用具体场景。

### 已定约束与工程假设（按需）

用户指定或项目必须沿用的做法，写明依据。暂且采用且会改变交付结果的判断，标为假设并说明影响。讨论过但尚未采用的做法，确有交接价值时标为待选方案，放在已定约束之外。例如，“最后一张票只能卖给一人”是验收要求。若暂定每单一张，就说明买两张需要下两单。用户指定的 SQLite 是约束，事务怎么写由实现者决定。

### 补充说明（按需）

放入有助于理解和实施的材料链接。既定决定需要精确表达时，可摘录关键片段并注明来源。

Spec 保存一份权威正文，其他位置引用它。完成后简要说明沉淀了什么，后续由用户手动选择下一步。
