# 整理需求规格

把当前需求整理到能支持后续设计、拆任务和实施的程度。读取已有结论、相关代码与文档，复用足够的依据；组织方式随项目调整，不重复抄写 PRD，也不重新进行完整访谈。

## 设计哲学

以代码实际为主：核实现状时以代码和实际行为为准，文档不一致就沿用现有实现的惯例，完成后列出差异与处理。本次目标仍以用户已确认的需求和规格为准，未实现的新要求不能当作过时文档；从零项目依据目标、约束与必要验证设计。

## 按范围组织

先识别当前请求是一处修改、一项能力、一个阶段还是完整产品。明确的小改动可以直接进入 Issue 或实施；有界能力通常用一份 Spec；大型项目按能力或重要变更组织多份规格，共同约定保留在已有全局设计中。不固定规格数量或文档层级。

以目标、行为、耦合关系与可观察验收判断边界。能相对独立修改或推迟时可以拆分，不要求独立部署；强耦合内容可放一起。不按页面、前后端、组件、表或字数机械切割。

PRD 已有的产品目标、范围、优先级与技术约定直接引用。各层内容可以由同一文件承载，只在有助理解和维护时拆开，不为结构完整补文件。

## 逐步细化

先明确当前阶段要交付的可用结果，优先形成从操作到结果的完整流程。默认把近期准备做的内容写细，远期保留范围、依赖和待解问题；影响方案的技术未知先安排有明确问题和证据要求的调查，不把猜测写成结论。

多份 Spec 在已有计划、总览或索引中交代各自边界、依赖与位置，缺少入口时再补简短索引。进度沿用任务和唯一项目状态入口，不另建重复状态表或空规格文件。

## 写到能接手即可

沿用已有位置；确需新建时可用 `docs/specs/<主题>.md`，只要求聊天草稿时在对话中交付。按任务需要说明：

- 要解决的问题、使用场景、本次范围与明确不包含的内容。
- 用户或其他系统能观察到的行为、输入输出、重要状态与失败情况。
- 必要的技术方案、共同约定、相关设计及真实依赖。
- 怎样判断完成，哪些结论已确认，哪些仍是假设或未知。

这些内容可合并，不机械凑标题；复杂的技术设计才单独记录，具体代码写法留到实施。区分现有行为、本次目标与已实现结果。

## 衔接与维护

技术设计前核对当前范围的业务定义，缺口按需衔接 `domain-modeling`；UI 复用已有设计，按需衔接 `design-ui`。当前交付所需设计足够即可继续，远期页面不阻塞；用户明确要求完整设计时按请求完成。

事实自行调查，可逆细节自行决定，只询问无法查清且影响目标或共同约定的用户选择。只要求写规格时交付规格与缺口，不自动扩大成界面制作或业务实现。

Issue 引用所属规格与共同约定，细化单项实施和验收。每项决定保留唯一正文，多份 Spec 共享其引用；一次变更可影响多份规格，同一能力也可持续更新，不为每次修改复制完整文档。

变化同步相关规格、共同约定与任务，实际实现和验证后再标为完成。交代本轮规格的位置、已定范围及剩余阻碍，后续按当前授权推进，不附加固定确认关卡。
