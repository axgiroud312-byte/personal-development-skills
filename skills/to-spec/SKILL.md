# 整理需求规格

用当前对话、计划、已有文档或任务整理中文 Spec；不要求先访谈、建模或执行其他技能。

1. 读取相关材料和必要代码，复用已确定结论；已有术语和架构决定存在时使用它们。
2. 只追问会影响目标、范围或关键设计且无法调查解决的缺口；其余未知标为待定，不为了填满模板编造决定。
3. 按工作规模选择下列内容，已有文档原位更新。项目位置优先，新项目默认 `docs/specs/<主题>.md`；只要求聊天草稿时在对话中交付。

## 可选结构

- **问题与目标**：为什么做，用户希望得到什么。
- **使用场景与范围**：主要操作流程、包含和排除的内容、约束。
- **设计决定**：涉及的模块及职责、模块接口、数据结构、状态变化、API 约定、异常处理，以及重要取舍的依据。
- **验证决定**：需要确认的行为和失败场景，复用哪些检查或测试，哪些需要实际操作，以及判断依据。
- **完成标准**：可观察、可核对的最终结果。
- **待定事项与依据**：尚缺的决定、相关术语、任务和资料链接。

只写当前有用且有依据的设计细节。路径或代码片段仅在比文字更准确且能维护时使用；不把试探方案写成已确认约定。验证方法按实际风险选择，不给每次修改附加整套检查。

开发中按已确认的变化更新目标、设计与验证决定，并同步受影响的任务或领域定义。Issue 引用共同设计、补充任务细节；未满足完成标准时如实记录。交付 Spec 位置或正文与关键未知，不自动生成下一阶段文档。
