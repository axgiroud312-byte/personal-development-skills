# 整理需求规格

负责整体技术方案。读取当前需求、已确认结论、相关代码和既有文档，直接复用充分的依据；只补阻止方案定稿的缺口，不重新进行一轮完整访谈。开放讨论按需衔接可用的 `grilling`，单项任务的局部设计交由 Issue 承接。

## 设计哲学

以代码实际为主：遇到文档与代码不一致时，沿用现有实现的惯例，并在完成后列出发现的差异（文档描述、代码实际及本次处理）。区分现有行为与本次变更目标；用户明确要求的新行为和修复仍按当前任务处理。

## 定稿前检查

1. 核对目标、主要场景、范围、关键取舍和可观察的完成标准。事实自行调查，可逆细节自行决定；无法调查解决且影响目标或整体方案的用户选择，逐项说明推荐与影响后澄清。等待时先写不依赖答案的部分，标清草稿、假设及待定影响。
2. 技术模块设计前核对核心场景的业务对象、关系、归属、生命周期和规则。已有定义直接引用；缺失或冲突时使用可用的 `domain-modeling` 或自行补齐相同梳理。未解决的业务含义不写成已定方案，不要求为已清楚的定义另建文档。
3. 涉及 UI 时读取已有 Token 说明、设计板或其他设计依据，按需衔接可用的 `design-ui` 或等价设计，与技术方案往返调整。只写 Spec 时记录设计要求、已有入口和未完成的设计工作，不自动制作设计板或实现页面。前端选型依据当前任务和项目约定，已有项目选择优先；组件具体操作按对应 Skill 处理。

## 整体方案

沿用已有位置并原位更新；新项目默认 `docs/specs/<主题>.md`，只要求聊天草稿时在对话中交付。按规模保留必要内容：

- **问题与目标**：为什么做，用户希望得到什么。
- **场景与范围**：主要操作、包含与排除的内容、约束。
- **整体设计**：模块职责、协作方式、关键技术数据流与归属、技术生命周期和重要取舍。
- **共同约束**：引用业务与设计依据，定义多个模块必须统一的接口、兼容要求及技术约束。
- **整体完成标准**：具体操作、可观察结果和关键失败表现，以及核对方法。
- **待定项与依据**：关键未知及其影响，引用当前有效的领域、设计和任务位置。

## 与后续工作的边界

Spec 保存整体设计与跨模块约定；Issue 引用这些依据并细化单项接口、字段、状态、异常及验收步骤，具体代码写法留到实施。设计规范保存呈现与交互，实际 Token 和组件实现沿用各自唯一源码，不在 Spec 复制另一套。

发现变化时更新对应权威来源与受影响的方案、任务和验收。交付 Spec 正文或位置、已定方案、关键未知及相关依据；后续设计、拆任务和开发按当前授权推进，不以写 Spec 为由附加测试、构建或发布。
