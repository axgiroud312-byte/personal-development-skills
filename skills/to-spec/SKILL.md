# 把当前讨论整理成 Spec

综合当前对话和已有的代码理解，记录已经形成的决定，让后续会话能接着工作。直接沿用已讨论清楚的内容，聚焦整理与表达。

## 流程

1. 读取用户给出的方案、原型或现有 Spec。对尚未了解的相关代码做必要探索，用实际实现核实现状；已有调查结论直接复用。
2. 按下面的结构写出 Spec。用户故事充分覆盖已确定的功能、交互和相关状态，实现决定记录已经讨论或查明的技术选择。
3. 保存到项目约定的位置：已有 Spec 原位更新；新 Spec 优先作为一条完整的规格发布到已配置的任务平台，并沿用项目的规格标签；采用仓库文档的项目沿用原位置，尚无约定时使用 `docs/specs/<feature>.md`。返回实际链接或路径。

## Spec 结构

### 问题

从用户的角度说明遇到了什么问题，以及为什么需要解决。

### 解决方案

从用户的角度描述解决后能做什么，主要体验如何连贯地完成。

### 用户故事

用编号列表覆盖功能的各个方面，每条表达一个明确的用户需求：

> 作为〈角色〉，我希望〈功能或行为〉，以便〈获得的价值〉。

例如：作为阅读者，我希望收藏文章并在收藏列表里再次找到它，以便之后继续阅读。

### 实现决定

记录已经确定、后续实现需要沿用的决定，按实际需要涵盖：

- 要新增或修改的模块及其职责。
- 模块之间的接口与配合方式。
- 已讨论清楚的技术选择和架构。
- 数据模型调整与 API 契约。
- 具体交互、状态流转，以及已有原型或设计的结论。

用模块、契约和行为表达稳定的决定，具体代码定位留给实施时核对。已有原型中的状态机、类型或数据结构，若能更准确地表达决定，可摘录关键片段并注明来源；其他设计材料保留引用。

### 补充说明（按需）

放入有助于理解和实施的其他已知信息或材料链接。

Spec 保存一份权威正文，其他位置引用它。完成后简要说明沉淀了什么，后续由用户手动选择下一步。
