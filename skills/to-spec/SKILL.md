# 把当前讨论整理成 Spec

让接手的人读完就能回答：这次要改什么，怎样看出改对了？以当前对话中已经形成的决定和项目实际行为为依据。

## 流程

1. 读取用户给出的方案、原型或现有 Spec。对尚未了解的相关代码做必要探索，用实际实现核实现状；已有调查结论直接复用。
2. 把每个主要改动写成目标行为。若两种解释会产生不同结果，先从已有决定和项目材料查证；仍需用户取舍时点明待定项，其余明确的行为可以先写。
3. 保存到项目约定的位置：已有 Spec 原位更新；新 Spec 优先作为一条完整的规格发布到已配置的任务平台，并沿用项目的规格标签；采用仓库文档的项目沿用原位置，尚无约定时使用 `docs/specs/<feature>.md`。返回实际链接或路径。

## Spec 结构

### 问题

从用户的角度说明遇到了什么问题，以及为什么需要解决。

### 要改什么

按用户目标组织主要改动。对每项说明在什么情况下，用户或调用方做了什么，会观察到什么结果。需要交代价值时，可写成用户故事。现有行为与目标行为的差异容易混淆时，把差异说清楚。

### 怎样知道改对了

为每个主要改动给出一个能直接判断对错的观察。可以就近跟在对应行为后面；同一个场景能验证多项行为时写一次即可。选例时问自己：哪种做法看起来完成了，却会给出错误结果？

例如，已约定“导出全部符合筛选条件的账单”时，让餐饮 A 和 B 分处两页，另有一笔交通 C。在第一页筛选餐饮并导出，文件里应恰好有 A 和 B。这个例子同时说清了筛选和分页。接口、迁移等任务可以观察返回值或重新读出的数据。已有原型或规格表达得足够准确时，引用具体场景。

### 已确定的约束（按需）

记录会影响交付的既定选择，例如兼容旧接口、沿用某个数据格式或原型中的状态转换。需要精确表达时摘录关键片段并注明来源。常规工程做法留给实现者结合代码选择。

### 补充说明（按需）

放入有助于理解和实施的其他已知信息或材料链接。

Spec 保存一份权威正文，其他位置引用它。完成后简要说明沉淀了什么，后续由用户手动选择下一步。
