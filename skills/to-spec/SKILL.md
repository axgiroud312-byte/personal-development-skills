# 整理需求规格

用当前对话、计划、已有文档或任务设计中文 Spec，负责整体方案。即使用户直接要求写 Spec，也先判断信息是否足够；需求澄清与领域模型检查由本技能主动衔接，不要求用户先手动调用其他技能。

## 写之前澄清关键决策

1. 读取相关材料和必要代码，复用已确定结论；已有术语和架构决定存在时使用它们。
2. 区分事实、用户选择和实现细节：事实由 Agent 调查；低风险可逆细节自行判断；会改变目标、范围、核心流程或整体设计且无法调查解决的选择，先向用户澄清。例如单人还是多人使用、数据存在哪里、哪些能力必须首版交付。
3. 默认一次聚焦一个关键决策，说明需要决定什么、推荐什么、会产生什么影响；不把整张技术问卷交给用户，不重复询问已确认内容。关键决定未明确时可整理不依赖答案的内容，并将文档标为草稿、列明待定影响；不把推荐或假设当成已确定方案。
4. 目标、主要场景、范围、关键取舍和可观察的完成标准足以支持业务梳理时结束需求澄清，不要求先确定模块设计、所有局部细节或代码写法。

## 整体设计前检查领域模型

1. 在划分模块、确定模块职责和协作方式前，读取已有术语表、领域记录及本次已确认的业务结论，核对主要场景中的对象、关系、归属、生命周期和关键业务规则。结合必要代码区分现状与期望，不能只检查有没有领域文档或是否执行过某个 Skill。
2. 已有定义足够且一致时直接复用并引用；缺失、冲突或出现新业务概念时，主动使用可用的 `domain-modeling` 补齐当前缺口。该技能不可用时也要自行完成上述梳理，不把寻找或调用技能的工作交给用户。业务含义涉及关键用户选择时先澄清，不自行猜定。
3. 当前核心场景能用一致的对象和规则解释清楚后，进入整体设计。目标和范围可以先写草稿；未解决的业务歧义标明影响，不将依赖它的设计定稿。不要求穷尽未来业务或在定义已清楚时另建模型文档。

## 与界面设计配合

需求与核心领域定义清楚后，涉及 UI 时先读取已有设计目录总览、共享 Token、设计板和原型组件源码，已有依据足够就复用；需补缺口时主动衔接可用的 `design-ui` 或等价设计，与技术方案往返调整。遵守本次请求范围，不因写 Spec 擅自扩大为完整设计实施。

前端尚未选型时，参考可用 `design-ui` 主文件开头的技术栈与组件约定，记录本次实际采用的方案；已有项目约定优先，具体依赖按项目需要选择。

Spec 保存总体技术方案并引用界面设计；已有设计位置沿用，新项目完整设计默认使用 `Designer/`，设计说明放在 `Designer/DESIGN.md`。实际 Token 值只在既有主题源或新设计目录的共享源码维护，由设计板、原型与业务组件共用。拆具体 UI Issue 前应具备本次足够的设计方向、关键流程、Token、组件与状态依据；引用真实路径和原型入口，当前小改动已有依据够用时直接复用，不添加阶段批准。

## 整体设计的内容

按规模选择必要内容，已有文档原位更新。项目位置优先，新项目默认 `docs/specs/<主题>.md`；只要求聊天草稿时在对话中交付。

- **问题与目标**：为什么做，用户希望得到什么。
- **使用场景与范围**：主要操作流程、包含和排除的内容、约束。
- **整体设计**：模块及职责、相互协作、关键数据流与归属、影响整体的生命周期和重要取舍。
- **共同约束**：引用领域记录中的业务规则，补充多个模块依赖的接口契约、兼容要求和其他已确认约束。只精确到需要统一的程度。
- **整体完成标准**：用户经过哪些操作能得到哪些可观察结果，关键失败场景应有何表现，怎样实际核对。
- **待定事项与依据**：尚缺的决定、相关术语、界面设计规范、共享 Token 与样板位置、任务和资料链接，按本次范围保留。

## 与 Issue 的边界

按决定的影响范围分工：整体设计与跨模块约定留在 Spec 或它引用的一份权威设计文档；单个任务的局部接口、数据字段、状态处理、异常提示及具体验收步骤交给 Issue。共享接口确需精确定义时可以在共同设计中写清，Issue 引用，不在多处复制正文。

具体代码写法留到实施时判断，不为填满模板预先冻结所有细节。验证依据实际风险和可观察行为选择，不为写 Spec 附加整套测试、构建或发布步骤。

设计中发现新的业务歧义时回到领域梳理，先更新业务定义，再调整受影响的模块设计、Issue 与验收条件；整体技术设计变化更新 Spec，呈现与交互变化更新设计规范及对应源码，局部执行变化由 Issue 承接，同步受影响任务。每个决定只维护一份有效正文。交付 Spec 位置或正文、引用的领域与界面设计依据、已定方案及关键未知；未满足完成标准时如实记录，后续动作沿用用户当前授权。
