# 整理需求规格

负责当前范围的整体技术方案。读取当前需求、已确认结论、相关代码和既有文档，直接复用充分的依据；只补阻止方案定稿的缺口，不重新进行一轮完整访谈。开放讨论按需衔接可用的 `grilling`，单项任务的局部设计按需由 Issue 承接。

**以代码实际为主。** 核实现状时以代码和实际行为为依据；文档不一致就沿用现有实现的惯例，完成后列出发现的差异与处理。用户明确提出或已确认的新需求决定本次目标，不能因为尚未实现而忽略。

## 按规模确定范围

明确的小改动可直接实施，或用一个 Issue 说明范围与验收；一项较完整的能力、简单项目通常一份 Spec。大项目先缩小单次实施范围、减少同时在上下文中处理的任务；当单个阶段仍难以保持清晰，或存在可独立验收的能力边界时，再以 PRD 为依据组织多份 Spec。拆分是解决实际复杂度的方法，不因项目大而机械增加文档。

按目标、行为、耦合关系与可观察验收判断边界，强耦合内容可以放一起；不按页面、前后端或文件大小机械切割，也不要求每份 Spec 独立部署。

PRD 已说明的目标、范围和优先级直接引用。在已有总览或计划中简要标明各 Spec 的边界、位置与依赖；共同接口和约束只定义一次，其他规格引用，不要求另建全局设计文件。

先细化近期准备交付的内容，远期保留范围、依赖与待解问题；当前范围所需依据足够即可继续，影响方案的关键未知先调查，不为未开始的阶段预建空文档。

## 定稿前检查

1. 核对目标、主要场景、范围、关键取舍和可观察的完成标准。事实自行调查，可逆的技术细节自行决定；会改变用户权利、业务规则或范围的取舍不能用“默认设计”替用户定案。未确认的选择标明待定及影响，按需澄清，只暂停依赖它的部分，继续整理已有依据足够的内容。
2. 技术模块设计前核对核心场景的业务对象、关系、归属、生命周期和规则。已有定义直接引用；缺失或冲突时使用可用的 `domain-modeling` 或自行补齐相同梳理。未解决的业务含义不写成已定方案，不要求为已清楚的定义另建文档。
3. 涉及 UI 时读取已有设计板、Token 说明或其他设计依据，按需衔接可用的 `design-ui` 或等价设计，与技术方案往返调整。只写 Spec 时记录设计要求、已有入口和未完成的设计工作，不自动制作设计板或实现页面。前端选型依据当前任务和项目约定，已有项目选择优先；组件具体操作按对应 Skill 处理。

## 整体方案

开始编写或更新时读取 [Spec 编写模板](references/spec-template.md)，用它核对目标、业务规则、模块协作、数据流、共同约定、依赖与验收是否足够。按范围删减、合并或沿用项目模板，不为凑齐标题发明内容。

沿用已有位置并原位更新；新项目可用 `docs/specs/<主题>.md`，只要求聊天草稿时在对话中交付。模板中的技术方案和可观察完成标准不能只用功能清单代替；已确认要求、技术决定和未决业务选择分清，不把模板占位内容当事实。

## 与后续工作的边界

Spec 保存其范围内的整体设计与跨模块约定，多份 Spec 引用必要的共同决定；Issue 引用所属规格并细化单项接口、字段、状态、异常及验收步骤，具体代码写法留到实施。设计规范保存呈现与交互，实际 Token 和组件实现沿用各自唯一源码，不在 Spec 复制另一套。

发现变化时更新对应来源与受影响的规格、任务和验收；已有规格持续维护，不为每次修改复制完整文档。交付 Spec 正文或位置、已定方案、关键未知及相关依据；后续设计、拆任务和开发按当前授权推进，不以写 Spec 为由附加测试、构建或发布。
