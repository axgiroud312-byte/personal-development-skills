# 写清需求与方案理由

交付一份清楚的 Spec：读者能理解本次需求、方案选择的原因，以及用户想要和不想要的内容。

## 理解当前需求

读取本次相关的需求、已有约定和代码，弄清目标、用户明确要求与当前实现。重要假设说明依据，方便用户纠正。

文档和代码有差异时先查证，沿用合适的现有实现，修正已证实的错误。普通工程选择自行调查和决定；影响目标、明确要求、关键体验或授权的重要取舍，由用户决定，其余部分继续。

## 整理方案

使用 [Spec 模板](references/spec-template.md) 的四部分：想实现什么、为什么选择这个方案、我想要什么、我不想要什么。方案部分简述做法，重点解释选择理由与取舍；两份清单按已表达的需求逐条填写，每条说明一件具体的事。

一个连贯主题通常写成一份 Spec；存在独立需求时再拆多份，相关资料在方案理由中引用。

把用户明确要求和当前工程选择区分清楚。方案写明依据，执行时可根据新事实调整工程细节；重要变化写回原处，影响用户重要选择时先交由用户决定。

涉及 UI 时，方案理由可以引用已有原型、对应 Token 和组件来源。需要独立设计时，由用户调用 `design-ui`；先看原型，满意后提取 Token。

## 交付规格

已有规格原位更新，新项目默认使用 `docs/specs/<主题>.md`。聊天草稿请求在对话中交付，文件按当前需要创建。

在聊天中交付规格位置和关键方案理由；需要用户决定的取舍在对话中澄清。后续 Issue 引用对应需求条目，补充具体做法、依赖和预期结果；实施沿用 `implement` 的集中开发节奏。
