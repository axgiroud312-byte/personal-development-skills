# 整理需求规格

负责当前范围的整体方案。以代码和实际行为判断现状，以用户已确认需求确定目标；文档不一致时沿用现有实现惯例，说明差异与处理。

1. 读取需求、已有结论和必要代码，只补阻止方案定稿的缺口。事实自行调查，可逆细节自行决定；无法判断且影响目标或业务规则的选择再澄清，未决项标明影响，其余部分继续。
2. 按规模确定范围：小改动可直接实施或写一个 Issue；一项连贯能力通常一份 Spec。复杂项目先缩小近期范围，必要时按能力、耦合与完成边界分为多份 Spec，不按页面或前后端机械切割，也不要求各自独立部署。
3. 技术模块设计前核对业务对象、关系、归属、状态与规则；已有定义直接引用，缺口按需交给 `domain-modeling`。涉及 UI 时引用已有原型、Token 与组件源码，设计不足就记录前置任务，或在授权范围内衔接 `design-ui`。
4. 写作前读 [Spec 编写模板](references/spec-template.md)，明确本次想实现什么、想要什么、不想要什么，补齐技术方案、数据流、模块协作与可观察结果。按任务裁剪，不能只列功能名或用猜测填空。
5. 更新现有位置；新项目可用 `docs/specs/<主题>.md`，只要聊天草稿就在聊天交付。多份规格在已有总览中标明范围与依赖，共同决定只定义一次；近期具体，远期保留概要和未知项。

完成标准描述结果。以集中开发为主，必要测试和构建由整体负责人在本次授权目标或明确交付阶段收尾安排；保留已知强制检查，不逐规格铺测试任务。

Spec 保存整体方案，Issue 细化局部接口、状态、异常与预期结果；变化更新对应来源和受影响任务。交付正文或位置、关键决定与未决项，后续按当前授权推进，不因写 Spec 自动开展设计、开发或发布。
