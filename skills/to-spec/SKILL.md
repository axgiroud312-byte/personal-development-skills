# 整理开发规格

只处理本次规格工作，已有材料直接引用，不自动启动项目配置、设计、任务拆分或开发。

## 先确定当前要求

读取当前需求、相关已有约定和必要代码，只补影响本次规格的缺口，不扫描整套文档。对话和历史材料帮助理解意图；重要假设明确说明，不能把推断写成用户已确认。

用户当前目标和明确约束决定要实现什么，代码与实际行为用于核实现状。文档冲突或过时时先查证，默认沿用现有实现惯例，不延续已证实的错误；新的功能要求不能因为尚未实现而被忽略。完成后列出实质差异。

常规工程选择自行调查和决定；只有影响目标、明确约束、关键体验或授权的重要取舍才问用户，不受影响的部分继续。需要开放讨论时按需使用 `grilling`。

## 写清整体方案

按目标和真实依赖划分规格，一项连贯能力通常一份；范围大且有独立能力边界时再拆多份，不按页面或前后端机械切割。相关规格互相引用，近期内容写到可实施，远期保留范围与未知项。

读取 [Spec 模板](references/spec-template.md)，只保留本次需要的内容：目标与范围、具体行为、整体技术方案、跨任务约束、真实依赖和完成标准。Spec 可以写本功能的开发规范，不放通用编程教程、重复执行流程、术语表、领域文档、项目进度或讨论日志。

写清方案及依据，在容易混淆处区分用户明确要求、当前工程选择和待核实假设，不强制新增表格。没有改变目标、明确约束和已授权影响范围的方案细节，可在实施中依据新事实调整；涉及重要取舍则由用户决定，不悄悄改写已确认要求。

涉及 UI 时引用已有原型、对应的已确认 Token 和组件源码；缺失只记设计要求及待补位置。用户主动调用 `design-ui` 后才制作原型，用户满意后再提取 Token，不把规格工作当成设计确认。

沿用已有位置原位更新；新项目默认 `docs/specs/<主题>.md`。仅要聊天草稿时在对话交付，不另建 PRD、计划、总览或空文档。

## 交给任务与实施

Issue 引用 Spec 中的目标与共同约束，只补本任务的具体方案、依赖和结果。同一规则只写一处；新事实改变方案时更新所属正文和受影响任务，保留明确要求与调整依据。

完成标准描述可观察结果，不把每条标准变成测试任务。执行节奏由可用的 `implement` 统一：集中开发、少做重复测试，目标收尾做必要验证；会影响后续工作的关键问题可提前小范围检查，已有强制检查保留。

交付规格位置、重要假设和取舍、仍未确定的事项，不额外生成报告。
