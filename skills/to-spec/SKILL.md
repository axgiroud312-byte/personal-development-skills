# 沉淀目标与总体方案

对用户真正想实现什么，以及方案能否实现它负责。用户的表达与现有上下文是理解需求的起点；主动接触相关的实际材料和实现，为影响方案的判断取得依据。探查的对象、方式和深度随尚未解决的问题决定，新的认识可以修正已有判断。

假设从已理解的需求出发，补足实现目标需要的合理选择。把用户要求、查证结果、工程判断和重要假设表达清楚；涉及用户意图或重要取舍的不确定性，带着已有发现和建议继续讨论。本次需求对齐在编写 Issue 前完成，已有明确结论直接沿用。

## 形成可以继续深化的设计

把目标、预期效果和可行的总体方案沉淀下来，让后续工作理解为什么这样设计、各部分怎样共同完成需求。根据项目需要深入整体架构、前后端职责、布局与关键交互、数据流转和接入方式；细节深度以明确设计方向、支撑后续任务细化为准。

将探查所得转化为适合当前项目的具体判断，在有助于核实或继续工作的地方保留依据。已有实现帮助核实现状；文档与代码不一致时查清原因，沿用合适的现有惯例，说明重要差异。

Spec 工作可以直接包含需求所需的原型、Design Token 或其他设计表达，按需参考 [design-ui](../design-ui/SKILL.md) 和 [design-quality](../design-quality/SKILL.md)。选择能帮助理解和实现需求的产物，沿用已有设计，并如实说明当前确定与待讨论的部分。

## 让信息容易找到和维护

结构、篇幅和表达方式由模型根据需求自主决定。简单需求可以集中表达；复杂项目按信息关系拆成相互索引的文档，让读者先理解整体，再按任务读取有关细节。每项结论在合适的位置维护，其他位置引用。

已有规格原位更新，新项目默认放在 `docs/specs/`；聊天草稿在对话中交付。新发现和用户反馈写回对应结论。目标、边界、关键行为和影响需求的假设明确后，再交给 Issue 深化实施方案和任务细节；待解决的需求问题留在当前讨论或 Spec 中解决。
