# 整理需求规格

读取需求、已确认结论、相关代码和文档，只补阻止定稿的缺口；开放讨论按需衔接 `grilling`。代码与实际行为决定现状，新需求决定目标；文档冲突时沿用现有惯例，记录差异与处理。

## 确定范围

小改动可直接实施或写一个 Issue；一项连贯能力通常一份 Spec。大项目先缩小近期范围，仍复杂或存在独立能力边界时，再以 PRD/计划组织多份 Spec。按目标、行为、真实耦合与可观察结果划分，不按页面或前后端机械切割，不要求独立部署。

复用 PRD 的目标和优先级，在已有总览标明各 Spec 的边界、位置与依赖。近期细化，远期保留范围与未知项；共同约定只写一次，其他规格引用，不为结构完整新建空文档。

## 补齐方案并成文

1. 核对目标、场景、范围与关键取舍。事实自行调查，可逆技术细节自行决定；影响业务规则、用户权利或范围的未决选择标明影响，只暂停依赖部分。
2. 技术模块设计前核对业务对象、关系、归属、生命周期与规则。已有领域定义直接引用，缺失时衔接 `domain-modeling` 或完成等价梳理。
3. 涉及 UI 时引用已有原型、Token 和组件源，按需与 `design-ui` 往返补齐方案。只要求写 Spec 时记录设计要求和待完成工作，不自动制作原型。
4. 读取 [Spec 模板](references/spec-template.md)，按本次范围删减或映射已有模板。说明模块如何协作、数据如何流动和完成后的行为，不能只列功能名。

沿用现有位置并原位更新；新项目可用 `docs/specs/<主题>.md`，仅要聊天草稿时在对话交付。分清现状、已定方案与未决选择，不把占位项当事实。

## 衔接实施

完成标准描述结果；以集中开发为主，必要测试与构建在授权目标或明确交付阶段收尾安排，详见可用的 `implement`，不逐份 Spec 附加测试阶段。明确的强制检查如实保留。

Spec 保存整体方案与跨模块约定，Issue 细化单项接口、字段、状态和异常；视觉规则归设计依据，实际值归共享源码。变化更新所属正文及受影响规格和任务。交付方案位置、关键结论与未知项，后续按当前授权推进。
