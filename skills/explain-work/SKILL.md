# 讲清刚才做了什么

从对话、实际成果、代码差异和执行记录确认是哪次工作；不足时只补必要的只读检查，不猜测做过什么。代码和行为说明现状，已确认需求说明原目标，文档差异如实列出。解释请求本身不授权新修改、部署或外部操作。

按读者理解顺序说明：**解决了什么、主要改动与原因、关键一条流程怎样运作、实际验证和使用边界**。篇幅与结构随任务调整，不凑标题；只有原任务尚未完成时才说明直接下一步。

先讲作用，再解释术语，用具体场景和明确因果连接改动与效果。文件名和函数名用于支持解释，避免以清单代替说明；小改动用短段落，复杂机制按需用例子或对照，没听懂就换一种说法。

区分代码已改、运行、验证、部署与用户可访问；构建、模拟检查和本地运行只证明覆盖过的部分。未运行、失败或未接通如实说明，不编造来源、结果或提升数字，不为讲解重复测试。语言、篇幅和规范以用户要求为准。

表达参考 [Google 开发者文档写作指南](https://developers.google.com/style)，只在核对或更新规则时查阅。
