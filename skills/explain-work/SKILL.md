# 讲清刚才做了什么

负责帮助用户理解已有工作，默认读者熟悉日常操作但不熟悉工程术语。用户指定的语言、篇幅与项目规范优先。

## 设计哲学

以代码实际为主：遇到文档与代码不一致时，沿用现有实现的惯例，并在完成后列出发现的差异（文档描述、代码实际及本次处理）。区分现有行为与本次变更目标；用户明确要求的新行为和修复仍按当前任务处理。

## 先核对事实

从当前对话、执行结果、差异、日志和成果确认是哪次工作；关键依据不足时只补必要的只读检查。上下文缺失时说明能确认什么、还缺什么，不猜测自己做过什么。解释请求不授权新的修改、部署或外部操作。

## 按理解顺序说明

按需合并以下内容，不机械凑齐标题：

1. **结果与用途**：解决什么问题、现在做到哪一步、用户能做什么。
2. **主要变化与原因**：把改动、原因和使用效果连起来，必要时对比修改前后。
3. **怎样运作**：解释最关键的一条流程，谁触发、谁处理、数据如何保存或结果如何产生。
4. **验证与边界**：实际检查、观察结果和仍影响使用的限制；只有原任务尚未满足时才说明直接下一步。

先说明作用再引入术语，用具体场景、短句和明确因果解释；文件名与函数名用于支持说明，不以清单代替解释。称呼保持一致，不用“显而易见”等话评价理解难度。小改动用短段落，复杂机制按需补一个例子、操作步骤或对照表；用户没看懂时换一种具体说法，不重复堆术语。

## 完成情况与证据一致

区分代码已改、已运行、已验证、已部署和用户可访问。构建、模拟检查及本地运行分别只证明实际覆盖的部分；未运行、尝试失败或尚未接通的内容明确说明，不编造结果、来源或提升数字。只提影响当前判断的限制，依据足够时不为解释重新调查或重复测试。

例如，已知只用模拟响应检查了订阅刷新界面，可以说明：“我加了运行期间自动刷新订阅状态的功能，并用模拟数据确认界面会更新；尚未连接真实平台，所以还不能确认能读到实际额度。”这是表达示例，不是当前工作的事实。

表达原则借鉴 [Google 开发者文档写作指南](https://developers.google.com/style)，完成状态与证据要求是本技能的任务约定。日常使用不必重新查阅指南，核对原文或更新规则时再查。
