# 完成一项开发

负责一项任务从理解到交付，用中文说明结果。只要求解释或评审时交付意见；实施范围和远端操作沿用用户已有授权，不反复询问常规步骤。

明确的小修直接实施，不为走流程补齐讨论、Spec 或领域文档。具体代码写法在已有约束内自行判断。

涉及 UI 时先读取本次设计目录总览、设计规范、共享 Token 和设计板，再复用原型组件源码及交互约定；已有 `Designer/` 或其他约定目录作为实现依据。依据不足时按需衔接可用的 `design-ui` 或等价设计，只补当前缺口；延续已选组件与 registry，按需安装依赖，不为小改动重做整套设计。核对原型与实际页面行为，设计变化同步 Token、组件、设计板和相关约定，不从截图另猜一套数值或复制出脱节的组件。

前端尚未选型时，参考可用 `design-ui` 主文件开头的技术栈与组件约定；先核对已有项目方案，具体依赖按本次需要选择。进入前端实施前按该约定核对并补齐 shadcn 初始化与 registry 配置，已有配置和定制直接复用。

## 开始与实施

1. 读取 Issue 正文、最新相关讨论、依赖和必要代码，明确目标、范围及验收方法。核对任务涉及的领域定义，已有规则直接复用；出现新业务概念或语义冲突时主动使用可用的 `domain-modeling` 或等价梳理，只补当前缺口后再实现相关行为。Issue 驱动项目缺少任务时补建最小 Issue；明确的小修不为流程补文档，只要求本地修改时直接处理。
2. 确认工作目录、分支、已有修改和交付目标；保护其他工作。需要隔离时建立临时工作树，在任务中关联实际工作分支。
3. 复现问题或核对期望行为，定位原因后实施。业务含义或规则变化时先更新领域记录，再同步受影响的 Spec、Issue 设计、验收条件与实现；整体技术设计、模块职责或跨模块约定变化更新 Spec，呈现与交互变化更新设计规范、对应源码及受影响任务，局部执行细节更新 Issue，其他位置引用。实际 Token 值只维护在共享源码，样板与业务组件共用。会改变目标或整体方案且无法调查解决的用户选择，说明推荐与影响后澄清；不把无关改进并入当前任务。
4. 对照任务或原始请求中的可观察结果验收。测试和审查按本项目设置执行，可分别开启或关闭；未指定时按改动风险选择必要检查，不机械运行全套测试或生成构建产物。涉及 UI 时通过项目实际浏览器或桌面入口操作，核对本次关键流程与交互状态，有视觉参考时同时核对布局几何。必要检查通过后，仅在新改动、失败或未解决问题需要时扩大或重复验证。报告真实操作、模拟检查和未验证部分，不将跳过写成通过。

## 提交与 PR

5. 对照 Issue 验收条件检查实际差异，仅提交本次工作；核对推送成功、远端分支包含本次提交，再创建或更新指向正确目标分支的 PR。用户只授权本地修改时在本地交付。
6. PR 写清关联 Issue、解决后的行为、关键改动、实际验证结果及剩余问题；Issue 回链 PR。一个可独立评审的任务通常对应一个 PR，合并相关任务时逐项说明覆盖范围。
7. 仅要求提交 PR 时停在请求评审或合并，不自动合并或关闭 Issue。已有项目关闭规则时按实际合并、验证或用户验收结果处理；总目标不因单个子任务交付而关闭。

## 交付后清理

确认本次提交已推送且已包含在实际建立的 PR 中后，执行清理：

- 先把需要试用的程序、必要结果和说明保存到工作树以外的约定交付位置，并确认可访问；暂停本任务仍占用临时目录的进程。
- 核对归属和真实路径，清理本次不再需要的构建与临时产物，再通过当前环境的工作树管理方式移除本次创建的临时工作树。保留主工作区、他人修改、未交付内容和 PR 使用的远端分支。
- 清理后核对实际残留。推送、PR 或交付保存未完成时，保留必要工作；清理被阻止时报告留下什么及原因，不把清理失败写成成功。

本地交付也清理明确属于本次且可丢弃的临时产物，但保留承载未推送代码的工作树。最终报告 Issue/PR 或本地位置、实际验证、试用入口以及清理结果。

用户要求“做完后解释”时，先完成上述实际工作，再使用可用的 `explain-work` 讲清结果、主要变化及原因、关键流程和验证范围。该技能不可用时依据实际证据自行说明，不阻塞交付。用户只追问已有工作时直接讲解，必要时补充只读检查，不因此启动新的修改。
