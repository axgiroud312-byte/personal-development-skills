# 集中完成开发

负责单项实施，也是 `implement-spec` 复用的执行方法。只要求分析、评审或解释时完成该范围。

## 理解目标并自主判断

读取当前请求、相关 Issue、Spec 和必要代码，只取本次需要的依据，不固定扫描全部文档。核对实际目录、分支、已有修改与交付授权，保护无关工作；明确任务缺少文档时可直接实施，不先补齐全套资料。

用户当前目标与明确约束决定要做什么，实际代码和运行结果用于核实现状。Spec、Issue 保存当前共识与实施方案；文档冲突或过时时先查证，默认沿用现有实现惯例，不延续已证实的错误，也不因功能尚未实现就忽略新需求。

常规细节，以及不改变目标、明确约束和已授权影响范围的非强制方案，自主选择或调整。重要假设、方向变化与实质副作用用简短说明让用户看见；历史记录与记忆是线索，需要核实，不能凭推断覆盖用户明确选择。取舍会改变功能范围、明确约束、关键体验或带来未授权的重要影响时，说明差异并由用户决定；只暂停依赖该决定的部分，已有授权不重复确认。

用户纠正时，先找出失效的理解或假设，再调整相关工作。过去的方法失败时核对原因，避免继续堆补丁或无新证据地重试；没有可行路径时报告具体阻碍，不把部分结果说成全部完成。

## 集中开发，少做重复测试

按任务与真实依赖持续完成本次授权范围。Issue、提交、子任务或内部步骤结束不自动触发一轮测试、构建、评审和收尾；不逐项询问是否继续。具体实施办法由任务与实际情况决定，不另套固定开发配方。

普通改动的必要检查集中到目标收尾。出现实际错误，或未证实的关键假设会影响大量后续工作时，先做足以判断该问题的小检查，再继续实施。

优先复用已有检查，不默认采用 TDD，不主动铺测试框架、覆盖率任务或反复全量构建。补测试须能验证本次实际行为或防止具体回归；保留已有强制检查。相关检查通过后，只有新改动、失败或未解决的问题才扩大或重复验证；修复后复查受影响部分。

## 按目标收尾与交付

收尾对照原始目标和当前有效要求，核对实际成果及证据，选择与最终改动相称的必要验证与构建。区分代码已改、真实运行、模拟、实际验证与用户验收；未做、失败和缺失如实说明，不能删减要求来宣布完成。

单独交付的任务自行收尾；作为整体开发的一部分，只回交成果位置、重要调整、已有检查和待收尾项，由负责人统一整合与验证，不要求每个子任务重复全套检查。

规格或任务有实质变化时，只原位更新对应 Spec 或 Issue；进展与剩余事项放对应 Issue，没有 Issue 就在聊天交接。完成后简明说明结果、重要取舍及原因、文档与实际情况的差异和未验证项，不额外生成报告。仅改工程内部结构不要求重做设计原型。

提交、推送、PR 和清理沿用已有授权，只交付本次范围并读回核对结果；只要求 PR 不自动合并。清理前确认成果已保留或整合，只移除本次可丢弃内容，保护其他修改、未推送成果和本地交付工作树，不另存备份。

## 与其他技能衔接

`setup-project-skills`、`to-spec`、`to-tickets`、`design-ui` 仍只由用户主动调用。正常实现和维护受影响的已有资料可继续，不能借自主判断另开专项流程或生成多余文档。

UI 实施按需参考已有原型、对应 Token、实际组件和 `design-quality`。原型仅作参考，不要求共用源码，也不代表正式前端已完成；沿用用户满意后才提取 Token 的约定，不自行更改明确指定的设计。
