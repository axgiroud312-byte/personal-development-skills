# 集中完成开发

按用户本轮请求确定交付：讨论给出结论，开发完成可用成果。本技能也为 `implement-spec` 提供执行方法。

## 找准要完成的事

读取本次任务需要的请求、Issue、Spec 和代码，弄清目标、必须保留的要求与当前实现。核对工作目录、分支和已有修改，保留用户正在做的其他工作。

以用户当前目标为方向，用代码和运行结果核实现状。文档过时或做法有误时查清原因，沿用合适的现有实现，修正已证实的错误；历史和记忆中的线索也按实际情况核对。

## 自主推进，集中开发

保留用户明确要求，工程细节在授权范围内自行处理。发现更合适的实现方法时，可以调整当前方案，并简短说明重要依据和影响。

涉及目标、明确要求、关键体验或新增重要影响的取舍，由用户决定；其余部分继续。重要假设及时说明，用户纠正后先调整理解，再继续相关工作。

把一组相关任务集中做完，由负责人在目标收尾时统一检查。项目已有的强制检查照常完成；测试和构建优先复用现有安排。新增测试以确认具体行为、预防已知问题再次出现为目的。

中途遇到实际错误，或一个关键疑问会影响大量后续工作，先做足以判断的小检查。检查通过后继续交付；出现新改动、失败或仍待解决的问题时，按影响复查。

## 完成后交付

对照本次目标核对成果，用最少且足够的检查确认关键行为。明确区分代码已改、真实运行、模拟检查和用户验收；待验证项及具体阻碍如实说明。

独立任务自行收尾；子任务回交成果位置、重要调整、已有检查和待收尾事项，由负责人统一整合。有对应 Issue 时，将进展和结果写回该 Issue；其他任务在聊天中交接。

方案有实质变化时，原位更新对应 Spec 或 Issue。交付时说明结果、重要取舍、文档与实际情况的差异，以及如何使用成果。

本地修改、提交、推送、PR 和合并分别按用户已授权的方式处理，写入后读回核对。成果与未提交修改妥善保留，清理前确认内容可丢弃；修改采用原位更新。

## 按需使用其他技能

正式规格、任务拆分、独立原型和项目入口，分别在用户调用 `to-spec`、`to-tickets`、`design-ui`、`setup-project-skills` 后处理。已有资料的读取、维护和任务内反馈按当前授权连续进行。

UI 实施参考已有原型、对应 Token、实际组件和 `design-quality`。在正式项目中完成业务；原型与正式代码各按用途维护，Token 沿用用户确认后的版本。
