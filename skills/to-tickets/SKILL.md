# 拆分项目任务

负责把当前目标拆成可接手、可检查的任务。读取用户材料、已有 Issue 与必要项目依据；没有正式 Spec 时在任务中写足必要约束，不要求用户先运行整套技能。

## 设计哲学

以代码实际为主：核实现状时以代码和实际行为为准，文档不一致就沿用现有实现的惯例，完成后列出差异与处理。本次目标仍以用户已确认的需求和规格为准，未实现的新要求不能当作过时文档；从零项目依据目标、约束与必要验证设计。

## 确定当前任务范围

读取当前交付目标、相关规格与共同约定，支持一份或多份 Spec；已有 PRD 或计划足以执行时直接引用。默认只细拆近期准备推进的范围，远期保留概述、依赖和待解问题，不一次铺开全产品的细节任务。能力边界不清时按需使用 `to-spec` 或等价梳理，明确的小改动不补全套文档。

## 设计与实施的前置条件

核对当前范围的业务含义与已定方案是否一致；发现缺口时调查、使用可用的 `domain-modeling` 或自行补齐业务梳理，影响整体方案的变化先更新相应依据。暂不能确定的内容写成有明确产出的调查或设计任务，不把依赖它的实现标为已可执行。

**拆设计任务不要求设计成果已经完成。** Token 说明、设计板和环境准备均可直接列为前置任务，页面效果与必要交互在设计板中展示。拆页面开发任务时引用足够支持本次实现的设计依据；尚缺设计时先列设计任务，将依赖它的开发任务标为受阻，已有依据足够的小改动直接复用。

前端环境准备沿用已定技术栈与组件来源。设计板或页面需要使用 shadcn 时，按其 Skill 安排必要准备，已有配置直接复用。只拆任务不自动初始化项目、制作设计板或实施页面。

## 写成可接手的 Issue

标题写要达成的结果。正文按任务大小保留：

- **目标与范围**：问题、期望行为、包含与排除的内容。
- **局部设计与依据**：必要的输入输出、接口、字段、状态与异常，引用所属 Spec、相关章节及适用的共同约定；无 Spec 时引用足够的原始需求。UI 任务引用已有设计、Token 和组件源码，并说明直接复用什么。
- **验收方法**：具体输入、操作、可观察结果及重要失败场景；按风险选择检查，不以“完成模块”或“构建通过”代替功能验收。
- **关联与依赖**：所属阶段与规格、实际阻塞项、跨规格依赖及其解除证据；区分可开始与仍受阻的任务。跨能力的公共改动明确负责人及受影响规格。
- **当前进展**：执行中维护负责人、结果、阻碍和实际分支、提交或 PR。

写到未读过聊天的执行者能开始工作并判断结果即可，不预先冻结所有代码写法。影响目标或整体方案且无法调查解决的用户选择，说明推荐与影响后澄清。

## 拆分与维护

优先按可观察的端到端结果组织任务，必要的公共准备先行；只需局部交付时沿用当前范围。按可独立检查的结果拆分，普通步骤留在 Issue 内；需要独立推进或验收时才拆子 Issue。父子关系表示所属目标，阻塞关系决定顺序，检查遗漏、重复、循环依赖与共享修改冲突。平台支持时使用原生关系，否则明确链接。

只要求讨论时交付草稿；已要求生成任务时沿用项目跟踪方式，无约定时使用已确定的 GitHub 仓库，没有 GitHub 则用 `docs/issues/<任务标识>.md`。远端不可用时标明待发布，创建结果不明先读回再重试。

Issue 正文维护当前要求与局部设计，评论记录关键取舍、阻碍和交付证据；变更先维护对应规格或共同约定，再同步所有受影响任务；不让多个 Issue 各自保存冲突的公共定义。实际交付后回链分支、提交或 PR 与验收结果，不把任务创建或代码提交当作已经验收。
