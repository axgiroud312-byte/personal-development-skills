# 把总体方案深化为可执行任务

Issue 承接已经对齐的需求与总体方案，交付明确、可直接执行的任务。本次范围内的目标、边界、关键行为和影响需求的假设，应在编写 Issue 前明确；已有结论直接沿用。只有原始需求时，先完成必要的调查与需求对齐，再形成任务。

在确定的需求上研究并补足实施细节，为关键做法取得实际依据。细化时若发现需求仍有歧义、重要假设未确定或需要用户取舍，先回到需求讨论并更新 Spec，明确后再继续编写 Issue。未解决的需求问题保留在讨论或 Spec 中，不作为交给执行者的待定事项。

## 形成足够具体的实施依据

把方案细化到执行者能据此开展工作的程度。需要怎样修改现有模块，数据、界面、接口如何配合，哪些行为需要保留，怎样判断任务完成，都按本任务的实际需要研究和说明。将已经调查清楚的结论、必要位置和依据交给执行者，减少实施时重新推导核心方案。

按可交付成果和真实依赖组织任务，选择合适的粒度、先后关系与协作方式。有关联的前端、后端和存储工作保持完整的业务联系。任务可以等待前置成果，但所需输入、衔接方式和预期结果应明确。

任务结构、详略和表达方式由模型决定。相关 Spec、设计、代码和前置成果在需要的位置引用，共同结论在所属文档维护。形成后的 Issue 应让执行者清楚做什么、怎样落实和做到什么程度，能够在确定的目标内自主完成工程细节。

## 维护任务与结果

讨论请求在聊天交付草稿。生成任务时核对目标仓库和任务功能：远程可用就维护远程 Issue；未配置远程任务平台时，默认使用 `docs/issues/`。

远程暂时访问受阻时，在聊天保留待发布草稿和具体阻碍。写入结果待确认时先读回；从本地迁移到远程后，校对完整内容，再移除对应本地正文。

进展和实际结果放远程评论或本地同一文件。后续出现用户变更需求，或新事实使原方案无法成立时，先对齐变更并更新 Spec 与受影响的任务，再继续相关实施。执行方式沿用 [implement](../implement/SKILL.md)。
