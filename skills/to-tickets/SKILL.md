# 把方案整理成开发 Issue

按**完整功能的垂直切片**组织工作。同一功能的界面、接口、业务逻辑、状态和数据修改集中在一个 Issue，细步骤放在 Issue 内。

Issue 承担开发职责，描述要实现的行为及必要的实施依据。测试、验证、构建和整体审查由用户随后触发的 `implement-pr` 在集成后统一组织，相关计划和结果归整个 PR。

## 1. 读取已有上下文

从当前对话中的方案和决定出发。用户提供 Spec 路径、Issue 编号或链接时，读取完整正文及有关评论。复用已有调查；需要补足实施依据时，再查看相关代码、接口和设计材料。

把各功能共用的模块、接口与前置成果梳理清楚，共同决定保留在原方案或 Spec，Issue 引用与自己有关的部分。

## 2. 先聚合完整功能，再判断是否拆分

先把每个完整功能视为一个 Issue，再根据实际理由调整：

- 同一用户目标、同一操作链路及其相关状态放在一起，覆盖实际涉及的各层实现。
- 多条用户故事可以属于同一个 Issue。新增、编辑、删除等紧密相关操作，可以作为同一功能的内部步骤。
- 脚手架、数据模型、接口接入、页面和局部整理随所属功能一起开发。
- 只有能形成独立功能成果、确实阻塞多个后续功能的共享前置工作，或实施内容明显超出一次独立上下文的承载量时，才另拆 Issue，并说明具体理由。
- 大功能需要拆分时，先划出能贯通实际使用流程的一块，再按功能扩展；前端、后端和数据修改仍随各自的功能一起安排。

例如，“文章收藏”通常是一条 Issue：收藏与取消、按钮状态、接口、持久化和收藏列表一起实现。各层修改和相关状态列在这一条内部。

跨大量模块的机械迁移，可按“加入兼容的新形式 → 分批迁移调用方 → 收起旧形式”组织。先作为一个 Issue 的步骤；规模确实需要多任务时，再按真实依赖拆分。

## 3. 合并检查与依赖

对照完整方案检查覆盖，再检查相邻 Issue 是否能合并：如果它们服务同一功能、共享上下文，而且单独完成只有半个成果，就合并；保留多条的，写清独立成果或依赖理由。以**足够完成目标的最少 Issue**为默认，不设固定条数。

每条 Issue 标出开始开发真正需要的前置任务。前置代码完成并集成后，下游即可开始；可以独立推进的功能保持独立。

向用户展示简洁的编号清单，每项包含标题、完整功能成果和前置依赖。用户要求先讨论拆分时，在反馈后调整；已经授权生成任务时，按当前方案直接发布。

## 4. 发布

- 使用项目已有的任务入口。远程平台按依赖顺序先创建前置 Issue，再建立后续 Issue 的原生阻塞关系；平台缺少此能力时，在正文引用前置 Issue。
- 来源是规格 Issue 时，将开发 Issue 关联为其子任务，并保持原规格作为整体需求记录。沿用项目已有的标签约定。
- 使用本地任务时，一条 Issue 对应一个文件，默认放在 `docs/issues/<feature>/<NN>-<slug>.md`，按依赖顺序编号；已有项目约定优先。
- 更新现有任务时沿用其标识和正文位置；写入结果不明确时先读回，再继续，避免重复建票。

## Issue 结构

```markdown
# 功能标题

## 来源

相关 Spec、设计或上级 Issue 的链接。

## 要实现的功能

从用户角度说明这一条完成后，什么完整行为能够工作。

## 开发内容

- 需要实现的功能行为、交互及相关状态。
- 关键模块、接口或数据如何配合，沿用哪些已确定的决定。
- 有助于实施的内部步骤。

## 前置依赖

确实需要先完成的 Issue；可以立即开始时写“可直接开始”。
```

已建立原生阻塞关系时，正文可省略前置依赖。按需使用各节，以行为、模块职责和接口约定表达开发要求；已有原型中精确表达决定的状态机、类型或数据结构，可保留关键片段及来源。

完成后返回 Issue 清单及关联关系。开发进展记录在各自 Issue，后续执行由用户手动触发 `implement-pr`。
