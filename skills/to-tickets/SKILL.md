# 把总体方案深化为可执行任务

承接 Spec 和当前对话形成的理解，对任务能否实现用户真实需求负责。结合实际项目主动探查，为任务中的关键做法取得依据；调查和讨论围绕仍未弄清且会影响结果的问题展开。只有原始需求时，也根据任务需要形成足够的理解与方案。

假设建立在已对齐的目标上，用户要求、事实和工程判断在容易混淆处说清楚。发现新的需求歧义或重要取舍时，带着调查所得继续与用户讨论；影响整体方向的结论同步回 Spec。

## 形成足够具体的实施依据

把方案细化到执行者能据此开展工作的程度。需要怎样修改现有模块，数据、界面、接口如何配合，哪些行为需要保留，怎样判断任务完成，都按本任务的实际需要研究和说明。将已经调查清楚的结论、必要位置和依据交给执行者，减少实施时重新推导核心方案。

按可交付成果和真实依赖组织任务，选择合适的粒度、先后关系与协作方式。有关联的前端、后端和存储工作保持完整的业务联系。尚不具备执行条件的任务如实说明依赖和待定事项。

任务结构、详略和表达方式由模型决定。相关 Spec、设计、代码和前置成果在需要的位置引用，共同结论在所属文档维护。拆分过程中持续修正理解与做法，让最终任务彼此衔接并能落实需求。

## 维护任务与结果

讨论请求在聊天交付草稿。生成任务时核对目标仓库和任务功能：远程可用就维护远程 Issue；未配置远程任务平台时，默认使用 `docs/issues/`。

远程暂时访问受阻时，在聊天保留待发布草稿和具体阻碍。写入结果待确认时先读回；从本地迁移到远程后，校对完整内容，再移除对应本地正文。

正文随方案变化原位维护；进展和实际结果放远程评论或本地同一文件。相关结论变化时同步受影响的 Spec 和任务，执行方式沿用 [implement](../implement/SKILL.md)。
