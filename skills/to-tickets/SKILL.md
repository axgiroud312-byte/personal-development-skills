# 拆分项目任务

负责把当前目标拆成可接手、可检查的任务。读取用户材料、已有 Issue 与必要项目依据；没有正式 Spec 时在任务中写足必要约束，不要求用户先运行整套技能。

## 设计与实施的前置条件

核对业务含义与已定方案是否一致；发现缺口时调查、使用可用的 `domain-modeling` 或自行补齐业务梳理，影响整体方案的变化先更新相应依据。暂不能确定的内容写成有明确产出的调查或设计任务，不把依赖它的实现标为已可执行。

**拆设计任务不要求设计成果已经完成。** Tokens、设计板、原型和环境准备均可直接列为前置任务。拆页面开发任务时引用足够支持本次实现的设计依据；尚缺设计时先列设计任务，将依赖它的开发任务标为受阻，已有依据足够的小改动直接复用。

前端环境准备沿用已定技术栈与组件来源，未定时参考可用 `design-ui` 主文件；将必要的 shadcn 初始化与 registry 配置安排在设计板、原型或页面编码之前，已有配置直接复用。只拆任务不自动初始化项目、制作原型或实施页面。

## 写成可接手的 Issue

标题写要达成的结果。正文按任务大小保留：

- **目标与范围**：问题、期望行为、包含与排除的内容。
- **局部设计与依据**：必要的输入输出、接口、字段、状态与异常，引用共同方案。UI 任务引用已有设计、Token 和组件源码，并说明直接复用什么。
- **验收方法**：具体输入、操作、可观察结果及重要失败场景；按风险选择检查，不以“完成模块”或“构建通过”代替功能验收。
- **关联与依赖**：所属目标、实际阻塞项、相关任务，以及未解决前置条件的解除方式。
- **当前进展**：执行中维护负责人、结果、阻碍和实际分支、提交或 PR。

写到未读过聊天的执行者能开始工作并判断结果即可，不预先冻结所有代码写法。影响目标或整体方案且无法调查解决的用户选择，说明推荐与影响后澄清。

## 拆分与维护

按可独立检查的结果拆分，普通步骤留在 Issue 内；需要独立推进或验收时才拆子 Issue。父子关系表示所属目标，阻塞关系决定顺序，检查遗漏、重复、循环依赖与共享修改冲突。平台支持时使用原生关系，否则明确链接。

只要求讨论时交付草稿；已要求生成任务时沿用项目跟踪方式，无约定时使用已确定的 GitHub 仓库，没有 GitHub 则用 `docs/issues/<任务标识>.md`。远端不可用时标明待发布，创建结果不明先读回再重试。

Issue 正文维护当前要求与局部设计，评论记录关键取舍、阻碍和交付证据；变更先维护对应权威依据，再同步受影响任务。实际交付后回链分支、提交或 PR 与验收结果，不把任务创建或代码提交当作已经验收。
