# 拆分项目任务

读取需求、项目约定、相关 Spec、已有任务与代码，复用已确认结论。代码和行为说明现状，用户需求决定目标。遇到文档与代码不一致时，沿用现有实现的惯例，并在完成后列出发现的差异。没有正式 Spec 也可拆任务，边界不清时补本项必要信息；只有用户主动调用 `to-spec` 才开启规格流程。

## 划分与安排

按可接手、用户可见的完整结果拆任务，涉及哪些层就贯通哪些层，优先把前端、接口和数据存储连成可用流程；共享基础能力按真实依赖安排。纯后端任务不硬加界面，大范围机械迁移可分成兼容过渡、分批替换与最终整合。普通步骤留在同一 Issue，确需独立推进才拆子任务。细化近期工作，远期保留概述与依赖；小改动可只保留一项。

核对关键成功与失败场景是否有对应实现和结果要求。未决选择标明影响，不在拆分时擅自定案；只询问影响本任务且无法调查解决的选择，不另设概念梳理阶段。只阻塞依赖该选择的工作。

设计、调查或环境准备有独立交接成果时才单列任务，不要求成果已完成才允许拆分。普通查证、可逆选型和顺手配置并入所属任务，由 Agent 在既定约束内决定。UI 任务引用已有设计展示版与确认后的 Token，缺失只记需求和待补位置。列出设计或配置任务不授权执行相应手动技能；用户主动调用 `design-ui` 后先交设计版，确认该版后再提取一份 Token。只暂停真实依赖，不把缺少辅助技能变成新的阻塞。

父子关系表示归属，阻塞关系决定顺序。检查遗漏、重复、循环依赖和共享修改冲突；平台支持时用原生关系，否则用明确链接。

## 写成 Issue

编写前读取 [Issue 模板](references/issue-template.md)，按任务大小裁剪。标题说明结果，正文让没读过聊天的人也能接手：说明目标、想要与不想要的内容、足够的局部设计、预期结果和真实依赖。

已有 Spec 时，Issue 的三问简述本任务边界，链接具体章节；局部方案只写本项新增或不同之处，预期结果指向所负责的场景，不复制字段表、错误表或整套完成标准。没有可用规格时，只在 Issue 补足完成本任务所必需的信息，不扩展成整个项目的规格、术语表或领域模型。写到下一位执行者能定位依据并开始即可，普通步骤留在正文；结果仍须可观察，不能用“完成模块”或“构建通过”代替。

以集中开发为主，必要测试与构建由负责人在授权目标或明确交付阶段收尾安排，详见可用的 `implement`；不为每个 Issue 铺测试任务。设计版的用户确认与 Token 提取按设计约定衔接，已有强制检查保留。

## 发布与维护

只要求讨论时在聊天交付草稿。要求生成任务时，先核对项目已配置的远程仓库、任务功能和读写能力；使用远程 Issue 就只在远程维护，不生成本地副本。未配置远程任务平台时用 `docs/issues/<标识>.md`；已配置但暂时不可用时，在聊天保留待发布草稿并说明阻碍，不静默改用本地任务体系。写入结果不明先读回再重试；从本地迁移到远程时，读回确认内容完整后移除已迁移本地正文，不维持两套。只拆任务不启动环境、设计或开发。

Issue 只放本任务的要求、局部方案、依赖、预期结果和实际进展；远程用正文与评论，本地在同一文件原位更新。不创建总览状态 Issue、术语表、领域说明或额外交接报告。规格或设计变化先更新相应已有依据，再同步受影响任务；中途实现可交回并标记待整体验证，不能把创建或提交当作验收。
