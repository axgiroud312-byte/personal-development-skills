# 拆分开发任务

读取用户提供的材料、已有 Issue 正文和相关讨论；现有 Spec、领域定义和设计决定存在时复用，不要求先执行其他技能。

## 写成可接手的 Issue

标题写要达成的结果。正文按任务大小保留以下内容，让没有看过聊天的 Agent 能接手：

- **目标与范围**：当前问题、期望行为、本次包含与排除的内容。
- **必要设计与依据**：已定约束、执行所需的细节、相关 Spec 或领域定义；引用共同设计，不重复复制。没有 Spec 时直接在 Issue 写足所需信息。
- **验收方法**：输入、操作、可观察的结果，以及重要的失败情况。
- **关联与依赖**：所属总目标、真正阻塞的任务、相关任务；使用实际编号或文件链接。
- **当前进展**：实施时补充负责人、分支或 PR、重要结果和阻碍。

未知项明确写待调查；只补会改变拆分或阻止实施的关键缺口，不要求预先确定每个实现细节。

## 拆分与关联

1. 按可独立检查的结果拆分，避免按文件或技术层机械建任务。普通步骤放 Issue 内；需要独立推进或验收时才拆子 Issue。
2. 父子关系表达“属于哪个目标”，阻塞关系表达“必须等谁”；同属一个父 Issue 不代表要顺序执行。大范围迁移可按兼容准备、分批迁移和收尾组织。
3. 检查遗漏、重复、循环依赖和共享修改冲突。平台支持时使用原生父子及阻塞关系，否则在正文中明确链接。

## 写入与维护

只要求讨论时交付草稿。已要求生成任务时沿用项目跟踪方式；无约定时使用已确定的 GitHub 仓库，没有 GitHub 时用 `docs/issues/<任务标识>.md`，每项一份。目标不明确先核对，远端暂不可用的草稿标明待发布，创建结果不明先读回再重试。

Issue 正文维护当前有效要求，评论记录关键取舍、阻碍和交付结果，不记录每次工具调用。实现后补上关联 PR；共同设计变化时同步相关依据和受影响任务。仅拆分、创建 PR 或提交代码，不表示任务或总目标已经验收。
