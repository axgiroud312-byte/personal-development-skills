# 把方案整理成开发 Issue

按**完整功能的垂直切片**组织工作。同一功能的界面、接口、业务逻辑、状态和数据修改集中在一个 Issue，细步骤放在 Issue 内。

Issue 先交代要改什么，再给出能证明改对了的最小检查。实现者应能独立判断这张票是否完成。开发进展归对应 Issue，最终验证和独立审查结果归 PR 或同一交付记录。

## 1. 读取已有上下文

从当前对话中的方案和决定出发。用户提供 Spec 路径、Issue 编号或链接时，读取完整正文及有关评论。复用已有调查；需要补足实施依据时，再查看相关代码、接口和设计材料。

把各功能共用的模块、接口与前置成果梳理清楚，共同决定保留在原方案或 Spec，Issue 引用与自己有关的部分。

## 2. 先聚合完整功能，再判断是否拆分

先把每个完整功能视为一个 Issue，再根据实际理由调整：

- 同一用户目标、同一操作链路及其相关状态放在一起，覆盖实际涉及的各层实现。
- 多条用户故事可以属于同一个 Issue。新增、编辑、删除等紧密相关操作，可以作为同一功能的内部步骤。
- 脚手架、数据模型、接口接入、页面和局部整理随所属功能一起开发。
- 只有能形成独立功能成果、确实阻塞多个后续功能的共享前置工作，或实施内容明显超出一次独立上下文的承载量时，才另拆 Issue，并说明具体理由。
- 大功能需要拆分时，先划出能贯通实际使用流程的一块，再按功能扩展；前端、后端和数据修改仍随各自的功能一起安排。

例如，“文章收藏”通常是一条 Issue。收藏、取消和列表状态属于同一用户目标，可以用收藏后刷新、取消后再刷新这一条操作链验收。

跨大量模块的机械迁移，可按“加入兼容的新形式 → 分批迁移调用方 → 收起旧形式”组织。先作为一个 Issue 的步骤；规模确实需要多任务时，再按真实依赖拆分。

## 3. 合并检查与依赖

能独立交付的简单改动写一张 Issue 即可。需要多张时，对照方案检查覆盖；相邻 Issue 服务同一功能、单独完成只有半个成果，就合并。保留多张的，写清独立成果或依赖理由。

如果一个结果要跨页面或跨工单才能看到，把整段操作的验收放到负责接通这条流程的那张 Issue。上游票验收自己的成果，并写清交给下游什么。例如，A、B 各有一笔不同的订单。从 A 切到 B，让 A 的旧响应最后返回，页面最终只显示 B 的那一笔。这个场景归接通身份切换和订单列表的票。

有下游工单时，标出它要用的具体能力。上游能力已在当前项目目录可用，并通过直接对应的最小检查，下游即可接手。例如保存接口能写入并读回设置后，设置界面就可以接入。可以独立推进的功能保持独立。

向用户简要说明每张票要交付的完整功能，有前置依赖时列出。用户要求先讨论拆分时，在反馈后调整；已经授权生成任务时，按当前方案直接发布。

## 4. 发布

- 使用项目已有的任务入口。远程平台按依赖顺序先创建前置 Issue，再建立后续 Issue 的原生阻塞关系；平台缺少此能力时，在正文引用前置 Issue。
- 来源是规格 Issue 时，将开发 Issue 关联为其子任务，并保持原规格作为整体需求记录。沿用项目已有的标签约定。
- 使用本地任务时，一条 Issue 对应一个文件，默认放在 `docs/issues/<feature>/<NN>-<slug>.md`，按依赖顺序编号；已有项目约定优先。
- 更新现有任务时沿用其标识和正文位置；写入结果不明确时先读回，再继续，避免重复建票。

## Issue 结构

```markdown
# 功能标题

## 要改什么

说明这项改动让用户或调用方在什么情况下得到什么结果，交代本票负责的范围。

## 怎样算完成

给每个主要行为写出最小检查：做什么，观察什么，什么结果算通过。同一场景可以覆盖多项行为。Spec 已有准确例子时，点明对应场景、预期结果并链接过去。

## 实施约束与依赖（按需）

写出必须沿用的决定和上游实际需要提供的能力。补充接手时用得上的来源链接或步骤。
```

例如，收藏功能可写“收藏文章 A 后刷新，收藏列表中有 A；取消收藏再刷新，A 消失”。如果验收通过接口或自动化测试完成，写清检查的返回值、数据或其他结果。只有真实约束才指定做法；原生阻塞关系已能说明依赖时，正文可省略。

完成后返回 Issue 清单及关联关系。开发进展记录在各自 Issue，后续执行由用户手动触发 `implement-pr`。
