# 拆分开发任务

读取当前需求、相关 Spec、已有任务和必要代码，复用已有结论。没有 Spec 也能拆分明确任务，不为结构完整补规格或其他文档。

用户当前目标与明确约束决定要求，实际代码与行为用于核实现状。文档冲突先查证，默认沿用现有实现惯例，不延续已证实的错误；重要假设说明依据，完成后列出实质差异。

## 按可交付结果拆分

任务应能由下一位执行者接手。按用户可见或可独立交接的结果拆分，普通实现步骤放同一 Issue；涉及哪些层就贯通哪些层，不机械拆成互不衔接的前后端清单。

按真实依赖安排顺序，父子关系只表示归属，不等于阻塞。核对遗漏、重复、循环依赖和共享修改；未决选择只阻塞依赖部分。近期任务写具体，远期保留范围与依赖，不要求一次穷尽细节。

设计、调查和环境准备确有独立成果时才单列任务。普通查证与可逆工程选择由 Agent 自行处理，不另立阶段；会改变目标、明确约束、关键体验或授权的重要选择交给用户决定。

## 写清每项怎么做

读取 [Issue 模板](references/issue-template.md)，写明本任务想实现什么、想要与不想要的结果、具体实施方案、依赖和完成标准。写到能开始实施即可，不逐行规定代码。

已有 Spec 时引用具体章节，只补本项的范围、局部方案和差异，不复制整套接口、字段和完成标准。缺少 Spec 时补足本任务所需信息，不扩成整个项目的规格或领域模型。

方案仍要具体，并在容易混淆处标明哪些是明确要求、哪些是当前工程选择或待核实假设。执行者可以依据新事实调整非强制细节，原位更新受影响方案；不能以优化为由跳过用户明确选择，或通过降低完成标准宣称完成。

UI 任务引用已有原型、对应 Token 和组件来源；缺失只记所需结果与待补位置，不伪造链接。列出任务不授权执行 `design-ui`、`to-spec` 或项目配置流程；用户主动调用设计后，先看原型，满意后再提取 Token。

Issue 的数量不决定测试次数。完成标准描述结果，不为每票附加测试、构建或评审阶段；集中开发与必要验证沿用可用的 `implement`，已有强制检查保留。

## 发布与维护

只要求讨论时在聊天给出草稿。要求生成任务时，核对目标仓库和任务平台的实际可用性；使用远程 Issue 就只在远程维护，未配置远程任务平台时用 `docs/issues/<标识>.md`。已配置但暂时不可用，在聊天保留待发布草稿并说明阻碍，不静默建立本地副本。写入结果不明先读回；迁移到远程并确认完整后移除已迁移的本地正文，不维护两套。

正文维护当前任务要求与方案；进展、重要调整依据、实际结果和未完成项放远程评论或本地同一文件。规格变化更新对应 Spec，再同步受影响任务；不另建状态总览、术语、领域、讨论或总结文档。只拆任务不启动开发。
