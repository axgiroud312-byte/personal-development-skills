# 拆分项目任务

以代码和实际行为判断现状，以用户已确认需求确定目标；文档不一致时沿用现有实现惯例，说明差异与处理。读取已有任务与相关方案，近期细拆，远期保留范围与依赖；没有正式 Spec 也能拆清楚的小任务。

1. 核对目标、关键成功与失败场景及业务含义。能力边界不清时衔接 `to-spec`，业务歧义按需衔接 `domain-modeling`；未决取舍只阻塞依赖它的工作，不能自行定案。
2. 按可接手的结果拆任务，普通步骤留在同一 Issue，确需独立推进时再拆子任务。设计、调查和环境准备可先列任务；缺少设计成果时，将依赖它的页面实现标为受阻。设计交付先 HTML 原型、后对应 Token，不另设验收关卡。
3. 编写前读 [Issue 编写模板](references/issue-template.md)，说明本次想实现什么、想要什么、不想要什么，以及足够实施的接口、字段、状态、异常和预期结果。引用所属规格、公共定义和 UI 依据，代码写法留给执行者。
4. 依赖写清取得哪份成果或代码后才能开始。区分父子归属与阻塞关系，检查遗漏、重复、循环依赖和共享修改冲突；平台支持时使用原生关系，否则明确链接。
5. 只要讨论就交草稿；已要求创建任务时沿用项目平台，无约定时用已确定的 GitHub 仓库，没有 GitHub 则用 `docs/issues/<任务标识>.md`。远端不可用标为待发布，创建结果不明先读回再重试。

预期结果指导集中开发。必要测试、验证与构建由整体负责人在授权目标或明确交付阶段收尾合并安排；不默认每个 Issue 写测试、补覆盖率或打包，已知强制检查照实保留。

正文保持当前要求，评论记录取舍、阻碍与交付事实。变化先更新领域、设计或技术来源，再同步受影响规格和任务；已交回实现仍可待整体验证，代码提交不等于验收。只拆任务不自动初始化工程、制作原型或开发页面。
