# 拆分开发任务

读取用户提供的材料、已有 Issue 正文和相关讨论；现有 Spec、领域定义和设计决定存在时复用，不要求用户先手动调用其他技能。Issue 承接具体任务的局部设计与验收，遵守 Spec 中的整体设计和共同约束。

拆分前核对本次任务涉及的业务定义是否足够且与 Spec 一致。已有定义直接引用；发现新增对象、规则缺失或冲突时，主动使用可用的 `domain-modeling` 或等价梳理补齐，先更新领域依据和受影响的 Spec，再写依赖这些规则的任务设计与验收。只处理本次缺口，不重建已有模型，也不在各 Issue 中另定一套业务含义。

拆具体 UI Issue 前，核对已有设计方向、关键流程、共享 Token、组件选型与交互状态能否支持本次实现。足够时直接引用；不足时衔接可用的 `design-ui` 或等价设计，只补缺口并与 Spec 协调。UI Issue 引用设计规范、Token 源文件、已选组件及 registry、样板代码入口，写清本次实现和可观察验收；已有依据足够的小改动不要求重做整套设计。

前端任务沿用项目依据默认搭配确定的方案，只列本任务需要复用或新增的依赖。拖拽、节点画布、图表等只在确有需求时拆入任务；区分界面共享状态、服务端缓存与消息流职责，同一种能力不在不同 Issue 中另选一套实现。

## 写成可接手的 Issue

标题写要达成的结果。正文按任务大小保留以下内容，让没有看过聊天的 Agent 能接手：

- **目标与范围**：当前问题、期望行为、本次包含与排除的内容。
- **局部设计与依据**：执行所需的输入输出、接口或字段、状态变化、异常处理及相关依据，按任务需要选择。引用共同设计，不重复复制；没有 Spec 时在 Issue 中写足必要约束。
- **验收方法**：用具体输入、操作、可观察结果和重要失败情况说明怎样判断交付；例如重启后仍能读到保存记录。按风险选择检查、测试或真实操作，不把“完成模块”“构建通过”当作功能验收。
- **关联与依赖**：所属总目标、真正阻塞的任务、相关任务；使用实际编号或文件链接。
- **当前进展**：实施时补充负责人、分支或 PR、重要结果和阻碍。

写到未读过聊天的执行者能理解范围、开始工作并判断结果即可，不预先规定所有代码写法。能调查的缺口自行调查；会改变目标或整体方案的用户选择，给出推荐与影响后澄清。阻止实施的未知项标明阻碍和解除条件，必要时安排有明确产出的调查任务，不将其写成已可实施。

## 拆分与关联

1. 按可独立检查的结果拆分，避免按文件或技术层机械建任务。普通步骤放 Issue 内；需要独立推进或验收时才拆子 Issue。
2. 父子关系表达“属于哪个目标”，阻塞关系表达“必须等谁”；同属一个父 Issue 不代表要顺序执行。大范围迁移可按兼容准备、分批迁移和收尾组织。
3. 检查遗漏、重复、循环依赖和共享修改冲突。平台支持时使用原生父子及阻塞关系，否则在正文中明确链接。

## 写入与维护

只要求讨论时交付草稿。已要求生成任务时沿用项目跟踪方式；无约定时使用已确定的 GitHub 仓库，没有 GitHub 时用 `docs/issues/<任务标识>.md`，每项一份。目标不明确先核对，远端暂不可用的草稿标明待发布，创建结果不明先读回再重试。

Issue 正文维护当前有效的任务要求和局部设计，评论记录关键取舍、阻碍和交付结果，不记录每次工具调用。实现后补上关联 PR 和实际验收证据。业务规则变化先更新领域依据，再核对相关 Spec、任务设计与验收；跨模块技术约定变化更新共同设计后同步任务；呈现与交互变化更新设计规范及对应源码，再同步受影响任务与验收。每个决定只维护一份有效正文。仅拆分、创建 PR 或提交代码，不表示任务或总目标已经验收。
