# 把方案拆成可执行任务

读取当前需求、相关 Spec、已有任务和必要代码，让每项任务都能交给下一位执行者。

## 按结果拆分

围绕可使用的功能或可独立交接的成果拆任务。普通实现步骤放在同一 Issue；涉及前端、接口和存储时，把它们连成完整流程。

按真实依赖安排顺序。父子任务表示归属，前置任务提供继续工作需要的成果。近期任务写具体，远期保留范围和依赖。

共享修改明确负责人。普通工程选择由 Agent 根据实际情况处理；影响目标、明确要求、关键体验或授权的重要选择，由用户决定，其余工作继续。

## 写清每项怎么做

使用 [Issue 模板](references/issue-template.md)，写清目标、范围、具体实施方案、依赖和预期结果。

有 Spec 时引用对应需求条目，补充本任务的做法和预期结果；依据来自原始需求时，把信息补到执行者能够开始。用户明确要求、当前工程选择和重要假设在容易混淆处说明。

文档过时或方案需要调整时先查证，保留用户明确要求，更新相关做法并说明依据。

UI 任务引用已有原型和对应 Token，待制作的部分如实标明。独立设计、规格或项目入口工作，在用户调用对应技能后执行。

完成标准写实际结果。开发按 `implement` 集中推进，普通检查由目标负责人在收尾统一安排。

## 放到正确位置

讨论请求在聊天交付草稿。生成任务时，先核对目标仓库和任务功能是否可用：远程可用就维护远程 Issue；未配置远程任务平台时，使用 `docs/issues/<标识>.md`。

远程暂时访问受阻时，在聊天保留待发布草稿和具体阻碍。写入结果待确认时先读回；从本地迁移到远程后，校对完整内容，再移除对应本地正文。

正文维护当前要求和方案；进展、重要调整、实际结果和剩余事项放远程评论或本地同一文件。跨任务的方案变化先更新所属 Spec，再同步相关 Issue。
