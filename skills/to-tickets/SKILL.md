# 拆分项目任务

负责把当前目标拆成可接手、有清楚结果的任务。读取用户材料、已有 Issue 与必要项目依据；没有正式 Spec 时在任务中写足必要约束，不要求用户先运行整套技能。

**以代码实际为主。** 核实现状时以代码和实际行为为依据；文档不一致就沿用现有实现的惯例，完成后列出发现的差异与处理。用户明确提出或已确认的新需求决定本次目标，不能因为尚未实现而忽略。

按当前范围引用 PRD、相关 Spec 与共同约定，默认细拆近期准备推进的工作，远期保留概述与依赖。能力边界不清时按需衔接 `to-spec`；明确的小改动可用一个 Issue 或直接实施，不强制先写规格。

## 设计与实施的前置条件

核对业务含义与已定方案是否一致；发现缺口时调查、使用可用的 `domain-modeling` 或自行补齐业务梳理，影响整体方案的变化先更新相应依据。未确认的业务取舍标明待定及影响，不能在拆任务时自行定案；调查或设计写清产出，仅将依赖未决内容的实现标为受阻。

**拆设计任务不要求设计成果已经完成。** 设计由 `design-ui` 先做设计板，再提取 Token；可以作为一个任务，确需拆开时标明这个先后依赖。环境准备按需先行。拆页面开发任务时引用足够支持本次实现的设计依据；尚缺设计时先列设计任务，将依赖它的开发任务标为受阻，已有依据足够的小改动直接复用。设计预览只交付 HTML 与 Token，不另设测试或验收任务。

前端环境准备沿用已定技术栈与组件来源。设计板或页面需要使用 shadcn 时，按其 Skill 安排必要准备，已有配置直接复用。只拆任务不自动初始化项目、制作设计板或实施页面。

## 写成可接手的 Issue

写任务前轻量核对本次 Spec 或原始需求的关键成功与失败场景是否已有对应实现和预期结果；缺口补功能范围或记录待定，不把每个场景自动拆成测试任务，不另建覆盖率或测试矩阵文档。

编写或更新 Issue 前读取 [Issue 编写模板](references/issue-template.md)。标题写要达成的结果，按任务大小保留目标与范围、局部设计和依据、预期结果、真实依赖及执行进展；已有项目模板可映射使用，小修可合并成短正文。

规格和公共规则通过链接引用，局部接口、状态与异常写到能实施；UI 任务引用实际设计板、Token 和组件源码。依赖写清可取得的代码或成果，结果要求写具体输入、操作与表现，不用“完成模块”或“构建通过”代替目标。

默认不为每个 Issue 加“编写单测、集成测试、端到端测试、补覆盖率、构建打包”等步骤或子任务。必要验证由主 Agent 在本次授权开发目标收尾合并安排；不是每个 Issue、提交或批次结束都验证一遍。只有确实需要独立协调的收尾工作才另建任务，用户明确要求和已有强制检查如实保留，不擅自关闭。

写到未读过聊天的执行者能开始工作并理解预期结果即可，不预先冻结所有代码写法。只澄清无法调查解决且影响目标或整体方案的用户选择。

## 拆分与维护

按可独立交付的结果拆分，普通步骤留在 Issue 内；需要独立推进时才拆子 Issue。父子关系表示所属目标，阻塞关系决定顺序，检查遗漏、重复、循环依赖与共享修改冲突。平台支持时使用原生关系，否则明确链接。

只要求讨论时交付草稿；已要求生成任务时沿用项目跟踪方式，无约定时使用已确定的 GitHub 仓库，没有 GitHub 则用 `docs/issues/<任务标识>.md`。远端不可用时标明待发布，创建结果不明先读回再重试。

Issue 正文维护当前要求与局部设计，评论记录关键取舍、阻碍和交付证据；变更先维护对应领域、设计或技术依据，再同步受影响规格与任务，避免各自保存冲突的公共定义。中途可交回已实现代码并注明待整体验证，实际做过检查才记录结果；不把任务创建或代码提交当作已经验收。
