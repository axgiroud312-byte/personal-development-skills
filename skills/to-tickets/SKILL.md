# 拆分项目任务

读取需求、相关 Spec、已有任务与代码，复用已确认结论。代码和行为说明现状，用户需求决定目标；文档冲突时沿用现有惯例并记录差异。没有正式 Spec 也可拆任务，边界不清才按需衔接 `to-spec`。

## 划分与安排

按可接手、用户可见的完整结果拆任务，优先把前端、接口和数据存储连成一条流程；共享基础能力按真实依赖安排，不机械分成互不衔接的前后端任务。普通步骤留在同一 Issue，确需独立推进才拆子任务。细化近期工作，远期保留概述与依赖；小改动可只有一项或直接实施。

核对关键成功与失败场景是否有对应实现和结果要求。业务含义不清时调查或按 `domain-modeling` 梳理；未决业务选择标明影响，不在拆分时擅自定案。只阻塞依赖该选择的工作。

设计、调查和环境准备可以先列任务，写清产出及后续取得方式；不要求成果已经完成才允许拆分。UI 任务引用足够的原型、Token 与组件源码，缺少时标明设计依赖；原型先完成 HTML 再提取 Token。指定组件的准备按相应 Skill，复用现有配置。

父子关系表示归属，阻塞关系决定顺序。检查遗漏、重复、循环依赖和共享修改冲突；平台支持时用原生关系，否则用明确链接。

## 写成 Issue

编写前读取 [Issue 模板](references/issue-template.md)，按任务大小裁剪。标题说明结果，正文让没读过聊天的人也能接手：说明目标、想要与不想要的内容、足够的局部设计、预期结果和真实依赖。

规格和共同规则引用来源；局部接口、字段、状态及异常写到能实施，代码写法留给执行者。结果用具体输入、操作和表现说明，不以“完成模块”或“构建通过”代替。

以集中开发为主，必要测试与构建由负责人在授权目标或明确交付阶段收尾安排，详见可用的 `implement`；不为每个 Issue 铺测试任务。设计原型做好即交付，已有强制检查保留。

## 发布与维护

只要求讨论时交付草稿；要求生成任务时沿用项目平台，无约定则用已确定的 GitHub 仓库，没有 GitHub 可用 `docs/issues/<标识>.md`。只拆任务不启动环境、设计或开发。远端不可用时标明待发布，写入结果不明先读回再重试。

正文维护当前要求与局部方案，评论记录取舍、阻碍及实际交付。变化先更新所属业务、技术或设计来源，再同步受影响任务；中途实现可交回并标记待整体验证，不能把创建或提交当作验收。
