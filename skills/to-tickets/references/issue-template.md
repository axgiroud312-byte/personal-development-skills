# Issue 编写模板

写到没读过聊天的人也能接手并核对结果。按任务大小删减或合并；明确的小修用短正文即可，已有平台模板直接映射。删除无关占位项，不虚构编号、负责人、链接或完成状态。

- **问题／目标：** <要解决什么，完成后行为如何改变>
- **本次包含：** <这项任务负责的交付>
- **本次不包含：** <必要边界，避免顺带扩展>
- **依据：** <所属 Spec 或原始需求、相关章节与共同约定>

## 局部方案

说明足够实施的输入输出、接口、字段、状态变化和异常处理；引用已有公共定义，不把同一规则复制到多个 Issue。具体代码写法由执行者判断。

- <需要修改或复用的模块、接口和数据>
- <与前后置任务的契约；兼容现有调用者的要求>
- <UI 任务的设计板、Token 和组件源码，以及直接复用的内容；核对按钮行为、权限与真实接口／状态规则，区分模拟与已接通>
- <已知现状与本次目标的差别>

未确认的业务选择明确标为待定，不能在拆任务时自行拍板。只让依赖该选择的工作受阻。

## 关联与依赖

- **所属目标／阶段：** <属于哪个结果；不等于阻塞依赖>
- **前置条件：** <必须先具备的成果或代码，标明真实任务链接>
- **解除证据：** <怎样确认前置成果可用，不能只凭“已经完成”的消息>
- **可推进范围：** <当前可以开始的部分与仍受阻的部分>
- **共享修改：** <确有冲突时说明归属与协作方式>

## 验收方法

| 前提／输入 | 操作 | 预期可观察结果 |
| --- | --- | --- |
| <正常数据> | <关键操作> | <具体结果> |
| <重要错误或边界> | <复现步骤> | <提示、状态保留或恢复结果> |

按风险选必要检查。UI 要核对实际操作与必要状态，涉及接口或数据的任务检查真实契约；“模块已完成”“测试通过”“构建通过”不能单独充当业务验收。

## 执行与交接（有实际信息时填写）

- **当前状态：** <待开始／受阻／执行中／待评审等，以项目约定为准>
- **执行位置与分工：** <真实目录、分支、负责人或主 Agent 的交接要求>
- **交付：** <实际改动、提交或 PR；本地交付不强行创建远端记录>
- **验证：** <做过的操作、结果和证据；模拟与未验证部分分开>
- **剩余问题：** <尚未完成或需接手的内容>

正文保持当前要求；评论按平台习惯记录关键取舍、阻碍和交付证据。代码提交不等于用户验收，子任务结束不等于总目标完成。

## 按任务类型调整

| 类型 | 主要产出与判断方式 |
| --- | --- |
| 调查 | 明确问题、证据、结论及尚不能确定的部分，说明会影响什么决定 |
| 设计 | 先完成可查看的设计板，再提取采用的 Token；需要拆开时明确依赖 |
| 环境准备 | 实际可用的配置、启动方法或共享基础，不把安装成功当成业务实现 |
| 功能／修复 | 可观察的行为变化、必要验证及对现有功能的影响 |

## 小任务示例

**标题：允许分页选择 100 条**

依据当前代码，默认仍为 50 条，只将允许值从 20、50 扩展为 20、50、100，返回类型和错误处理沿用现有实现。README 的默认值与代码不符时同步说明。

验收分页大小的解析：省略参数仍采用 50，允许指定 100，原有 20、50 仍合法，无效值按原约定拒绝。实际返回条数取决于匹配数据，不能要求每页必满。说明实际验证结果即可，无需另建 Spec 或子任务。
