# 从需求交付一个 PR

需求已明确就直接实现。已有规格或工单时，只读与本次改动有关的决定、验收场景和依赖。普通本地修复可直接在当前分支完成。

## 实现与交接

核对项目约定、当前改动、目标分支和已有 PR。在同一项目目录和一条交付分支上工作，优先沿用原 PR。保留用户已有的修改与暂存状态，只交付属于本次任务的改动。若复用分支会夹带无关提交，先理清交付范围。

主 Agent 可自行实施。同一时间由一人写项目文件，只读调查可并行。确有下游接手时，先在当前项目验证它要用的能力，交接入口和结果。已有工单只补进展或剩余事项。中断后从实际差异和上次验证结果接续。

## 选最能抓错的那一测

结合实际写法想一个具体错法：即使代码错了，哪项普通检查仍会通过？从正常使用入口选一个能区分对错的最小检查，优先运行已有检查，缺口再补。例如页面定时刷新时，把响应持续延后到超过刷新间隔，观察用户最终能否看到数据。只看到请求成功，还漏掉了页面一直加载的错法。

简单改动验到目标行为即可。若检查失败，先修根因，用同一场景复验；若改动牵连其他行为，再扩到受影响范围。照常运行用户或项目要求的检查。在 PR 里引用审查者能打开的验收场景并写下实测结果。场景只在私聊里时，用一句操作和结果让审查者能复验。若结果依赖提交外的改动，验证实际提交或注明尚未验证的范围。

## 审查与交付

主 Agent 核对目标基线到最终提交的完整差异，确认应交付的文件均已纳入。请新的独立上下文只读审查正确性、接口和回归，给出能触发问题的操作、位置和后果。核实意见，修复本次引入或阻碍交付的问题，按影响复验。无法独立审查时，完成自查并说明缺项。

在授权内推送并创建或更新同一个 PR，关联已有资料。交付依赖远程检查时跟到结果，说明未完成或受阻事项，由用户决定合并。
