# 协调开发并交付一个 PR

主 Agent 负责理解目标、编排任务、整合代码和完成交付。每个任务交给一个新建、独立上下文的子 Agent 集中实施；所有任务通过一个集成分支和一个 PR 交付。

沿用用户已作出的决定和授权，自主处理常规工程选择，连续推进到授权目标完成。明确的小任务直接按一个任务走同样机制。

## 1. 核对目标与任务关系

读取项目指令、实际代码、相关 Spec 和开发 Issue，核实已完成与剩余工作。Spec 沿用远程方案 Issue 或 `docs/specs/`；开发 Issue 沿用远程任务或 `docs/issues/<feature>/<NN>-<slug>.md`，不复制另一份正文。

按可交付的完整功能垂直切片聚合任务，覆盖这项功能所需的相关层。沿用已经整理好的 Issue；明确的小需求也可以直接作为一个任务。

开发 Issue 描述目标、实施细节、预期行为、真实依赖和开发进展。测试用例、验证计划与结果集中在整个 PR 的交付记录中维护。

依据代码、接口和数据关系建立简洁依赖图。需要使用上游实际产物才是依赖；同改共享文件时，安排先后或明确负责人。

必要时先派探索子 Agent 查明跨任务共用的接口和约束，输出短资料供实施者读取。已有足够资料时直接开发。

发现新事实需要调整需求或方案时，说明证据与建议，在现有授权范围内完成必要讨论和资料修订；决定明确后继续受影响任务，其他可独立工作持续推进。

## 2. 建立集成分支并记录进度

从确认的目标基线建立一个 integration branch；已有本次集成分支或 PR 时继续使用。核对当前改动和工作区归属，保留用户与其他执行者的工作。

沿用已有 PR 正文或项目交付记录，简要记录任务状态、worktree/branch、提交与合入位置。首次整合出实际改动后可建立本次唯一的草稿 PR，把进度集中到这里；已有合适记录时直接引用。

任务状态区分待实施、实施中、待整合、已整合和受阻。子 Agent 报告完成只表示待整合；上游代码已经合入 integration branch，才解锁下游，Issue 是否关闭不影响调度。

恢复工作时，对照记录核实实际分支、提交和集成状态，补齐遗漏的合入信息。继续尚未完成的工作，保留未整合成果；需要重新派工时仍使用全新上下文。

## 3. 为每个任务新建实施者

每次派工都创建新的独立上下文子 Agent，例如设置 `fork_turns: "none"`，仅提供本任务材料。审查后的修复也使用新建实施者。

给实施者分配独立 worktree 和任务分支，从已包含其全部依赖的当前 integration branch 创建。只有依赖已整合且写入范围可分离的任务并行；共享文件由明确负责人修改，或安排串行，避免多个执行者同时改同一工区。

派工说明只交付当前任务所需的材料：

- 目标、范围、预期行为，以及相关 Spec、Issue 和必要共享资料的链接。
- 仓库与 worktree 路径、任务分支、起始集成提交，以及已合入的依赖。
- 负责的文件或模块、必须遵守的接口、与其他并行任务的写入边界。
- 完成后回交分支和提交、实际改动、重要接口调整，以及剩余开发事项或阻塞。

实施者自行读取必要材料，集中完成开发。遇到确实阻塞开发的错误，做足以定位与修复的小范围排查；测试、必要构建和验证由主 Agent 在集成后统一组织。

实施者将开发成果提交在自己的分支，交回主 Agent 统一整合。环境缺少独立子 Agent 能力时，如实说明具体限制并保留当前进度。

## 4. 串行整合并解锁后续任务

主 Agent 核对回交提交、任务范围、接口变化与剩余开发事项，再按依赖顺序串行合入 integration branch。

检查共享接口是否一致，解决常规整合冲突。涉及功能实现取舍或遗漏开发时，向新的独立上下文实施者派发明确修复任务；更新受影响任务的交接资料和依赖。

确认提交已进入集成分支后更新状态，解锁依赖它的任务。待整合或受阻的任务保持真实状态，其余就绪任务继续推进。

开发 Issue 仅补充实际开发成果、重要调整和剩余事项；测试与验证内容留在统一交付记录或最终 PR 中。

## 5. 在集成结果上统一验证

全部开发任务整合后，由主 Agent 围绕实际行为、跨任务接口和改动影响组织必要测试、构建与验证，优先复用项目已有检查，按实际需要补充，完成项目要求的必要项。

将验证对象的集成提交、实际执行的检查与结果、未能验证的内容集中记录。根据实际改动选择范围，足以确认本次目标后继续交付。

发现失败先定位根因，将需要的开发修复交给新的独立上下文实施者。修复合入后按影响重新验证，更新结果对应的提交。

## 6. 用全新上下文审查整个 PR diff

集成结果完成必要验证后，新建一个独立上下文审查者，例如设置 `fork_turns: "none"`。提供目标、相关资料、目标基线和当前集成提交，让它审查整个 PR diff，并自行读取必要上下文。

审查者重点寻找正确性、集成遗漏、接口不一致和回归风险，返回具体位置、影响及依据；没有发现也如实说明。

主 Agent 核实发现，每项需要的修复交给新建独立上下文实施者；可将同一根因的相关问题合为一个修复任务。修复串行整合后，按影响补做验证并让审查者复核；范围显著变化时重新整体审查。

最终记录明确当前集成提交、针对该版本完成的验证与复核，以及仍存在的限制。

## 7. 交付一个 PR

沿用已有授权，提交、推送并创建或更新一个覆盖全部任务的 PR，关联 Spec 与全部开发 Issue。说明解决的问题、实际变化、统一验证与审查结果，以及明确的剩余事项。

必要验证和审查完成后，将草稿 PR 标为可审阅，交给用户决定合并。存在未完成或受阻事项时，保留草稿并说明实际进度。

确认任务成果已整合、没有待保留改动后，清理本次不再需要的任务 worktree；保留集成分支、PR 和恢复工作所需的状态。向用户说明交付位置、实际结果和需要其关注的决定。
