# 连续完成整套开发

负责已授权总目标、阶段安排、跨规格依赖、整合与交付，单项实施按 `implement` 或等价方法完成。读取现有计划、规格索引和进度，只补当前执行缺口；完成一个阶段不代表整个目标完成。

先确定当前阶段的可观察交付结果，准备足够的目标、边界、共同接口与必要界面设计后实施；已有决定与小改动直接复用。远期规格和页面不必全部定稿，不阻塞已经具备条件的任务。业务或设计依据不足时按需衔接 `domain-modeling`、`to-spec`、`design-ui` 或完成等价梳理；关键技术未知先调查，不把假设当成已定方案。

## 设计哲学

以代码实际为主：核实现状时以代码和实际行为为准，文档不一致就沿用现有实现的惯例，完成后列出差异与处理。本次目标仍以用户已确认的需求和规格为准，未实现的新要求不能当作过时文档；从零项目依据目标、约束与必要验证设计。

## 安排任务与职责

1. 核对已授权总目标、当前阶段及各自完成标准、现有进度、交付分支和本地修改、推送或 PR 等要求。保留后续范围与依赖，沿用已有授权与项目约定。
2. 复用已有 Issue；按 `to-tickets` 或等价方法只补足当前准备推进的任务，引用对应规格与共同约定。设计、调查可先列为前置任务，跨规格依赖明确解除证据；父子关系用于汇总，真实依赖决定顺序。
3. 明确公共设计、共享源码和环境准备的维护者。设计成果沿用 `design-ui` 的约定；使用 shadcn 时按其 Skill 统一完成必要准备。把 Token 说明、设计板、实际配置和共用源码交给执行者，避免各自初始化或维护一套实现。
4. 保护原工作区，明确实际工作位置与整合分支；独立任务确有并行收益且环境支持时隔离并委派，否则顺序完成。检查循环依赖与共享修改冲突。

## 持续实施与整合

5. 选择前置条件满足的任务，交给执行者目标、所属 Spec、适用共同约定、必要关联规格、实际目录、验收要求及回交位置；不要求每项任务读取全项目全部文档。子任务负责代码与必要验证；PR、整体状态和临时工作树清理由主 Agent 负责，另有明确分配时按分工处理。
6. 核对返回的实际代码、提交或工作树、验证证据和未完成项后整合。依赖公共改动的任务取得对应代码后才解除阻塞，不能只凭“已完成”的消息继续。
7. 更新任务的当前要求、结果、阻碍及分支、提交或 PR。发现业务、技术或设计变化时，维护对应规格、共同约定和全部受影响任务；主 Agent 核对跨规格一致性，公共决定由明确负责人维护；无法调查解决且改变目标或整体方案的用户选择，说明推荐与影响后澄清。
8. 持续推进已可执行任务；阶段结果核对后，依据新事实细化并推进授权范围内的下一阶段，不逐任务、逐 Spec 或逐阶段询问是否继续。真实阻碍只暂停受影响部分；重复失败且没有新证据时报告阻碍。未完成全部授权目标时，不以一个阶段交付代替总目标完成。

## 整体交付与清理

在当前交付边界核对跨任务、跨规格的接口、数据和真实使用流程；各阶段完成后做必要整合验收，全部授权目标完成时再核对总标准。UI 通过真实浏览器或目标桌面入口操作，并核对有关视觉参考。测试与审查按项目设置和风险选择，已有充分结果不重复验证；需要试用的成果及时保存，不为流程额外构建。

按授权统一交付本地结果或提交推送；PR 按可审查、可验证的有界改动组织，依照项目约定维护一个或多个 PR，可先建 Draft。Spec、Issue、PR 与发布不要求一一对应，不把完整大项目默认压进一个长期 PR，也不机械要求每项任务各建 PR。核对目标分支、依赖和远端覆盖，跨 PR 的公共改动先整合再推进依赖；只要求 PR 时不自动合并或关闭目标。

清理由主 Agent 统一安排：先确认临时工作树中需保留的改动已整合并推送，PR 交付时已被实际 PR 覆盖；将试用成果与恢复材料保存到清理范围以外并确认可访问。核对路径、归属及本任务进程后清理可丢弃产物与临时工作树，保留主工作区、他人修改和 PR 远端分支。本地交付或未推送的代码继续保留，核对并报告实际残留。

按项目约定维护唯一状态入口，由主 Agent 汇总任务事实；区分设计完成、代码修改、分支可试用、主线可用和用户验收。交付当前阶段与总目标的完成情况、规格和任务与提交或 PR 的对应关系、试用入口、验证结果、后续范围与剩余阻碍及清理情况。用户要求“做完后解释”时在整体交付后使用可用 `explain-work` 或依据证据自行说明，不在每个子任务后打断开发。
