# 连续完成整套开发

负责总目标、任务依赖、整合与整体交付，单项实施按 `implement` 或等价方法完成。直接使用已有需求与进度，只补执行缺口，不要求先运行整套技能。

完整开发先完成本次整体方案与必要界面设计，再进入业务实现；已有决定与小改动直接复用。业务或设计依据不足时按需衔接 `domain-modeling`、`to-spec`、`design-ui` 或自行完成相应梳理，不把未决的关键含义当成已定方案。

## 设计哲学

以代码实际为主：遇到文档与代码不一致时，沿用现有实现的惯例，并在完成后列出发现的差异（文档描述、代码实际及本次处理）。区分现有行为与本次变更目标；用户明确要求的新行为和修复仍按当前任务处理。

## 安排任务与职责

1. 核对总目标、整体完成标准、当前进度、交付目标分支和本地修改、提交推送或 PR 等交付要求，沿用已有授权与项目约定。
2. 复用已有 Issue；需要拆分时按 `to-tickets` 或等价方法补足任务。设计与调查可先列为前置任务，依赖成果的实现明确阻塞条件；父子关系用于汇总，真实依赖决定顺序。
3. 明确公共设计、共享源码和环境准备的维护者。设计成果沿用 `design-ui` 的约定；使用 shadcn 时按其 Skill 统一完成必要准备。把 Token 说明、设计板、实际配置和共用源码交给执行者，避免各自初始化或维护一套实现。
4. 保护原工作区，明确实际工作位置与整合分支；独立任务确有并行收益且环境支持时隔离并委派，否则顺序完成。检查循环依赖与共享修改冲突。

## 持续实施与整合

5. 选择前置条件满足的任务，交给执行者目标、依据、实际目录、验收要求，以及提交和回交位置。子任务负责代码与必要验证；PR、整体状态和临时工作树清理由主 Agent 负责，另有明确分配时按分工处理。
6. 核对返回的实际代码、提交或工作树、验证证据和未完成项后整合。依赖公共改动的任务取得对应代码后才解除阻塞，不能只凭“已完成”的消息继续。
7. 更新任务的当前要求、结果、阻碍及分支、提交或 PR。发现业务、技术或设计变化时维护相应权威依据与受影响任务，公共决定由明确负责人维护；无法调查解决且改变目标或整体方案的用户选择，说明推荐与影响后澄清。
8. 持续推进已可执行任务，不在每项结束后询问是否继续。真实阻碍只暂停受影响部分；重复失败且没有新证据时报告阻碍，不反复重试同一步。

## 整体交付与清理

核对跨任务接口、数据和真实使用流程，对照整体标准完成必要验收。UI 通过真实浏览器或目标桌面入口操作，并核对有关视觉参考。测试与审查按项目设置和风险选择，已有充分结果不重复验证；需要试用的成果及时保存，不为流程额外构建。

按授权统一交付本地结果或提交推送；PR 交付通常维护一个覆盖整体任务的 PR，可先建 Draft 后持续更新。项目已有逐项 PR 约定时沿用，不重复创建同等 PR。核对远端提交与覆盖范围；只要求 PR 时不自动合并或关闭目标。

清理由主 Agent 统一安排：先确认临时工作树中需保留的改动已整合并推送，PR 交付时已被实际 PR 覆盖；将试用成果与恢复材料保存到清理范围以外并确认可访问。核对路径、归属及本任务进程后清理可丢弃产物与临时工作树，保留主工作区、他人修改和 PR 远端分支。本地交付或未推送的代码继续保留，核对并报告实际残留。

按项目约定维护唯一状态入口，由主 Agent 汇总任务事实；区分设计完成、代码修改、分支可试用、主线可用和用户验收。最终交付任务与提交或 PR 的对应关系、试用入口、验证结果、剩余阻碍及清理情况。用户要求“做完后解释”时在整体交付后使用可用 `explain-work` 或依据证据自行说明，不在每个子任务后打断开发。
