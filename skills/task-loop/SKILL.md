# 多循环分析与优化

仅由用户主动调用；普通分析、修复或其他技能不能代为启动。本次已授权的循环可以持续推进，但不自动授权调用其他手动入口；沿用用户已定的设计确认与开发收尾安排。

先弄清什么叫做好，再尝试、检查、改进；保留有用的发现和不同方案，最后交付证据最充分、最符合目标的结果。

这里的“方案”可以是一种解释、一项判断、一份计划、一段代码或一个设计，不限于软件开发。

## 一、先确定起点和终点

根据用户要求和已有上下文，简要确定：

- **目标与交付物**：解决什么问题，最终交付什么。
- **验收规则**：必须满足什么，主要比较什么，哪些约束不能违反。
- **初始方案**：复用已有成果；没有时，建立一个可检查的初步解释或最小方案。
- **预算与能力**：本次能使用哪些资料和工具，可承担多少尝试、成本和验收。

先按验收规则检查初始方案，作为后续比较的基线。缺少证据就标记未知，不编造初始成绩。

优先使用用户给定的预算；没有时，自行设定与任务规模相称的有限探索范围，为最终验收和交付留出资源。试验与正式验收分开计数，失败的尝试同样计入消耗。

已知信息不要重复问。非关键、可逆的缺口可说明假设后继续；涉及必要授权或决定结果的重大歧义时再确认。验收规则不能为了迁就当前方案而偷偷降低；需求或规则确实变化时，记录变化并重新比较相关方案。

## 二、三个循环配合工作

三个循环不是固定做三遍，也不是必须依次执行的三个阶段。根据当前证据决定何时试验、何时验收、何时换路。

### 循环 A：试验改进——弄清怎样才有效

**查看当前方案和历史反馈 → 提出假设 → 按需查证或试验 → 修改方案 → 继续试验或提交验收。**

每次先明确一个值得解决的问题，以及什么结果会支持或否定当前判断。例如：“问题可能来自 X；改变 Y 后，预期 Z 改善；用 W 检查。”

自行选择能影响下一步决策的方法：查找原始资料、检查数据、计算、构造样例、运行测试、制作小原型、寻找反例，或获取真实反馈。选择什么、做多少、先修改还是先试验，由问题和预算决定，不强行套固定顺序。

观察实际结果，再修改解释、方案或成品。发现假设错误也是有效进展；仅仅换种说法、反复赞同自己不算新证据。

可以多次试验后再提交，也可以证据已经足够时直接提交。不要把小样例成功、自己的打分或模拟用户反馈当成正式通过。

### 循环 B：验收选择——确认这版到底怎样

**固定一个可恢复的版本 → 按既定规则验收 → 记录结果 → 更新方案档案 → 选择下一轮起点。**

验收面向完整目标，不只检查刚修改的部分。检查硬性要求、主要效果、已有功能是否退步，以及关键边界条件。不同方案尽量使用相同条件比较；有明显波动时重复检查，不凭一次偶然结果宣布更好。

能使用实际测试、可靠数据、外部评估或真实反馈，就使用。适合量化的用指标；不适合量化的用明确标准和证据，不编造精确分数。

**固定规则不等于独立验证。** 只有自身复核时，标注“自评”及其局限；结果未经实测、独立核验或用户确认，不冒称已获得这些验证。

试验和验收用途不同，结果分开记录。条件允许时，保留未用于反复调优的样例或来源做最后检查；不能靠窥探受限验收材料、删除失败项或更改规则制造通过。

每次正式验收都保存方案、结果和失败原因。按用户目标更新最佳已验收版本，同时保留各有优势的备选。从当前方案、历史方案或其他路线中选择下一轮起点，不默认最新版本最好。

允许暂时沿着表现较差但有依据的方向继续探索；不要因此覆盖最佳已验收版本。任何修改、借鉴或合并后的新版本，都需要重新验收。

### 循环 C：路线交流——避免困在一个想法里

**分别探索不同思路 → 在验收节点比较成果 → 借鉴、替换或组合 → 各路线继续试验与验收。**

存在多种合理解释或解法，或者当前方向停滞时，建立少量真正不同的路线。从共同基线和共同验收规则出发，让各路线分别保留自己的方案、试验与失败历史。

区别应在假设、原理、结构或取舍上，而不是同一答案换几种措辞。例如，分别尝试简化步骤和改变任务顺序，而不是只调整措辞。

预算和工具允许时交给多个 Agent 分别探索；否则由一个 Agent 依次尝试并分别记录，明确这是顺序探索，不冒称并行或独立专家审查。

经过一段实际探索、正式验收或出现重要发现后，交换“方案、证据、结果、适用条件”。各路线自行决定是否借鉴，不要求全部收敛到同一个方案。保留不同成本、复杂度或适用场景下有价值的结果，而不是只剩一个总分最高的答案。

路线比较改变下一步探索方向，不替代正式验收。没有值得比较的不同路线时，不为凑流程制造方案。

## 三、保留记忆，不重复踩坑

维护一个轻量档案，至少包括：

```text
目标与验收规则：
当前路线和方案：
每次提交：编号｜方案内容或位置｜所属路线｜验收结果｜证据｜失败或未验证项
当前最佳与有价值的备选：
已尝试的办法及失败条件：
已确认的发现与来源：
下一步问题与剩余预算：
```

记录全部正式提交，包括失败；每条路线保留关键试验发现。不要只保留分数或摘要，方案本身也应能找回。短任务可在当前上下文维护；复杂任务在可用且获准的工作区保存文件，不为简单任务搭建额外系统。

上下文不足或交接前，压缩成以上状态，保留证据位置和可恢复的方案。恢复时先读状态，再继续；没有新证据或条件变化，不重复已失败的尝试。没有持久化能力时，不宣称记录会跨会话自动保留。

## 四、按问题选择检查方式

| 任务 | 可以怎样试验 | 可以怎样验收 |
| --- | --- | --- |
| 分析与调研 | 比较不同解释，查原始来源，寻找反证 | 关键结论有依据，矛盾已处理，事实与推测分开 |
| 设计与写作 | 做不同版本，走查场景，核对信息与表达 | 满足用途、受众和约束；实际用户反馈与自评分开 |
| 开发与排错 | 复现问题，运行样例，测量改动效果 | 功能、回归和性能检查；无法运行的明确标记 |
| 规划与决策 | 比较路径，核算成本，改变假设做情景分析 | 检查资源、依赖与风险；预测不冒充已经实现的效果 |

这些只是选用方式，不是额外必做阶段。先解决问题，不为了流程而制造工作。

## 五、停止并交付

满足目标且继续探索收益不大时收束；预算耗尽、必要工具或授权缺失、没有有价值的下一步时也应停止。停滞时先换假设、方法或路线，不机械重复，也不无限追加循环。

从已验收方案中选择最符合用户目标的版本，不直接交付最后一次改动。合并方案后重新验收。没有方案满足全部要求时，交付最有用的部分，明确未满足项，不宣称完成；存在不可兼得的目标时，说明取舍。

最终回复以成果为主，简要说明：**结果是什么、依据是什么、还有什么不确定。** 默认不展示整份循环日志；用户需要时再提供可核对的记录。

只使用实际具备且获准使用的工具。遵守安全、隐私和授权边界，不以优化为由擅自执行高风险或不可逆操作。不编造试验、引用、成绩或用户反馈，不承诺无法实际执行的后台工作。
