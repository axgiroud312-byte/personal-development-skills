# 写入技能流程与文档位置

只在项目 `AGENTS.md` 中添加或更新“技能流程与文档位置”一节，保留其他内容；文件缺失才创建，同类说明已有则原位修改，不重复追加。后续修正文档位置无需重新调用。

先读取已有 `AGENTS.md`、实际可用的本套技能、项目文档路径和已配置的任务位置。只核对写这段说明所需的信息，不调查或配置技术栈、启动命令、CI、交付方式，不修改其他客户端入口。

## 写明技能如何使用

用简短说明覆盖实际可用的技能：

- 想法不清时用 `grilling` 在对话中澄清。
- 用户主动调用 `to-spec` 才整理整体开发规格；主动调用 `to-tickets` 才拆成有具体方案、依赖与结果的 Issue。主动调用 `design-ui` 才制作 HTML 原型，满意后提取 Token 供规格与实施引用。
- 单项开发用 `implement`，结合任务和实际情况自主实施；连续多任务用 `implement-spec` 协调整合，两者都集中开发、少做重复测试。设计按需参考 `design-quality`，做完后需要讲解时用 `explain-work`。

这些技能按任务需要组合，小改动直接实现，不强制依次走完。`setup-project-skills` 同样只由用户主动调用；已有调用的修改与续接无需反复点名。写入流程不代表执行其中任何阶段。

## 写明文档在哪里

用一张短表列出本项目 Spec、Issue、HTML 原型和 Design Token 的实际位置。已有位置直接引用；尚未建立时明确标记，默认位置可写为待建立的 `docs/specs/`、`docs/issues/`、`docs/design/design-board.html` 与 `docs/design/design-token.md`，不假装文件已经存在，也不为填表创建它们。

使用远程 Issue 时记录真实仓库或任务入口，不再安排本地副本。Spec 只放规格内容，Issue 只放任务内容；不另设术语、领域、讨论、状态或总结文档。

## 保留工作准则

在同一节中写明；已有相同规则就沿用，不重复追加：

- 第一性原理大于一切，遇到问题首先从根源上解决。
- 以用户当前目标和明确约束确定要做什么，以实际代码和运行结果核实现状；文档冲突或方案过时时先查证，默认沿用现有实现惯例，不延续已证实的错误，完成后列出实质差异。
- 在授权范围内自主调整非强制工程方案，重要假设、方向变化与副作用简短说明，推断不能覆盖用户明确选择；改变目标、明确约束、关键体验或带来未授权的重要影响时由用户决定，其余工作继续。
- 集中开发，普通必要验证放在目标收尾；实际错误或会影响大量后续工作的关键假设可提前小范围检查。没有新改动、失败或未解决问题就不重复或扩大测试，不额外增加文档和流程。

完成后在聊天说明修改位置；本次发现的文档与实际情况差异也在聊天列出，不新增报告。
