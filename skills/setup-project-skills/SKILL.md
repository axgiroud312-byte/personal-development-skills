# 写入技能流程与文档位置

交付集中在项目 `AGENTS.md` 的“技能流程与文档位置”一节。已有同类说明原位更新，其他项目内容保持原样；文件缺失时创建。

先读取已有入口、可用技能、文档位置和任务入口，把真实可用的信息写清楚。

## 说明技能怎么衔接

- 想法需要讨论时用 `grilling`，在聊天中明确目标和关键选择。
- 用户调用 `to-spec` 写整体规格，调用 `to-tickets` 拆具体任务；需要看设计时调用 `design-ui`，先交原型，满意后提取 Token。
- 单项开发用 `implement`，连续多任务用 `implement-spec`；按 Issue 和实际代码自主执行，集中开发、少测试，最后统一收尾。
- 设计和界面开发参考 `design-quality`；需要听懂工作结果时用 `explain-work`。

按实际需要组合技能，简单任务可以直接实施。四个手动入口由用户启动，任务里的补充、修改和确认连续处理。

## 说明文档在哪里

用一张短表列出本项目 Spec、Issue、HTML 原型和 Token 的实际位置。待建立的位置标明状态，供后续需要时使用。

默认位置是 `docs/specs/`、`docs/issues/`、`docs/design/design-board.html` 和 `docs/design/design-token.md`。使用远程 Issue 时记录真实任务入口，任务正文集中在远程。

## 写入简短工作准则

已有相同规则直接沿用：

- 第一性原理大于一切，遇到问题首先从根源上解决。
- 用户当前目标和明确要求决定方向；代码与运行结果帮助核实现状。文档有冲突时先查证，沿用合适的现有实现，修正已证实的错误，完成后说明重要差异。
- 工程细节自主处理，重要假设和方案变化简短说明。影响用户目标、明确要求、关键体验或新增重要影响的取舍，由用户决定，其余工作继续。
- 集中完成开发，目标收尾统一必要检查；实际错误和影响后续工作的关键疑问先小范围核实。检查通过后推进交付，新变化按影响复查。

完成后在聊天说明修改位置和重要差异。
