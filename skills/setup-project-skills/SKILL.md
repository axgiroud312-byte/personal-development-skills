# 让项目找到技能与工作依据

读取项目现有 `AGENTS.md`、可用技能、权威资料与任务入口，把真实可用的信息写进项目 `AGENTS.md`。已有同类内容原位维护，保留其他项目指令；文件缺失时创建，内容和组织方式按项目需要决定。

## 说明职责与调用方式

按项目实际需要说明可用技能的职责：

- `grill-me` 按决策依赖分轮追问关键选择，每问提供推荐，代码能查明的事实由 Agent 调查。
- `to-spec` 综合当前对话和实际代码，将已有决定整理为 Spec：问题、解决方案、用户故事、已确定的实现决定，以及按需补充的内容。
- `to-tickets` 将 Spec 组织为简洁的开发 Issue，写清目标、预期行为和真实依赖，按完整功能尽量合并任务。
- `implement-pr` 按真实依赖编排任务，每任务使用新的独立子 Agent、worktree 和分支，汇入单一集成分支。整体完成后由主 Agent 统一测试、验证与构建，再安排新的独立 Agent 全局审查、修复并交付一个 PR。
- `design-ui` 根据需求探索和完善界面；`design-quality` 结合真实页面判断布局、信息层级与 AI slop。
- `component-variants` 结合当前组件库探索同一组件的多套设计与交互方案，提供可切换的对比预览，按用户选择继续细化。
- `explain-work` 用通俗中文讲清实际成果和使用方式。

四个主入口 `grill-me`、`to-spec`、`to-tickets`、`implement-pr` 由用户分别手动调用和衔接。`design-ui` 与本技能也保留手动入口，其余技能延续当前触发方式。已有决定、Spec 或 Issue 时可从对应入口开始，一次调用内已授权的调查、修改与补充工作连续完成。

本技能按需用于记录项目约定，其他技能可独立使用。

## 记录实际资料位置

沿用项目的权威来源，写清各类资料的实际入口和必要关联，每份正文在一个位置维护。项目尚未建立的位置如实说明。

- **Spec：** 已有关联 Spec 原位更新；新 Spec 优先发布到项目已配置的任务系统，可用独立 Spec Issue 记录方案。未配置远程入口时用 `docs/specs/<slug>.md`。项目已有 `docs/specs/` 等权威来源时继续沿用，任务系统中保留链接。
- **开发 Issue：** 优先使用项目远程任务系统；未配置远程入口时用 `docs/issues/<feature>/<NN>-<slug>.md`，一票一文件。区分用于记录方案的 Spec Issue 与执行开发的 Issue，标签沿用项目已有配置。
- **交付记录：** PR 或同一交付记录承载集成结果、整体验证、构建与全局审查结论，开发进展与实现结果写回相应 Issue。
- **设计资料：** 沿用现有原型与 Token 位置；新建时可用 `docs/design/design-board.html` 和 `docs/design/design-token.md`，与相关 Spec 相互引用。

## 融入工作原则

按项目已有表达组织以下原则：

- 对用户真实意图和成果负责，主动调查代码与材料，按当前问题决定深度。事实自己核实，重要取舍带着建议讨论，已有决定直接沿用。
- 第一性原理大于一切，遇到问题先查根源。文档与代码有差异时查明原因，将重要调整写回对应资料。
- 开发任务围绕完整用户功能组织。同一功能的 UI、API、状态和数据改动放在同一张 Issue，细步骤写在票内；仅按独立价值、真实阻塞或单次独立上下文容量拆分。
- Issue 聚焦开发目标、范围、预期行为、实施依据和依赖。整体验证与审查在集成完成后进行，结论记录到 PR 或同一交付记录。
- 在确定的任务范围内自主处理常规工程选择。新事实推翻原方案或用户改变目标时，说明影响并修订相关决定和任务，其余明确工作继续。
- 集中开发，实际错误与影响后续工作的疑问先做小范围核实，整体完成后统一必要检查。完成的 PR 交给用户决定合并。

完成后说明修改位置与重要变化。
