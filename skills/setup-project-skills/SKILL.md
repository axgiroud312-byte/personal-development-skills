# 配置项目技能

只配置当前项目实际需要的约定。已有配置足够时沿用；其他技能可独立使用，不要求每个项目或每次任务都先运行本技能。

## 配置方法

1. 读取项目现有 `AGENTS.md`、`CLAUDE.md`、仓库远端、文档布局、`package.json`、锁文件及项目脚本，找出已有约定与实际入口。
2. 从现有材料和用户要求确定下列必要信息。缺失信息先调查；只有无法推断且会影响配置的选择才提问，给出推荐项。
3. 优先原位更新已有配置。没有合适位置时使用 `docs/agents/project.md`，只记录当前有用的内容；不创建空的规格、任务或领域文档。
4. 按下文确定唯一的项目状态入口与主 Agent 的维护职责。沿用已有入口；新建时先核实目标与本次授权，只初始化有事实依据的状态。
5. 核对完约定后，在目标项目的 Agent 入口文件中写入或更新固定标题 `## 项目索引`。沿用项目现有分工；只有 `CLAUDE.md` 时写入该文件，只有 `AGENTS.md` 时写入该文件，两者都没有时新建 `AGENTS.md`。两者都有时，在负责项目事实的入口维护一份索引，另一入口按既有分工引用，不复制整张表。
6. 原位更新索引及本次相关配置，保留其他内容；核对路径、命令、状态入口与实际项目一致，说明写入位置和未确定项。除按授权建立固定状态 Issue 外，项目配置不自动创建任务 Issue、远端标签、提交或执行发布。

## 压缩项目索引

入口文件保存一张便于每次接手时查找的短表，列为“项目事实｜位置或命令｜一句用途”。只收录实际存在或本次已建立并核实的文件、目录、入口及命令；仅确定了将来的存放位置但文件尚不存在时，留在项目约定中，不列入索引。按实际情况选择以下行，不填空项：

- 业务术语与领域记录。
- Spec。
- 界面设计规范。
- 共享 Token 源文件。
- 组件清单或样板入口。
- 任务跟踪位置与唯一项目状态入口，分别注明用途。
- 开发、测试、预览命令：只写在 `package.json` 或项目脚本中查到的命令，沿用已核实的包管理器，注明必要工作目录和脚本来源。未查到就省略，不补惯用命令；查到不代表已经运行通过。

表旁保留一句指令：“涉及上述内容时，先读对应文件或入口再动手，不凭记忆或默认假设；位置或命令变化时同步更新本索引。”有独立项目约定文档时，也在表中放一条路径与用途引用。

索引只放路径、入口或真实命令与一句用途，不复制 Spec、领域定义、Token 数值、动态进度或流程正文，建议整个段落不超过 40 行。再次配置时按 `## 项目索引` 定位，在下一个同级或更高级标题之前原位更新，保留段落之外的内容；已有重复索引时合并为一份，不继续追加。

## 固定项目状态入口

已有明确入口时直接沿用。没有约定且项目使用 GitHub 时，默认复用或建立一个固定的“项目当前状态”Issue；没有 GitHub 时使用项目根目录 `STATUS.md`。两者只选一个作为项目级状态摘要，不另做双向镜像。先查已有入口，避免重复创建；远端写入受本次授权约束，未获授权或不可用时说明待建立，不虚构编号或声称已更新，也不静默另建第二个入口。

按已有 README 结构放一个稳定的查看链接，并在项目索引中记录同一入口。详细任务、设计和验证证据仍留在原文档或 Issue，状态页只写短摘要及来源链接：

- 最近核对时间、当前阶段和本次范围。
- 当前目标。
- 已完成什么、目前能用什么及实际验证范围。
- 接下来做什么、实际阻碍。
- 需要用户决定什么；没有就写“无”。

将下列维护约定写入项目既有的约定位置，由入口索引引用；没有其他位置时可作为入口文件中独立的短约定段落，不塞入索引表：

- 保留用户先完成本次整体设计、再进入开发的顺序；状态页可明确写“正在完整设计，开发尚未开始”。记录已有阶段与结论，不增加批准步骤或为了填写进度提前开发。
- 由当前主 Agent 维护项目级摘要；子 Agent 提供或更新自己负责的任务事实，由主 Agent 核对后汇总。多个会话协作时明确一个汇总负责人，避免同时覆盖正文。
- 开始或接手工作时先读状态入口并核对相关事实；关键设计结论、阶段、阻碍或交付发生变化，以及暂停或结束本轮工作前更新。没有实质变化不反复改写，不记录每次工具调用。
- 更新前读取最新正文，只调整约定的状态内容并保留其他内容。区分设计已完成、代码已修改、分支可试用、已合并和用户已验收；分支结果注明实际分支或 PR，不能写成主线已经可用。
- 状态是最近一次核对后的摘要，更新依赖工作中的 Agent，不承诺后台实时刷新。无法读取新证据或会话中断时，不把旧记录当成当前事实；下次接手先核对再更新，并如实说明未核实或未成功写入的部分。

## 需要时记录

- **文档位置与职责**：术语或领域记录保存业务定义与规则，Spec 引用领域及界面设计依据并保存整体技术设计与共同约束，Issue 保存局部设计、任务细节和具体验收；每个决定只维护一份有效正文。沿用现状；新项目可用 `docs/specs/`、`GLOSSARY.md` 和 `docs/domain/`。
- **领域模型衔接**：Spec 整体设计前检查本次业务定义，已有模型直接复用，不足时主动衔接 `domain-modeling` 或等价梳理。拆任务与实施沿用这些定义，业务变化同步领域记录、受影响的 Spec、Issue、验收与实现，不要求为小修增加文档阶段。
- **界面设计衔接**：需求与核心领域定义清楚后，`design-ui` 与 Spec 配合；拆具体 UI Issue 前具备本次足够的设计依据，已有设计系统和小改动直接复用。记录项目设计规范（缺省 `DESIGN.md`）、共享 Token 源码、组件及 registry 清单和样板入口；实际 Token 值只在源码维护，由样板与业务组件共用。设计变化同步权威依据及受影响任务，不增加阶段批准或独立展示站。
- **前端默认搭配**：通用 SaaS、工作台与 Agent 界面尚无约定时，读取可用 `design-ui` 的前端默认搭配，记录本项目采用的能力、统一方案与必要例外。已有项目方案优先，按页面需要引入依赖；配置约定本身不安装整套依赖或迁移技术栈。
- **任务跟踪**：跟踪平台、已核实的仓库或项目，以及必要状态规则。无约定时优先已确定的 GitHub 仓库，没有 GitHub 时用 `docs/issues/`；多个远端有歧义时先确认目标。
- **验证方式**：测试和审查分别采用什么方式、是否启用，以及已有运行入口和真实操作验收方式。UI 通过项目实际浏览器或桌面入口核对流程与交互，有视觉参考时核对布局几何。按可观察结果与改动风险选择，只写查到的命令，不要求每次运行全部检查或生成构建产物。
- **交付与关联**：目标分支、Issue 与 PR 的关联方式、合并及关闭条件。沿用已有授权；只请求 PR 的任务不自动合并或关闭。
- **清理位置**：本项目临时构建目录、需要保留的交付位置和临时工作树归属。提交推送及 PR 建立后，先保存交付结果再清理，保留 PR 远端分支。
- **协作约定**：项目已有的工作区及共享修改方式，只补确实需要的部分。

配置说明应让 Agent 找到现有材料和正确的操作位置。没有术语表、Spec 或固定任务系统本身不阻止开发；缺少发布目的地等必要信息时只补当前缺项。
