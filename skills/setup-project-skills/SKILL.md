# 让项目找到技能与工作依据

读取项目现有入口、可用技能、资料位置和任务入口，把真实可用的信息写进项目 `AGENTS.md`。已有同类内容原位维护，保留其他项目指令；文件缺失时创建，内容和组织方式按项目需要决定。

## 说明各技能承担什么

按项目实际需要说明可用技能的职责与联系：

- `grilling` 围绕关键决策、需求边界与重要假设讨论，逐步形成共同理解。
- `to-spec` 沉淀目标、总体方案和设计架构，按需求包含原型或 Token 等设计表达。
- `to-tickets` 在总体方案上调查并补足实施细节，拆成可执行任务。
- `design-ui` 根据需求探索和完善界面；`design-quality` 帮助判断布局、信息和整体效果。
- `implement` 完成具体任务；`implement-spec` 协调多个 Issue，执行方式复用 implement，集中开发、少测试，统一收尾。
- `explain-work` 用通俗中文讲清实际成果和使用方式。

这些职责按需要衔接，任务里的理解、调查、讨论和修正持续发生，简单任务可以直接实施。保留手动入口的调用配置，按当前授权完成任务中需要的补充产物。

## 写清资料位置与协作原则

记录本项目 Spec、Issue、设计等资料的实际位置及必要关联，表达形式自主决定。尚未建立的位置如实说明；远程 Issue 可用时记录真实入口，任务正文集中在远程。

新建资料的默认位置可参考 `docs/specs/`、`docs/issues/` 和 `docs/design/`，已有资料沿用原处。

将下列原则融入已有工作约定，保留适合项目的表达：

- 对用户真实意图和成果负责。主动探查实际情况，为关键判断取得依据；调查的对象和深度随尚未理解的问题决定。假设建立在已理解的需求上，重要分歧带着发现与建议讨论，新的认识持续修正已有结论。
- 需求对齐贯穿讨论、Spec、Issue 与实施，已明确的决定直接沿用。产物结构、详略和组织方式由模型根据任务判断。
- 第一性原理大于一切，遇到问题先查根源。代码与运行结果帮助核实现状；文档与代码不一致时沿用合适的现有惯例，完成后说明重要差异。
- 常规工程选择自主处理，影响目标、明确要求或关键体验的取舍由用户决定，其余工作继续。
- 集中开发，少做测试；目标收尾统一必要检查，实际错误和影响后续工作的疑问先小范围核实，检查通过后推进交付。

完成后说明修改位置与重要变化。
