## 1. 目标与依据

近期目标是让单个使用者在桌面环境中查看、新增和编辑订阅，清楚看到金额与下次续订日期。新增和编辑必须真正写入现有本地存储；提交成功后从服务端重新读取结果，刷新页面、重启本地服务后仍能读取。

方案只依据当前项目内的以下文件，不引用以前聊天中的规则：

- [本次需求](request.md)：功能、页面、持久化要求、范围排除项和归档待定事项。
- [README](../README.md)：项目没有正式界面；声明时区为 `Asia/Shanghai`，数据路径为 `data/subscriptions.json`。
- [现有源码](../src/store.py)：只定义 `TIME_ZONE`、`STORE_PATH` 和 `FIELDS` 三项常量。

## 4. 组件职责与端到端流程

### 4.1 最小组件边界

| 组件 | 职责 | 边界 |
| --- | --- | --- |
| 桌面界面 | 列表、详情、设置、弹窗、表单校验反馈、路由与分页状态 | 不直接操作 JSON 文件，不自行生成最终记录 ID |
| 本地 API/应用服务 | 接收契约数据、执行权威校验、生成 ID、分页、映射错误 | 仅服务本机使用；不引入账号或公网部署 |
| Python 存储层 | 加载、校验、创建、更新、原子替换 JSON 文件 | 沿用现有存储路径；保存完整记录；不引入数据库 |

若最终采用 HTTP，使用下文的接口提案；若采用桌面桥接，保留等价操作、DTO、分页和错误码。先确定载体再定传输方式，不把接口路径当成已选定框架。

### 4.2 新增流程

1. 打开新增弹窗，填写业务字段；金额输入转换为整数 `amount_cents`，字段错误指向相同业务字段。
2. 提交时进入等待状态，防止同一次点击被重复提交；本地服务再次校验并生成唯一 ID。
3. 存储层完成写入后，服务才返回成功和完整记录。写入失败时保留表单，展示稳定错误，不提示保存成功。
4. 成功后关闭弹窗并请求列表第一页。列表中的新条目必须来自新的读取结果，不能只向前端数组追加一条伪造成功记录。
5. 若保存成功但列表重读失败，分别提示“已保存，列表刷新失败”并提供重新加载；不要把保存失败与刷新失败混为一谈，也不要引导用户再次新增。

### 4.3 编辑与返回流程

1. 列表通过 ID 打开详情，同时携带来源页码；详情单独读取记录，直接打开详情也必须可用。
2. 编辑位置建议放在详情页；仅提交可编辑字段，ID 保持不变。
3. 服务将修改与现有记录合并、校验并写入；保存成功后重新读取详情，返回列表时重新读取原页数据。
4. 保存失败时保留输入及原记录；未知 ID 显示“记录不存在”。详情返回列表保留原页码，直接进入详情时默认返回第一页。

## 5. 统一数据与错误契约提案

### 5.1 业务记录

表单提交对象、API 记录对象、存储记录使用同一套字段名称。控件可有显示态，但禁止把 `price`、`nextBillingDate` 等另一套别名写入 API 或 JSON。分页信息和错误对象属于协议元数据，不写入订阅记录。

| 字段 | 拟定类型与含义 | 新增 / 编辑 | 校验与展示 |
| --- | --- | --- | --- |
| `id` | 不透明的非空唯一字符串，由服务生成 | 新增请求不传；编辑不可改 | 读取和定位记录使用；持久化后不变 |
| `name` | 非空字符串，订阅名称 | 必填 / 可改 | 去除首尾空白后不能为空；长度上限在契约定稿时统一 |
| `amount_cents` | 整数，支持币种中以“分”为单位的金额 | 必填 / 可改 | 只接受整数分值，不存浮点数或负值；零值政策和上限待定；金额显示带币种标识 |
| `currency` | 大写币种代码 | 必填 / 可改 | 只接受已声明支持的币种；具体集合与精度在 Issue 001 定稿 |
| `renewal_date` | `YYYY-MM-DD`，用户填写的下次续订日 | 必填 / 可改 | 必须是真实日历日期；按本地日期处理，不转换成 UTC 时间戳 |

补充规则：

- 日期过期仍可展示和编辑；本期不自动推进续订日期，不从日期推导尚未定义的订阅周期。
- 金额转换使用十进制定点规则，避免二进制浮点运算导致分位误差；控件显示值最终映射回 `amount_cents`。
- 未声明字段和客户端提交的 `id` 不应悄悄落库；明确报错。存储读取也校验同一数据约束，发现损坏不能默默覆盖为空列表。
- 同名订阅可能合法，不以名称去重；ID 才是记录身份。

### 5.2 操作与分页

以下为 HTTP 传输时的接口提案；没有对应的现有实现。

| 操作 | 拟定接口 | 输入 | 成功结果 |
| --- | --- | --- | --- |
| 分页列表 | `GET /api/subscriptions` | `page`、`page_size` | `items` 与 `page`、`page_size`、`total` |
| 单条详情 | `GET /api/subscriptions/{id}` | ID | 完整五字段记录 |
| 新增 | `POST /api/subscriptions` | 四个业务字段，不含 ID | 保存后的完整记录；HTTP 201 |
| 编辑 | `PATCH /api/subscriptions/{id}` | 至少一个可编辑字段 | 合并校验并保存后的完整记录；HTTP 200 |

分页建议：页码从 1 开始，默认每页 20 条，允许范围 1–100；无效参数明确报错。超过末页返回空 `items` 和实际 `total`，界面据此回到有效页并重读。总数为 0 时展示空态。

默认顺序建议为新增记录在前，编辑不改变位置。存储数组顺序作为首期稳定顺序，不额外增加 `created_at` 字段。新增成功后读取第一页即可看到新记录；暂不增加排序、搜索或筛选能力。

### 5.3 错误语义

错误响应建议统一为 `error.code`、`error.message` 和可选的 `error.field_errors`；字段错误条目使用 `field`、`code`、`message`。`field` 必须使用上表中的字段名。中文提示由同一份错误映射约定，界面预校验不能与服务端规则相反。

| 语义 | 建议错误码 | HTTP 提案 | 界面行为 |
| --- | --- | --- | --- |
| 格式或分页参数不合法 | `INVALID_REQUEST` | 400 | 提示请求有误，允许修正或重试 |
| 字段不合法 | `VALIDATION_ERROR` | 422 | 具体字段标记原因，保留输入 |
| 记录不存在 | `NOT_FOUND` | 404 | 显示不存在状态并可返回列表 |
| 文件读取失败或内容损坏 | `STORAGE_READ_FAILED` | 500 | 明确读取失败，不伪装成空列表 |
| 文件写入失败 | `STORAGE_WRITE_FAILED` | 500 | 明确未保存，保留输入及原数据 |

字段原因至少覆盖 `REQUIRED`、`INVALID_TYPE`、`INVALID_VALUE`、`UNSUPPORTED_CURRENCY`、`INVALID_DATE`、`UNKNOWN_FIELD`、`IMMUTABLE_FIELD`。前端对服务端错误码统一映射；连接中断或响应丢失需独立提示，不能凭超时断言写入一定失败。首期不为此扩展整套幂等协议，用户重试前先重读列表或详情核对结果。

## 6. JSON 存储方案

1. **固定路径含义。** 沿用 `data/subscriptions.json`，实施时明确相对于项目根目录解析，避免从不同工作目录启动时产生另一份数据。
2. **拟定文件结构。** 使用由五字段完整记录组成的 JSON 数组。现有代码未规定顶层结构，这属于新提案；实施前如出现真实数据文件，先检查其结构和兼容性，不能直接覆盖或擅自迁移。
3. **区分空数据与故障。** 首次无数据文件可读为空集合，首次有效保存时创建目录和文件；已有但无效的 JSON、重复 ID、缺字段、权限错误均应返回存储错误并保留原文件。
4. **完整保存。** 对新增、更新执行读取—校验—修改—写入；在目标目录写临时文件并原子替换，成功后才返回成功。同一服务进程内串行化写入，避免同时提交互相覆盖。
5. **限制并发假设。** 首期为一个本地服务实例；外部手工编辑和多个服务进程同时写入不属于本期支持场景，启动说明中明确这一点，不借此引入数据库改造。
6. **更新不扩范围。** 新增放在数组前部；编辑保持 ID 与原位置；不做删除、归档或历史版本化。

## 9. 本期完成标准

以下是未来实现的验收清单，本次未执行，也不表示当前项目已经可运行。

- 在桌面入口打开列表、详情和设置；中文信息清楚，金额带币种、日期不出现时区偏移。
- 新增一条合法订阅后，记录已写入指定 JSON 文件；弹窗成功后通过新列表请求读到同一 ID，位于第一页；刷新页面并重启服务后仍保留。
- 编辑名称、金额、币种或日期后，保存结果反映在详情及返回后的列表；重启后仍是更新后的值；ID 和其他记录不变。
- 使用超过一页的数据验证总数、页码切换、稳定顺序、详情返回保留页码；验证空列表与越界页处理。
- 前端、API 和 JSON 的五字段一致；同一非法金额、日期或币种得到一致的错误语义；直接调用 API 不能绕过权威校验。
- 损坏文件、读取失败、写入失败、记录不存在和连接失败有准确提示；不能显示虚假保存成功，不能把损坏文件覆盖成空数组。
- 新增成功但列表刷新失败、提交响应不确定等情况分别处理，不诱导重复创建。
- README 记载实际启动方式、有效时区、存储路径和范围；没有夹带归档、删除、账号或其他排除项。
