# 十轮工作流实验与技能优化（2026-10-26）

基线：d8c07780022e685fdc7da665664fda424cea97e0；本轮测试以效果为首要验收指标，篇幅和文档数量为次要因素。完整可运行的隔离样例、Python/Chromium 测试与截图另附于本次对话。

## 方法

借鉴 [AgenticEvolve 论文](https://arxiv.org/abs/2610.31326)：持久保留候选与失败、先自设计局部实验、执行实验、按结果调整候选，再做正式评估。这里只采用其局部实验与反馈归档思想，没有复制多岛进化、MAP-Elites 或独立模型采样。

同时参照 GitHub 官方 [Spec Kit](https://github.github.com/spec-kit/quickstart.html)、[复杂功能的分阶段执行](https://github.github.com/spec-kit/concepts/complex-features.html) 和 [实施后收敛](https://github.github.com/spec-kit/guides/evolving-specs.html)：先缩小单次执行范围，再视实际复杂度拆 Spec；先确认目标，再用真实代码核对是否达成，不能修改目标来掩盖未实现部分。

**证据类型：**真实执行=Python/Chromium；流程产物检查=同一助理按 Skill 编写的样例和断言；静态检查=技能元数据与相对链接。不存在可调用的独立 LLM Skill runner，因此这不是十次独立模型会话或显著性试验。

## 本轮固化到 Skill 的规则

1. to-spec：先按阶段缩小执行上下文，只有能力/验收边界真实独立时再拆多份 Spec。
2. to-tickets：拆任务前核对关键成功与失败场景是否有交付与验收覆盖。
3. design-ui 与设计质量参考：视觉之外检查真实状态/权限契约，不能把设计板模拟成已经授权或接通后端。
4. implement：边界测试关注状态不变量与失败时既有数据不被破坏；重启/恢复按任务需要选择。
5. implement-spec：按可验收的端到端批次工作，实施后把 Spec、Issue 与真实代码核对，未实现项回到任务和实施中，不能修改意图冒充完成。
6. Spec/Issue 模板与维护约定同步跨层追踪，并明确局部实验与正式/独立模型评估的不同证据等级。

## 已知边界

十轮来自**同一助理会话的场景执行和工具反馈**，不是十个隔离 LLM 运行，不证明提示词修改对其他模型带来可量化提升。Chromium 窄屏为桌面视口模拟，未测真实手机或读屏器；没有将设计板连接到真实 API，也没有真实远端 Issue、PR/工作树并发验收。最终效果是对**这套隔离样例及可观察约束**成立；进一步效果比较需要冻结评分器、用旧/新 Skill 独立运行同一组未泄露答案的测试并记录成本。
