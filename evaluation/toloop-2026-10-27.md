# 2026-10-27：轻量工程技能的迭代评估

本次按用户提供的 `toloop` 执行两条独立路线、共同评分、反馈修订与实际任务对照。目标是从方案到前后端落地都实用，同时保留集中开发、阶段收尾、不默认 TDD 的方法。分数仅用于本次候选比较，不等于外部认证、任务成功率或用户认可。

## 评估依据与边界

借鉴 [Agent Skills 评估指南](https://agentskills.io/skill-creation/evaluating-skills) 的真实任务、干净上下文、新旧版/无技能对照与实际产物评价，以及 [SWE-Skills-Bench](https://arxiv.org/abs/2603.15401) 的固定项目和执行证据思路。Issue 划分参考 [Matt Pocock to-tickets](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-tickets/SKILL.md) 的完整业务切片与真实依赖；按用户偏好不采用其 [implement](https://github.com/mattpocock/skills/blob/main/skills/engineering/implement/SKILL.md) 的默认 TDD。

没有运行上述公开基准全套。本次是同一环境、少量自建项目的单次试跑；规划对照的输入文件一致，执行 Agent 使用独立上下文，产物匿名交给评估 Agent。它能发现具体问题，不能证明所有项目、模型或多轮重复下都有同样收益。

## 固定规则

用户追加实用性、配置和扩展要求后，在候选比较前将 v1 改为 v2；此后未改标准。v2：实用交付 35、衔接与独立 20、要求与方法完整 20、轻量可读 15、配置与扩展 10。分别考察完整请求/校验/保存/响应链、真实依赖与交接、可选入口和缺失回退、全部设计要求和模板三问、文档负担、配置优先级和专业工具替换。

硬要求：保留九项职责及已确认设计细节；Spec/Issue 均说明想实现、想要、不想要；引用可解析且交接明确；集中实现，必要测试/构建在授权目标或明确独立交付阶段收尾；不把静态判断冒充实际效果。达到静态合格、具体失败已修复且必要复跑无阻断时停止，不为追求满分继续添规则。

## 实际任务

### 1. 同一需求生成 Spec 与本地 Issue

输入为自用桌面订阅管理工具：查看、新增、编辑、续订日期，列表/详情/设置、弹窗和分页；API 与保存使用一致字段及错误，刷新后保留数据。排除账号、手机端、付费和外部集成；归档历史编辑规则留到后续，不阻塞当前范围。项目仅有 Python 存储常量，README 与源码时区冲突。授权仅规划，不设计、开发或写远端。

产物评分另用固定 100 分规则：范围 20、事实/未知/意图 20、可实施契约/保存/结果 25、Issue 依赖/交接 20、轻量与选择负担 15。它衡量这个任务产物，与上面的技能静态分不可相加或互换。

| 条件 | 新增文档 / Issue | 产物字符数 | 匿名产物评分 | 主要发现 |
| --- | ---: | ---: | ---: | --- |
| 不使用本套技能 | 10 / 8 | 14,983 | 81 | 把时区、技术载体、货币、限制等集中为全局阻塞，设置契约较薄。 |
| 原版 | 6 / 4 | 13,070 | 95 | 公共契约较集中，整体平衡；技术载体决定的责任归属可更明确。 |
| C2 | 7 / 5 | 18,195 | 92 | 交接与依赖更清楚，但公共规则重复、选型确认增负担，规划另造了设计文件名与 JSON Token。 |
| C3 | 5 / 3 | 10,547 | 96 | 运行方案与责任归属落定；标准集中编号、Issue 引用认领；无核心结果遗漏。 |

设计格式漂移由主 Agent 的跨技能交接复核发现；匿名评估器未读取技能源。C3 没有限制 Issue 数量，也没有禁止调查任务；只为需要独立交接的成果拆任务。已有 Spec 时引用具体章节/场景，缺少 Spec 时仍补足执行信息。读取可用制作技能约定不等于执行制作；不可用则只写产物类型，之后补链接。

### 2. 连续完成真实前后端功能

C2 的 `implement-spec` 与 `implement` 在一个已有 Python 标准库服务和原生页面的项目完成两个 Issue：真实新增 API、页面接入与错误反馈。C3 未改这两份技能。

执行 Agent 实际启动 HTTP 服务，检查新增后的文件保存、重新读取和重启后读取；页面原脚本在轻量 DOM 环境连接真实 API，检查新增、重新载入、错误与输入保留。另核对无效请求、并发写入与替换失败，原数据和用户笔记保持原样。两项实现合并后统一收尾，没有逐 Issue 铺测试阶段，没有提交或部署测试项目。

环境无 Chromium 可执行文件，未做真实浏览器视觉和交互验收；轻量 DOM 证据不能替代真实浏览器。执行记录保留实际检查范围，不声明部署或用户验收。

### 3. 完整前端原型

C2 的 `design-ui` 按指定桌面尺寸、列表/详情/设置及子页、弹窗/抽屉、分页、字体字重、颜色、200ms 动效与减少动态效果要求，产出一个 `design-board.html` 与一个 `design-token.md`；C3 未改此技能。

实际产物静态检查确认两个交付文件、指定 CSS 变量值与 Token 对应、主要页面/浮层和减少动态效果标记，页面 JavaScript 语法检查通过。未做浏览器截图或视觉评分，因此不把文件存在和语法通过写成设计质量保证。

## 选择与剩余限制

选择 C3：它在固定 v2 静态规则下与 C2 同为最高的 98 分，实际规划复跑由 92 提高到 96，高于同案原版的 95；执行和设计主体未改，沿用已完成的实际试跑证据。没有因模板更短直接加分，也没有将这个分数解释为 96% 的成功率。金额 JSON 类型、名称计数单位、详情 URL 及无现成设计约定时的具体格式仍需执行者在项目内明确，均不要求增加通用流程或请用户处理普通实现选择。

保留九个可选职责入口，没有新增技能、配置框架或日常评估流程。日常小修可直接 implement；需要管理任务时使用 Issue，复杂目标按需补方案和原型。保留少量跨入口短提醒以支持独立使用，未为最后两分继续增加条件。grilling、domain-modeling、setup-project-skills、explain-work 本次主要接受静态审阅，没有各自单独进行多模型行为评估。
