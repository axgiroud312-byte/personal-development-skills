# 手动触发与设计拆分迭代记录

日期：2026-10-30。基线：`3c3a35ff791f388120f48b091dd1af1507cc278c`。本次按用户主动要求进行多轮优化，不将这些评估变成日常开发步骤。

## 目标与固定约束

- `setup-project-skills`、`to-spec`、`to-tickets`、`design-ui`、`task-loop` 仅用户主动调用；其他技能保持按需使用。
- 好坏设计独立为 `design-quality`，原指导正文不改。生成设计版与 Token 的流程集中在简短的 `design-ui`。
- 需求不清时问通常 3–5 个关键问题，已清楚就制作。先交一个 HTML，用户确认该版后输出一份 Token；只确认草图不追加 Token。
- 联动复用已有资料，不自动启动另一手动流程，也不以“等价方法”生成同类专项产物。
- 保留集中开发、收尾验证与构建、三问模板、grilling 中性选项、不编造完成状态以及原有单项/多项实施分工。
- 使用用户原有 `task-loop` v2：试验、固定验收、路线交流、失败记录和按预算停止；方法正文不改。

## 路线比较与四轮迭代

先比较“只在 description 写手动”和“原生开关配合正文边界”两种方式。前者不能改变原有 `allow_implicit_invocation: true`，也不能消除执行技能的自动衔接；采用后者，没有新增路由技能或配置框架。

| 轮次 | 可恢复候选 | 检查与实际发现 | 后续修改 |
| --- | --- | --- | --- |
| 1 | 拆出设计指导、导入原 loop、加五组手动开关与跨技能边界的候选 | YAML、内部链接和原文比较通过。模糊需求试跑问了 4 题；明确需求交一个 HTML 且没有 Token，但首次产物落在临时根目录，没有使用默认 `docs/design/`。 | 保留已通过的流程；收紧默认路径，并继续检查版本衔接。 |
| 2 | 补全联动与设计/Token 对应关系的候选 | 普通按钮文字修改只改目标文件；独立静态复核确认原开发规则保留。发现独立安装 `design-ui` 时，“确认草图”可能被误读为 Token 阶段的确认。 | 在设计技能自身明确草图不追加 Token；Token 注明已确认设计版，旧 Token 不冒称对应未确认新版。 |
| 3 | 收紧草图、版本和默认路径的候选 | 草图确认、仅拆任务和默认路径试跑通过。完整设计确认后确实只新增一份 Token，但该文档展开到 101 行，仍偏向完整样式说明，不符合尽量简单的目标。 | 将 Token 明确为一张共用变量表；未变量化样式只引用源码，不展开组件尺寸、状态和响应式清单。 |
| 4 | 当前候选 | 用同一 HTML、同一确认请求交给新的独立 Agent：输出 29 行、1 张表，13 个实际使用变量均保留，并引用共用样式位置；不再展开整套样式规范。 | 保留精简后的候选，再核对设计修改时不会提前同步 Token，最后执行结构与原文检查。 |

当前环境没有 Codex、Claude Code 或 Pi CLI，因此没有宣称已在这些宿主实测原生路由。独立 Agent 试跑验证的是文本指导下的实际行为，不等于跨模型稳定性保证。HTML 示例未做浏览器视觉验收；这些示例只用于核对提问、产物范围与确认衔接，不作为用户项目的设计成品交付。
